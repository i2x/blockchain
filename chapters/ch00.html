0.1ฟังก์ชันแฮชและคุณสมบัติของ SHA-256

ทำไมต้องมีฟังก์ชันแฮช

ในเครือข่าย Bitcoin คอมพิวเตอร์หลายหมื่นเครื่องเก็บข้อมูลชุดเดียวกัน และต้องคอยตรวจว่าข้อมูลของแต่ละเครื่องตรงกัน ไม่มีใครแอบแก้ ข้อมูลทั้งหมดมีขนาดหลายร้อยกิกะไบต์ จึงส่งทั้งก้อนมาเทียบกันทุกครั้งไม่ได้ สิ่งที่ต้องการคือ ค่าสั้น ๆ ที่ใช้แทนข้อมูลทั้งก้อน ค่านี้ต้องเทียบกันได้ทันที และต้องเปลี่ยนไปเมื่อข้อมูลเปลี่ยนแม้เพียงตัวอักษรเดียว ฟังก์ชันแฮชทำหน้าที่นี้

นิยาม

ฟังก์ชันแฮช (Hash function) คือฟังก์ชันที่รับข้อมูลขนาดเท่าใดก็ได้ แล้วให้ผลลัพธ์ที่มีความยาวคงที่เสมอ ผลลัพธ์นี้เรียกว่า ค่าแฮช (hash) หรือ digest และใช้เป็นลายนิ้วมือ (fingerprint) ของข้อมูลได้ ข้อมูลชุดเดิมให้ค่าแฮชเดิมทุกครั้ง แต่ถ้าข้อมูลเปลี่ยนแม้เพียงเล็กน้อย ค่าแฮชจะเปลี่ยนไปจนดูไม่ออกเลยว่ามาจากข้อมูลที่ใกล้เคียงกัน (บิตเปลี่ยนไปราวครึ่งหนึ่ง ดู Avalanche effect ในตารางด้านล่าง)

Bitcoin ใช้ฟังก์ชัน SHA-256 ผลลัพธ์ยาว 256 บิต เขียนเป็นเลขฐานสิบหก (hexadecimal) ได้ 64 ตัวอักษร (1 ตัวอักษรฐานสิบหกแทน 4 บิต)

SHA-256("hello") = 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
SHA-256("Hello") = 185f8db32271fe25f561a6fc938b2e264306ec304eda518007d1764826381969
SHA-256("")      = e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855

ข้อความ "hello" กับ "Hello" ต่างกันเพียงตัวอักษรตัวแรก แต่ค่าแฮชไม่มีส่วนใดคล้ายกันเลย ส่วนข้อความว่างก็ยังได้ค่าแฮชยาว 64 ตัวอักษรเท่าเดิม

คุณสมบัติที่ต้องจำ

คุณสมบัติความหมายBitcoin ใช้ประโยชน์อย่างไร
Deterministicข้อมูลเดิมให้ค่าแฮชเดิมเสมอทุกโหนด (node) คำนวณแล้วได้ผลตรงกัน จึงตรวจสอบกันได้
Efficient (คำนวณได้เร็ว)หาค่าแฮชจากข้อมูลใช้เวลาน้อยตรวจบล็อกที่ได้รับได้ทันที
Pre-image resistance (one-way)รู้ค่าแฮชแล้วหาข้อมูลต้นทางไม่ได้ นอกจากเดาสุ่มไปเรื่อย ๆใกล้กับหลักของ Proof-of-Work ผู้ขุด (miner) ต้องหาค่าแฮชที่ต่ำกว่าเป้าหมาย (target) และไม่มีทางคำนวณย้อนจากเป้าหมายกลับมาหา nonce จึงต้องลองค่า nonce ทีละค่า (บทที่ 2) คุณสมบัติที่ PoW ใช้จริงจึงกว้างกว่านิยามนี้เล็กน้อย บางตำราเรียกว่า puzzle friendliness
Second pre-image resistanceมีข้อมูลชุดหนึ่งแล้ว หาข้อมูลชุดอื่นที่ให้ค่าแฮชเดียวกันไม่ได้ปลอมธุรกรรมให้มีค่าแฮชเท่าของจริงไม่ได้
Collision resistanceCollision (ข้อมูลสองชุดให้ค่าแฮชเดียวกัน) มีอยู่จริง เพราะข้อมูลนำเข้ามีได้ไม่จำกัด แต่ค่าแฮชมีเพียง 2256 แบบ ถึงอย่างนั้นก็ไม่มีใครหา collision ของ SHA-256 เจอได้ในทางปฏิบัติ เพราะต้องลองประมาณ 2128 ครั้งค่าแฮชใช้เป็นรหัสประจำตัวที่ไม่ซ้ำกันได้ เช่น txid และ block hash
Avalanche effectข้อมูลเปลี่ยนหนึ่งบิต ค่าแฮชเปลี่ยนประมาณครึ่งหนึ่งของบิตทั้งหมดแก้ข้อมูลเพียงเล็กน้อยก็ตรวจพบได้ทันที

ลองคำนวณเอง

พิมพ์ข้อความลงในสองช่องด้านล่าง หน้านี้จะคำนวณ SHA-256 ของทั้งสองข้อความ แล้วนับว่าต่างกันกี่บิตจากทั้งหมด 256 บิต ลองเปลี่ยนตัวอักษรเพียงตัวเดียวแล้วสังเกตผล ตัวอักษรฐานสิบหกที่ไม่ตรงกันจะแสดงเป็นสีแดง

Bitcoin ใช้แฮชที่ไหนบ้าง Block hash และ txid ใช้ SHA-256 สองรอบซ้อนกัน เรียกว่า SHA-256d หรือ double SHA-256 ส่วน address แบบดั้งเดิม (legacy) ได้จากการแฮช public key ด้วย SHA-256 แล้วแฮชผลอีกรอบด้วย RIPEMD-160 (เรียกรวมว่า HASH160) Merkle root (บทที่ 3) ได้จากการนำค่าแฮชของธุรกรรมมาจับคู่แล้วแฮชซ้ำทีละชั้น ส่วน Proof-of-Work (บทที่ 2) คือการหาค่าแฮชของ header ที่ต่ำกว่าเป้าหมาย
จุดที่มักสับสน การแฮช (hashing) ไม่ใช่การเข้ารหัส (encryption) การเข้ารหัสต้องใช้กุญแจ และผู้ถือกุญแจถอดกลับเป็นข้อมูลเดิมได้ ส่วนการแฮชไม่ใช้กุญแจเลย และไม่มีวิธีคำนวณย้อนจากค่าแฮชกลับเป็นข้อมูลเดิม ทำได้เพียงเดาข้อมูลแล้วแฮชเทียบ ถ้าข้อมูลต้นทางสั้นหรือเดาง่าย เช่น "hello" ก็เดาเจอได้เร็ว

0.2กุญแจสาธารณะ กุญแจส่วนตัว และลายเซ็นดิจิทัล

ทำไมต้องมีกุญแจและลายเซ็น

เมื่อถอนเงินที่ธนาคาร เราพิสูจน์ตัวตนด้วยบัตรประชาชนหรือรหัสผ่าน และธนาคารเป็นผู้ตรวจ แต่ใน Bitcoin ไม่มีใครคอยตรวจบัตร และไม่มีฐานข้อมูลกลางที่บอกว่าเหรียญไหนเป็นของใคร เจ้าของจึงต้องพิสูจน์ตัวด้วย สิ่งที่เจ้าของเท่านั้นสร้างได้ แต่ทุกคนตรวจสอบได้ สิ่งนั้นคือลายเซ็นดิจิทัล ลายเซ็นนี้สร้างได้ด้วย private key เท่านั้น ใครถือ private key จึงเท่ากับเป็นเจ้าของเหรียญ ถ้า private key หาย เหรียญก็หายไปด้วย เพราะไม่มีธนาคารให้ขอรหัสใหม่

กุญแจคู่ (Key pair)

Bitcoin ใช้ กุญแจคู่ (key pair) จากวิทยาการที่เรียกว่า public-key cryptography ผู้ใช้แต่ละคนมีกุญแจสองดอกที่สัมพันธ์กันทางคณิตศาสตร์ Bitcoin ใช้กุญแจคู่นี้เพื่อลงนามเท่านั้น ไม่ได้ใช้เข้ารหัสข้อมูล

  • Private key (กุญแจส่วนตัว) คือเลขสุ่มขนาด 256 บิต ต้องเก็บเป็นความลับ ผู้ที่ถือ private key คือผู้มีสิทธิ์ใช้เหรียญ ค่านี้ต้องมากกว่า 0 และน้อยกว่า order ของเส้นโค้ง secp256k1 ค่า order นี้ต่ำกว่า 2256 เล็กน้อย เลข 256 บิตเกือบทุกค่าจึงใช้เป็น private key ได้
  • Public key (กุญแจสาธารณะ) คำนวณจาก private key บนเส้นโค้งวงรี (elliptic curve) ชื่อ secp256k1 โดยนำจุดตั้งต้นบนเส้นโค้ง (generator point) มาคูณด้วย private key (scalar multiplication) การคำนวณทางนี้ทำได้เร็ว แต่ยังไม่มีวิธีใดย้อนจาก public key กลับไปหา private key ได้ทันในทางปฏิบัติ Public key จึงเปิดเผยให้ผู้อื่นรู้ได้
  • Address ใช้เหมือนเลขบัญชีสำหรับรับเงิน Address แบบดั้งเดิม (P2PKH ขึ้นต้นด้วย 1…) และแบบ SegWit (P2WPKH ขึ้นต้นด้วย bc1q…) ได้จากการแฮช public key ด้วย SHA-256 แล้วตามด้วย RIPEMD-160 (HASH160) ได้ค่า 20 ไบต์ เหตุผลที่มักยกกันว่าทำไมไม่ใช้ public key เป็นเลขบัญชีตรง ๆ คือ address สั้นกว่า และเจ้าของไม่ต้องเปิดเผย public key จนกว่าจะใช้เหรียญ ส่วน address แบบอื่น เช่น P2SH (3…) และ Taproot (bc1p…) สร้างต่างออกไป บทที่ 4 หัวข้อ 4.6 อธิบายครบทุกแบบ

ลายเซ็นดิจิทัล (Digital signature)

เมื่อต้องการใช้เหรียญ เจ้าของจะสร้างธุรกรรม แล้ว ลงนาม (sign) ด้วย private key ของตน จากนั้นแนบลายเซ็นและ public key มากับธุรกรรม สำหรับ address แบบ P2PKH โหนดจะนำ public key นั้นไปแฮช แล้วเทียบกับ address ที่รับเหรียญนั้นมา ถ้าตรงกัน โหนดจึงใช้ public key ตรวจสอบ (verify) ว่าลายเซ็นถูกต้อง ทุกขั้นนี้ไม่ต้องรู้ private key เลย

ลายเซ็นดิจิทัลให้คุณสมบัติสามประการ

  • Authentication: ยืนยันได้ว่าผู้ลงนามถือ private key ที่คู่กับ public key นั้นจริง
  • Integrity: ถ้ามีใครแก้ข้อความหลังลงนาม การตรวจสอบจะไม่ผ่าน
  • Non-repudiation: ถ้าลายเซ็นตรวจผ่าน ผู้ลงนามจะอ้างภายหลังว่าเป็นฝีมือคนอื่นไม่ได้ เพราะลายเซ็นนี้สร้างได้ด้วย private key ของผู้ลงนามเท่านั้น

Bitcoin ใช้อัลกอริทึมลงนาม ECDSA บนเส้นโค้ง secp256k1 และตั้งแต่อัปเกรด Taproot ในปี 2021 ก็รองรับ Schnorr signature เพิ่มด้วย Ethereum ใช้เส้นโค้ง secp256k1 เช่นเดียวกัน แต่สร้าง address ต่างออกไป คือแฮช public key ด้วย Keccak-256 แล้วใช้ 20 ไบต์สุดท้ายของผลลัพธ์

จุดที่มักสับสน การลงนามไม่ได้ซ่อนเนื้อหาของธุรกรรม ธุรกรรม Bitcoin ทุกรายการเปิดเผยต่อสาธารณะ ลายเซ็นมีไว้พิสูจน์ว่าเจ้าของเหรียญอนุญาตให้โอน ไม่ได้มีไว้ปกปิดข้อมูล

0.3เชื่อมบล็อกเป็นสายโซ่ด้วยค่าแฮช (Hash chain)

ทำไมต้องเชื่อมบล็อก

ทุกเครื่องในเครือข่าย Bitcoin เก็บสำเนาบัญชีแยกประเภท (ledger) ไว้เอง ใครที่ถือสำเนาก็แก้ไฟล์ในเครื่องตัวเองได้ เช่น ลบธุรกรรมที่ตนเคยจ่ายเงินออกไป แล้วส่งสำเนาที่แก้แล้วให้ผู้อื่น ระบบจึงต้องเก็บประวัติในรูปแบบที่ แก้ตรงไหนแล้วผู้อื่นเห็นทันที วิธีที่ Bitcoin ใช้คือผูกบล็อกเข้าด้วยกันด้วยค่าแฮช

โครงสร้างของบล็อก

Blockchain คือรายการบล็อกที่เรียงต่อกัน แต่ละบล็อกประกอบด้วยสองส่วน คือ Block header ขนาด 80 ไบต์ และ รายการธุรกรรม ค่าแฮชของบล็อกคำนวณจาก header เท่านั้น ส่วนธุรกรรมทั้งหมดสรุปรวมอยู่ใน header ในรูปค่า Merkle root

ฟิลด์ใน Block headerขนาดหน้าที่
Version4 ไบต์รุ่นของกติกาที่บล็อกใช้
Previous block hash32 ไบต์ค่าแฮชของบล็อกก่อนหน้า ใช้ผูกบล็อกเข้าเป็นสายโซ่
Merkle root32 ไบต์ค่าแฮชที่สรุปธุรกรรมทุกรายการในบล็อก (บทที่ 3)
Timestamp4 ไบต์เวลาที่สร้างบล็อก
Bits (Target)4 ไบต์ระดับความยากที่ค่าแฮชต้องผ่าน (บทที่ 2)
Nonce4 ไบต์ตัวเลขที่ผู้ขุดปรับไปเรื่อย ๆ เพื่อหาค่าแฮชที่ผ่านเกณฑ์ (บทที่ 2)

ฟิลด์ที่สำคัญที่สุดในหัวข้อนี้คือ Previous block hash ทุกบล็อกเก็บค่าแฮชของบล็อกก่อนหน้าไว้ใน header ของตัวเอง บล็อกจึงผูกต่อกันเป็นสายโซ่ (chain) ย้อนไปจนถึงบล็อกแรก ผลคือค่าแฮชของบล็อกล่าสุดค่าเดียวขึ้นกับข้อมูลทุกบล็อกในประวัติ ถ้าสองเครื่องมีค่าแฮชของบล็อกล่าสุดตรงกัน ประวัติทั้งหมดของทั้งสองเครื่องก็ตรงกัน โดยไม่ต้องส่งข้อมูลทั้งก้อนมาเทียบ

บล็อกแรกของ Bitcoin เรียกว่า Genesis block (บล็อก #0) สร้างเมื่อวันที่ 3 มกราคม 2009 ฟิลด์ Previous block hash ของบล็อกนี้เป็นศูนย์ทั้งหมด เพราะไม่มีบล็อกก่อนหน้า

ถ้ามีคนแก้ข้อมูลในบล็อกเก่า

สมมติว่าผู้โจมตี (attacker) แก้ธุรกรรมหนึ่งรายการในบล็อก #100 ผลจะต่อเนื่องกันไปดังนี้

  1. Merkle root ของบล็อก #100 เปลี่ยน เพราะธุรกรรมเปลี่ยน
  2. Header ของบล็อก #100 เปลี่ยน ค่าแฮชของบล็อก #100 จึงเปลี่ยนตาม
  3. ค่า Prev hash ที่เก็บอยู่ในบล็อก #101 ไม่ตรงกับค่าแฮชใหม่ของบล็อก #100 อีกต่อไป
  4. ถ้าผู้โจมตีแก้ Prev hash ในบล็อก #101 ให้ตรง ค่าแฮชของบล็อก #101 ก็เปลี่ยน และไม่ตรงกับ Prev hash ในบล็อก #102 อีก เป็นแบบนี้ต่อไปจนถึงบล็อกล่าสุด
เชื่อมไปบทถัดไป การผูกบล็อกด้วยค่าแฮชอย่างเดียวช่วยให้ ตรวจพบ การแก้ไขได้ แต่ยังไม่ได้ทำให้ แก้ได้ยาก เพราะคำนวณแฮชใหม่ทุกบล็อกได้ในเวลาไม่นาน ถ้าผู้โจมตีคำนวณแฮชใหม่ครบทุกบล็อก สายโซ่ฉบับแก้จะต่อกันสมบูรณ์ โหนดอื่นรู้เพียงว่ามีสองฉบับที่ค่าแฮชของบล็อกล่าสุดไม่ตรงกัน แต่ยังบอกไม่ได้ว่าฉบับไหนจริง Proof-of-Work ในบทที่ 2 แก้ปัญหานี้ โดยกำหนดให้ผู้สร้างทุกบล็อกต้องใช้พลังประมวลผลจำนวนมาก ผู้ที่จะแก้ประวัติจึงต้องจ่ายต้นทุนนี้ใหม่ทุกบล็อกจนไม่คุ้ม สังเกตว่าค่าแฮชใหม่ 9b2d41c7… ในภาพไม่ได้ขึ้นต้นด้วยศูนย์หลายตัวเหมือนค่าเดิม บทที่ 2 จะอธิบายว่าทำไมแฮชแบบนี้จึงทำให้บล็อกไม่ผ่านเกณฑ์ตั้งแต่ต้น

0.4ปัญหาการใช้จ่ายซ้ำ (Double-spending)

เมื่อจ่ายด้วยธนบัตร เงินจะออกจากมือผู้จ่ายไปอยู่ในมือผู้รับ ผู้จ่ายจึงนำธนบัตรใบเดิมไปจ่ายซ้ำไม่ได้ แต่เงินดิจิทัลเป็นเพียงข้อมูล และข้อมูลคัดลอกได้ไม่จำกัด หากไม่มีกลไกป้องกัน ผู้ถือเหรียญดิจิทัลหนึ่งเหรียญอาจส่งเหรียญเดียวกันให้คนสองคนพร้อมกัน ปัญหานี้เรียกว่า การใช้จ่ายซ้ำ (Double-spending)

ลายเซ็นดิจิทัลในหัวข้อ 0.2 แก้ปัญหานี้ไม่ได้ ลายเซ็นพิสูจน์ได้เพียงว่าเจ้าของเหรียญอนุญาตให้โอน แต่ถ้าเจ้าของลงนามสองธุรกรรมที่ใช้เหรียญเดียวกัน ลายเซ็นในสองธุรกรรมนั้นก็ถูกต้องเหมือนกัน การเชื่อมบล็อกในหัวข้อ 0.3 ก็ยังไม่พอ เพราะสายโซ่ช่วยตรวจการแก้ประวัติที่บันทึกไปแล้ว แต่ไม่ได้ตัดสินว่าเมื่อมีสองธุรกรรมขัดกัน ควรบันทึกรายการไหน

วิธีแก้แบบดั้งเดิม: ตัวกลาง

ระบบการเงินทั่วไปแก้ปัญหานี้ด้วย ตัวกลางที่ทุกคนเชื่อถือ (Trusted third party) เช่น ธนาคาร ธนาคารถือบัญชีแยกประเภทกลาง และตรวจทุกรายการก่อนอนุมัติ วิธีนี้ใช้ได้ผล แต่มีข้อเสีย ได้แก่ ทุกคนต้องเชื่อใจตัวกลาง ต้องเสียค่าธรรมเนียม ตัวกลางยกเลิกหรือย้อนรายการได้ และถ้าตัวกลางล่ม ระบบทั้งหมดก็ใช้งานไม่ได้ (single point of failure) ข้อเสียสามข้อแรกตรงกับที่ Whitepaper ข้อ 1 ยกขึ้นมาเป็นโจทย์ (บทที่ 1) ส่วนข้อสุดท้ายเป็นเหตุผลที่มักยกเพิ่ม แต่ไม่ได้อยู่ใน Whitepaper

วิธีของ Bitcoin: ทุกคนเห็นลำดับธุรกรรมเดียวกัน

Bitcoin ไม่ใช้ตัวกลาง แต่ประกาศ (broadcast) ทุกธุรกรรมให้ทั้งเครือข่ายรู้ แล้วให้เครือข่ายตกลงร่วมกัน (consensus) ว่าธุรกรรมใดเกิดก่อน เมื่อธุรกรรมหนึ่งอยู่ในบล็อกแล้ว เครือข่ายจะปฏิเสธธุรกรรมอื่นที่ใช้เหรียญเดียวกัน

ก่อนธุรกรรมจะอยู่ในบล็อก ผู้จ่ายยังส่งธุรกรรมอีกรายการที่ใช้เหรียญเดียวกันเข้ามาแข่งได้ เช่น จ่ายค่าธรรมเนียมสูงกว่าเพื่อให้ผู้ขุดเลือกรายการใหม่แทน ผู้รับเงินจึงควรรอให้ธุรกรรมอยู่ในบล็อก และรอให้มีบล็อกต่อท้ายอีกหลายบล็อก ก่อนจะถือว่าได้รับเงินแล้ว จำนวนบล็อกนับตั้งแต่บล็อกที่มีธุรกรรมนั้นไปจนถึงบล็อกล่าสุดเรียกว่า จำนวน Confirmation ธุรกรรมที่เพิ่งเข้าบล็อกล่าสุดจึงมี 1 confirmation ยิ่งมีบล็อกต่อท้ายมาก ผู้ที่จะย้อนรายการก็ต้องสร้างบล็อกใหม่แทนมากขึ้น (หัวข้อ 0.3 และบทที่ 2) ธรรมเนียมที่ใช้กันคือถือว่า 6 confirmation (ประมาณ 1 ชั่วโมง) ปลอดภัยพอสำหรับยอดเงินขนาดใหญ่

สรุปท้ายบท

  • ฟังก์ชันแฮชแปลงข้อมูลขนาดใดก็ได้เป็นค่าความยาวคงที่ ไม่มีวิธีคำนวณย้อนกลับเป็นข้อมูลเดิม และถ้าข้อมูลเปลี่ยนเพียงเล็กน้อย ค่าแฮชจะเปลี่ยนไปจนดูไม่ออก (บิตเปลี่ยนราวครึ่งหนึ่ง) Collision มีอยู่จริง แต่ไม่มีใครหาเจอได้ในทางปฏิบัติ
  • Private key ใช้ลงนาม Public key ใช้ตรวจสอบ ส่วน address แบบดั้งเดิม (P2PKH) ได้จากการแฮช public key ทุกขั้นเป็นทางเดียว
  • ลายเซ็นดิจิทัลพิสูจน์ความเป็นเจ้าของ และทำให้ตรวจพบได้เมื่อมีใครแก้ข้อความ แต่ไม่ได้ซ่อนข้อมูล และไม่ได้ป้องกันการใช้จ่ายซ้ำ
  • บล็อกแต่ละบล็อกเก็บค่าแฮชของบล็อกก่อนหน้า ค่าแฮชของบล็อกล่าสุดจึงขึ้นกับประวัติทั้งหมด การแก้บล็อกเก่าทำให้สายโซ่ขาดและตรวจพบได้ แต่ต้องมี Proof-of-Work (บทที่ 2) จึงจะแก้ได้ยาก
  • Double-spending คือการใช้เหรียญดิจิทัลเดียวกันมากกว่าหนึ่งครั้ง Bitcoin แก้โดยให้ทั้งเครือข่ายตกลงลำดับธุรกรรมร่วมกัน (consensus) แทนการพึ่งตัวกลาง ธุรกรรมที่นับคือธุรกรรมที่ได้อยู่ในบล็อกก่อน

แบบฝึกหัด

1. ผลลัพธ์ของ SHA-256 เมื่อเขียนเป็นเลขฐานสิบหกยาวกี่ตัวอักษร

  1. ก. 32
  2. ข. 64
  3. ค. 128
  4. ง. ขึ้นกับความยาวของข้อมูลนำเข้า
ดูเฉลย
ข. 64 ผลลัพธ์ยาว 256 บิตเสมอ และ 1 ตัวอักษรฐานสิบหกแทน 4 บิต จึงได้ 256 ÷ 4 = 64 ตัวอักษร ข้อ ง ผิด เพราะความยาวผลลัพธ์คงที่ไม่ว่าข้อมูลนำเข้าจะยาวเท่าใด

2. คุณสมบัติใดของฟังก์ชันแฮชทำให้ผู้ขุดใน Proof-of-Work ต้องเดาค่า nonce ไปทีละค่า

  1. ก. Deterministic
  2. ข. Collision resistance
  3. ค. Pre-image resistance
  4. ง. คำนวณได้เร็ว
ดูเฉลย
ค. Pre-image resistance เมื่อกำหนดเป้าหมายของค่าแฮชไว้ ไม่มีวิธีคำนวณย้อนกลับว่าข้อมูลต้องเป็นอะไร ผู้ขุดจึงต้องลองค่า nonce ไปเรื่อย ๆ จนกว่าจะพบค่าที่ผ่าน ข้อนี้เป็นการขยายความจากนิยาม เพราะ Pre-image resistance พูดถึงการหาข้อมูลจากค่าแฮชค่าเดียว แต่ Proof-of-Work ต้องการค่าแฮชใดก็ได้ที่ต่ำกว่าเป้าหมาย บางตำราเรียกคุณสมบัติที่ไม่มีทางลัดในการหาข้อมูลแบบนี้ว่า puzzle friendliness ในตัวเลือกที่ให้มา ข้อ ค จึงใกล้ที่สุด

3. ข้อใดกล่าวถึงลายเซ็นดิจิทัลได้ถูกต้อง

  1. ก. ลายเซ็นทำให้คนอื่นอ่านเนื้อหาธุรกรรมไม่ได้
  2. ข. ผู้ตรวจสอบต้องรู้ private key ของผู้ลงนาม
  3. ค. ผู้ตรวจสอบใช้ public key ยืนยันว่าลายเซ็นสร้างจาก private key ที่คู่กัน
  4. ง. ลายเซ็นป้องกันการใช้จ่ายซ้ำได้ด้วยตัวเอง
ดูเฉลย
ค. ข้อ ก ผิด เพราะการลงนามไม่ได้เข้ารหัสข้อมูล ข้อ ข ผิด เพราะการตรวจสอบใช้เพียง public key ข้อ ง ผิด เพราะเจ้าของเหรียญลงนามสองธุรกรรมที่ใช้เหรียญเดียวกันได้ และลายเซ็นทั้งสองก็ถูกต้อง

4. ถ้ามีผู้แก้ไขธุรกรรมในบล็อก #100 จะเกิดอะไรขึ้นกับบล็อก #101

ดูเฉลย
เมื่อธุรกรรมเปลี่ยน Merkle root และค่าแฮชของบล็อก #100 ก็เปลี่ยนตาม ค่า Previous block hash ที่บล็อก #101 เก็บไว้จึงไม่ตรงกับค่าแฮชใหม่ สายโซ่ขาดตั้งแต่จุดนั้น โหนดอื่นจะปฏิเสธข้อมูลชุดนี้ หากผู้แก้ต้องการให้สายโซ่กลับมาต่อกันได้ ต้องสร้างบล็อก #100 ที่แก้แล้ว รวมทั้งบล็อก #101 และทุกบล็อกหลังจากนั้นใหม่ทั้งหมด (บทที่ 2 จะอธิบายว่างานนี้ใช้พลังประมวลผลมากเพียงใด)

5. Double-spending คืออะไร และเหตุใดธนบัตรจึงไม่มีปัญหานี้

ดูเฉลย
Double-spending คือการใช้เงินดิจิทัลหน่วยเดียวกันมากกว่าหนึ่งครั้ง เกิดขึ้นได้เพราะข้อมูลดิจิทัลคัดลอกได้ ธนบัตรไม่มีปัญหานี้เพราะเป็นวัตถุ เมื่อจ่ายแล้วธนบัตรย้ายไปอยู่กับผู้รับ ผู้จ่ายจึงไม่มีธนบัตรใบนั้นเหลือไว้จ่ายซ้ำ
