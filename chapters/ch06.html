Counter Storage: Smart Contract แรก

บทที่ 5 อธิบายว่า Ethereum เก็บสถานะ (state) อย่างไร รันโปรแกรมบน EVM อย่างไร และคิดค่า gas อย่างไร บทนี้ลงมือเขียนตัวนับ (Counter) ซึ่งเป็น contract ที่เล็กที่สุดแต่ยังต้องจำข้อมูลข้ามธุรกรรม (transaction) Counter เก็บตัวเลขไว้เพียงหนึ่งตัว เนื้อหาครอบคลุมโค้ดทีละบรรทัด ที่เก็บข้อมูลหลักสามแบบของ EVM ที่ผู้เขียนต้องเลือกเอง (storage, memory และ calldata) เหตุที่การแก้ค่าต้องเสีย gas แต่การอ่านค่าไม่ต้องเสีย การ deploy และทดสอบบน Remix และการเพิ่ม require, owner และ event ให้ contract ใช้งานได้จริง

เริ่มจากโจทย์: ตัวนับที่ไม่มีใครแอบแก้ได้

สมมุติว่าชมรมหนึ่งต้องการนับจำนวนผู้ลงชื่อเข้าร่วมกิจกรรม แล้วประกาศผลให้สมาชิกทุกคนเห็น วิธีที่ง่ายที่สุดคือเก็บตัวเลขไว้ในฐานข้อมูลบนเซิร์ฟเวอร์ของชมรม แต่วิธีนี้มีจุดอ่อนสามข้อ

  • ผู้ดูแลแก้ตัวเลขได้: ผู้ที่เข้าถึงฐานข้อมูลเปลี่ยนตัวเลขได้ทุกเมื่อ และสมาชิกตรวจย้อนหลังไม่ได้ว่าใครเปลี่ยนไว้เมื่อใด
  • เซิร์ฟเวอร์ล่มได้: ถ้าเซิร์ฟเวอร์ปิด ก็ไม่มีใครเพิ่มหรืออ่านตัวเลขได้
  • สมาชิกต้องเชื่อใจผู้ดูแล: ปัญหานี้คือปัญหาตัวกลาง (trusted third party) แบบเดียวกับที่บทที่ 1 อธิบายไว้สำหรับระบบการเงิน

บทที่ 5 (หัวข้อ 5.1) อธิบายว่า UTXO model ของ Bitcoin ไม่เหมาะกับโจทย์นี้ สถานะที่ต้องแก้ร่วมกันต้องอยู่ใน UTXO ก้อนเดียว ทุกครั้งที่แก้ต้องใช้ก้อนเดิมจนหมดแล้วสร้างก้อนใหม่ และเมื่อผู้ใช้สองคนส่งธุรกรรมพร้อมกัน ธุรกรรมทั้งสองจะชนกันที่ UTXO ก้อนเดียว Ethereum เก็บตัวเลขไว้ใน world state ที่แก้ทับได้ ถ้าเขียนตัวนับเป็น smart contract ตัวเลขจะอยู่ใน world state และทุกโหนดเก็บสำเนาไว้ ทุกครั้งที่ตัวเลขเปลี่ยน ต้องมีธุรกรรมที่ลงลายเซ็น (signature) และทุกโหนดตรวจซ้ำ ไม่มีใครแก้ตัวเลขเงียบ ๆ ได้ และไม่มีเซิร์ฟเวอร์กลางให้ปิด

Counter มีโค้ดเพียงไม่กี่บรรทัด แต่ต้องตอบคำถามเดียวกับแอปขนาดใหญ่ทุกข้อ บทนี้จึงใช้ Counter เป็นตัวอย่างตลอดทั้งบท

6.1เขียน Counter contract ทีละบรรทัด

ทำไมเริ่มจากตัวนับ

โปรแกรมที่เล็กที่สุดซึ่งยังต้องจำข้อมูลข้ามธุรกรรมคือโปรแกรมที่เก็บตัวเลขหนึ่งตัว เพิ่มค่าได้ ลดค่าได้ และอ่านค่าได้ ถ้าเข้าใจว่าตัวเลขตัวเดียวนี้อยู่ที่ใด ใครแก้ได้ และแก้แล้วเสียค่าใช้จ่ายเท่าใด ก็นำหลักเดียวกันไปเข้าใจ contract ที่ซับซ้อนกว่านี้ได้ เช่น ยอดเหรียญของ ERC-20 ในบทที่ 12 ก็คือตัวเลขใน storage จำนวนมากที่เพิ่มลดตามกติกา

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract Counter {
    uint256 public count;

    function increment() public {
        count += 1;
    }

    function decrement() public {
        count -= 1;
    }

    function getCount() public view returns (uint256) {
        return count;
    }
}

บรรทัดความหมายมีไว้เพื่อ

count += 1;อ่าน count จาก storage บวกหนึ่ง แล้วเขียนกลับEVM แปลบรรทัดนี้เป็น opcode SLOAD (อ่าน storage) ADD และ SSTORE (เขียน storage) ค่า gas ส่วนใหญ่ของฟังก์ชันมาจาก SSTORE
count -= 1;ลดค่าลงหนึ่งถ้า count เป็น 0 อยู่แล้ว ผลลบจะติดลบ ซึ่งชนิด uint256 เก็บไม่ได้ Solidity 0.8 ขึ้นไปจึงหยุดการทำงานและย้อนสถานะทั้งหมด (revert) ด้วยรหัส Panic(0x11) ก่อนรุ่น 0.8 ค่าจะวนกลับไปเป็นค่าสูงสุดของ uint256 คือ 2256 − 1

getCount() ซ้ำกับ count() เมื่อประกาศ uint256 public count แล้ว คอมไพเลอร์สร้าง count() ให้อยู่แล้ว ฟังก์ชัน getCount() จึงทำหน้าที่ซ้ำกัน ตัวอย่างในชั้นเรียนมักเขียนไว้เพื่อแสดงรูปแบบของฟังก์ชัน view ถ้าเปลี่ยน count เป็น private จะไม่มี getter อัตโนมัติ และต้องเขียน getCount() เอง แต่ข้อมูลยังเปิดให้ทุกคนอ่านได้จาก storage ตามที่หัวข้อ 5.6 เตือนไว้

contract ไม่มีลูปรอคำสั่ง

โปรแกรมบนเซิร์ฟเวอร์ทั่วไปมีลูปหลักที่ทำงานตลอดเวลาและรอรับคำขอ แต่ Counter ไม่มีฟังก์ชัน main และไม่มีลูปใดทำงานอยู่เบื้องหลัง เหตุผลมาจากหัวข้อ 5.2 คือ contract เริ่มทำงานเองไม่ได้ โค้ดจะรันเมื่อมีธุรกรรมหรือการเรียกเข้ามาเท่านั้น รันจบแล้วก็หยุด สิ่งที่เหลืออยู่ระหว่างการเรียกแต่ละครั้งมีเพียงค่าใน storage ถ้าต้องการให้ตัวนับเพิ่มเองทุกชั่วโมง ต้องมีผู้ส่งธุรกรรมมาเรียกทุกชั่วโมง ไม่มีวิธีตั้งเวลาไว้ใน contract

ประเด็นที่มักออกสอบ state variable ที่ไม่ได้กำหนดค่าเริ่มต้นจะมีค่าเริ่มต้นตามชนิด เช่น uint256 เป็น 0 และ address เป็น 0x000…0 ส่วน state variable ที่ประกาศเป็น public จะได้ getter ชื่อเดียวกับตัวแปรโดยอัตโนมัติ และ getter นั้นเป็นฟังก์ชัน view

6.2ความแตกต่างของ storage, memory และ calldata

ทำไม EVM ต้องมีที่เก็บข้อมูลหลายแบบ

ข้อมูลในโปรแกรมมีอายุต่างกัน ตัวเลขของ Counter ต้องอยู่ต่อไปหลังธุรกรรมจบ เพื่อให้ธุรกรรมถัดไปบวกต่อได้ ส่วนค่าระหว่างคำนวณ เช่น ข้อความที่ต่อกันเพื่อส่งคืน ใช้เสร็จแล้วก็ทิ้งได้ ต้นทุนของสองกรณีนี้ต่างกันมาก ข้อมูลที่อยู่ถาวรต้องเก็บไว้ในเครื่องของทุก full node ทั่วโลกไปตลอด ส่วนข้อมูลชั่วคราวใช้ RAM ของโหนดเพียงไม่กี่มิลลิวินาที

ถ้า EVM มีที่เก็บแบบเดียว จะเกิดปัญหาไม่ทางใดก็ทางหนึ่ง ถ้าทุกอย่างอยู่ถาวร ค่าระหว่างคำนวณทุกค่าต้องจ่ายราคาของข้อมูลถาวร และ world state จะโตเร็วจนโหนดทั่วไปเก็บไม่ไหว ถ้าทุกอย่างหายเมื่อจบการเรียก Counter ก็จำตัวเลขไม่ได้ EVM จึงแยกที่เก็บตามอายุของข้อมูล และตั้งราคาแต่ละแบบตามภาระที่โหนดต้องแบก

storage แบ่งเป็น slot

storage ของแต่ละ contract แบ่งเป็นช่อง (slot) ช่องละ 32 ไบต์ คอมไพเลอร์วาง state variable ลงช่องตามลำดับที่ประกาศ count ของ Counter จึงอยู่ที่ slot 0 ช่องที่ไม่เคยเขียนจะอ่านได้ค่า 0 ทุกช่อง ค่าเริ่มต้นของ state variable จึงเป็น 0 โดยไม่ต้องเขียนอะไรลง storage ตอน deploy

ตัวเลข gas บน Sepolia ต่างจากบทนี้ ตัวเลข gas ในบทนี้ใช้กติกาบน mainnet และ Remix VM รุ่นก่อนการอัปเกรด Glamsterdam เช่นเดียวกับหัวข้อ 5.5 Sepolia เปิดใช้ Glamsterdam แล้วตั้งแต่ 6 ตุลาคม 2026 การอัปเกรดนี้ปรับราคา gas ของงานบางประเภท เช่น การเขียน state ใหม่ ค่า gas ที่เห็นบน Sepolia และ Etherscan จึงต่างจากตัวเลขในบทนี้ บทนี้ไม่ใส่ตัวเลขใหม่ไว้ เพราะราคาเหล่านี้อาจยังปรับอีกก่อนขึ้น mainnet

data location คือคำว่า storage, memory หรือ calldata ที่เขียนกำกับตัวแปรเพื่อบอกว่าข้อมูลอยู่ที่ใด ชนิดข้อมูลแบบ value (value type) เช่น uint256, bool และ address มีขนาดไม่เกิน 32 ไบต์ คัดลอกได้ถูก คอมไพเลอร์จึงจัดที่เก็บให้เอง ส่วนชนิดแบบ reference (reference type) ได้แก่ string, bytes, array, struct และ mapping (mapping อยู่ได้เฉพาะใน storage) ข้อมูลชนิดนี้อาจยาวมาก การคัดลอกจากที่หนึ่งไปอีกที่หนึ่งจึงเสีย gas ตามขนาด

ตั้งแต่ Solidity 0.5 ตัวแปรชนิด reference ต้องระบุ data location ทุกครั้งในสามกรณี คือเมื่อเป็น parameter, ค่าที่คืน (return value) หรือตัวแปรภายในฟังก์ชัน คอมไพเลอร์ไม่เดาให้ เพราะถ้าเลือกผิด โปรแกรมจะเสีย gas มากขึ้นหรือทำงานผิด

contract NameBoard {
    string[] public names;                         // state variable อยู่ใน storage เสมอ

    // รับข้อความเป็น calldata: อ่านจากข้อมูลที่ส่งมาได้เลย ไม่ต้องคัดลอกลง memory
    function addName(string calldata name) external {
        names.push(name);                          // คัดลอกจาก calldata ลง storage
    }

    // ต้องสร้างข้อความใหม่ จึงคืนค่าเป็น memory
    function greet(string calldata name) external pure returns (string memory) {
        return string.concat("Hello, ", name);
    }
}

ตัวแปร storage กับตัวแปร memory ให้ผลต่างกัน

ถ้าตัวแปรภายในฟังก์ชันรับค่ามาจากข้อมูลใน storage คำว่า storage หรือ memory จะกำหนดว่าตัวแปรนั้นเป็น ตัวอ้างอิง (reference) ไปยังข้อมูลจริง หรือเป็น สำเนา (copy) ผลของสองแบบต่างกันมาก

struct Player { string name; uint256 score; }
Player[] public players;

function addScore(uint256 i) external {
    Player storage p = players[i];   // p อ้างอิงข้อมูลจริงใน storage
    p.score += 10;                   // แก้ค่าใน storage ทันที
}

function addScoreWrong(uint256 i) external {
    Player memory p = players[i];    // คัดลอกข้อมูลมาไว้ใน memory
    p.score += 10;                   // แก้เฉพาะสำเนา จบการเรียกแล้วสำเนาหายไป
}
ฟังก์ชันที่ดูเหมือนทำงาน แต่ไม่ได้บันทึกอะไร addScoreWrong คอมไพล์ผ่าน รันได้ และเสีย gas แต่คะแนนใน storage ไม่เปลี่ยนเลย คอมไพเลอร์ให้คำใบ้ไว้แล้ว คือเตือนว่าฟังก์ชันนี้ควรเป็น view เพราะไม่ได้เขียน storage ถ้าเห็นคำเตือนนี้กับฟังก์ชันที่ตั้งใจให้แก้ข้อมูล ให้ตรวจ data location ก่อน
ประเด็นที่มักออกสอบ parameter ของฟังก์ชัน external ที่ไม่ต้องแก้ค่า ควรประกาศเป็น calldata เพราะอ่านจากข้อมูลที่ส่งมาได้โดยตรง ถ้าประกาศเป็น memory EVM ต้องคัดลอกข้อมูลทั้งก้อนลง memory ก่อน และเสีย gas เพิ่มตามขนาดข้อมูล ข้อแลกเปลี่ยน (trade-off) คือแก้ค่าตัวแปร calldata ไม่ได้ ส่วน state variable ระบุ data location ไม่ได้ เพราะอยู่ใน storage เสมอ

6.3ธุรกรรมที่เปลี่ยนสถานะ (เสีย gas) กับการเรียกอ่านด้วย view / pure (ไม่เสีย gas)

ทำไมการแก้ค่ากับการอ่านค่าจึงต่างกัน

เมื่อมีคนกด increment() ตัวเลขใน world state ต้องเปลี่ยนพร้อมกันในทุกโหนด ถ้าโหนดหนึ่งเห็น count เป็น 5 แต่อีกโหนดเห็นเป็น 6 เครือข่ายก็ตกลงเรื่อง state root ไม่ได้ (หัวข้อ 5.4) การแก้ค่าจึงต้องผ่านขั้นตอนเดียวกับการโอนเงิน คือผู้เรียกลงลายเซ็นเพื่อยืนยันว่าเป็นผู้สั่ง ธุรกรรมต้องเข้าบล็อก และทุกโหนดต้องรันซ้ำ ผู้เรียกจ่ายค่า gas เพื่อชดเชยงานที่ทุกโหนดทำ และเพื่อให้ผู้ที่ส่งธุรกรรมขยะ (spam) ต้องเสียเงิน

การอ่านค่าไม่ได้เปลี่ยนอะไร เครือข่ายจึงไม่ต้องตกลงร่วมกัน full node ทุกตัวมี world state ครบอยู่ในเครื่องแล้ว โหนดที่เราเชื่อมต่ออยู่จึงรันฟังก์ชัน view บนสำเนาของตัวเองแล้วตอบกลับได้ทันที ไม่ต้องลงลายเซ็น ไม่ต้องรอบล็อก และไม่ต้องจ่าย gas ให้ใคร

view กับ pure ต่างกันอย่างไร

เครื่องมือฝั่งผู้ใช้ เช่น Remix หรือ MetaMask ต้องรู้ว่าฟังก์ชันใดเรียกด้วย eth_call ได้ และฟังก์ชันใดต้องส่งเป็นธุรกรรม ข้อมูลนี้มาจาก state mutability (หัวข้อ 5.6) ที่ผู้เขียนประกาศไว้ คอมไพเลอร์บันทึกค่านี้ลงใน ABI และ Remix ใช้ค่านี้เลือกสีปุ่ม ตอนคอมไพล์ คอมไพเลอร์ยังตรวจด้วยว่าคำประกาศตรงกับสิ่งที่โค้ดทำจริง ถ้าฟังก์ชัน view พยายามเขียน storage คอมไพเลอร์จะแจ้ง error ถ้าฟังก์ชันที่ไม่ได้ระบุ state mutability อ่านข้อมูลอย่างเดียว คอมไพเลอร์จะเตือนว่าควรระบุเป็น view หรือ pure

function getCount() public view returns (uint256) {
    return count;                    // อ่าน storage จึงเป็น view
}

function double(uint256 x) public pure returns (uint256) {
    return x * 2;                    // ใช้เฉพาะ parameter จึงเป็น pure
}

pure สัญญาว่าผลลัพธ์ขึ้นกับ parameter เท่านั้น เรียกด้วยค่าเดิมกี่ครั้งก็ได้ผลเดิม ส่วน msg.sender และข้อมูลของบล็อกมาจากบริบทของการเรียก (execution context) และเปลี่ยนไปตามผู้เรียกหรือบล็อก ค่าเหล่านี้จึงนับเป็นการอ่านสถานะ ฟังก์ชันที่ใช้ค่าเหล่านี้จึงเป็น pure ไม่ได้ และต้องประกาศอย่างน้อยเป็น view

"view ไม่เสีย gas" มีเงื่อนไข ฟังก์ชัน view และ pure ไม่เสีย gas เฉพาะเมื่อเรียกจากภายนอกด้วย eth_call เท่านั้น ถ้าฟังก์ชันที่แก้สถานะเรียก getCount() ภายในธุรกรรม หรือ contract อื่นเรียก getCount() ระหว่างธุรกรรม คำสั่งของ getCount() ก็รันอยู่ในธุรกรรมนั้น และ gas ที่ใช้นับรวมกับค่าธรรมเนียมของธุรกรรม

ทำไมฟังก์ชันที่แก้สถานะจึงคืนค่าให้ผู้เรียกไม่ได้

ถ้าเขียน function increment() public returns (uint256) แล้วเรียกผ่าน MetaMask แอปจะไม่ได้ตัวเลขใหม่กลับมา เพราะตอนที่ wallet ส่งธุรกรรม ฟังก์ชันยังไม่ได้รัน ฟังก์ชันจะรันจริงเมื่อธุรกรรมเข้าบล็อก ซึ่งอาจเป็นอีกหลายวินาทีต่อมา นอกจากนี้ receipt ของธุรกรรมก็ไม่ได้เก็บค่าที่ฟังก์ชันคืนไว้ แอปจึงมีสองทางเลือก คือรอให้ธุรกรรมเข้าบล็อกแล้วเรียก count() อีกครั้ง หรืออ่าน event ที่ contract บันทึกไว้ใน receipt (หัวข้อ 6.5) ค่าที่คืนจากฟังก์ชันแบบนี้ยังมีประโยชน์เมื่อ contract อื่นเรียกใช้ภายในธุรกรรมเดียวกัน

อ่านฟรี แต่ต้องเชื่อโหนดที่ถาม ผลของ eth_call มาจากโหนดเดียว ถ้าโหนดนั้นเป็นของผู้ให้บริการ RPC ภายนอก (RPC provider) เช่น Infura หรือ Alchemy และตอบค่าผิด แอปก็ได้ค่าผิด ปัญหานี้คล้ายข้อจำกัดของ SPV ในหัวข้อ 3.5 ผู้ที่ต้องการความมั่นใจสูงจึงรัน full node ของตัวเอง หรือขอ Merkle proof ที่ผูกกับ stateRoot ใน header ของบล็อกมาตรวจเอง (หัวข้อ 5.4)

6.4Deploy และทดสอบบน Remix

deploy คือธุรกรรมที่สร้างบัญชีใหม่

โค้ด Solidity ที่เขียนเสร็จยังอยู่ในเครื่องของเรา โหนดอื่นไม่รู้จักโค้ดนี้ และ EVM ก็รันภาษา Solidity โดยตรงไม่ได้ ขั้นแรกจึงต้องคอมไพล์โค้ดให้เป็น bytecode ถ้าจะให้ทุกโหนดรัน Counter ได้ bytecode ของ Counter ต้องเข้าไปอยู่ใน world state และวิธีเดียวที่จะเปลี่ยน world state ได้คือส่งธุรกรรม ธุรกรรม deploy จึงเป็นธุรกรรมธรรมดาที่มีลักษณะพิเศษสองข้อ คือฟิลด์ to ว่าง และฟิลด์ data บรรจุ creation bytecode (หัวข้อ 5.4)

creation bytecode มีสองส่วน ส่วนแรกคือ init code ที่รัน constructor ครั้งเดียว ส่วนที่สองคือ runtime bytecode เมื่อ init code รันเสร็จ จะคืน runtime bytecode ออกมา แล้วเครือข่ายเก็บไว้เป็น code ของบัญชีใหม่ คอมไพเลอร์แยกสองส่วนนี้เพราะโค้ดตั้งค่าเริ่มต้นใช้เพียงครั้งเดียว ถ้าเก็บไว้ใน code ของ contract ทุกโหนดต้องเก็บโค้ดที่ไม่มีวันใช้อีก และอาจมีคนเรียก constructor ซ้ำเพื่อตั้งค่าใหม่ได้

หัวข้อ 5.7 แนะนำให้เริ่มจาก Remix VM ซึ่งเป็น blockchain จำลองในเบราว์เซอร์ เหตุผลเดียวกับ Regtest ในบทที่ 4 คือธุรกรรมยืนยันทันที ไม่เสียเงินจริง และลองผิดได้ไม่จำกัด

  1. เปิด remix.ethereum.org ในแท็บ File Explorer สร้างไฟล์ Counter.sol แล้ววางโค้ดจากหัวข้อ 6.1
  2. ในแท็บ Solidity Compiler เลือกรุ่นคอมไพเลอร์ที่ตรงกับ pragma คือ 0.8.20 ขึ้นไปแต่ต่ำกว่า 0.9 แล้วกด Compile Counter.sol เมื่อคอมไพล์ผ่าน ด้านล่างของแท็บจะมีปุ่มคัดลอก ABI และ Bytecode
  3. ในแท็บ Deploy & Run Transactions ตั้ง Environment เป็น Remix VM (Remix อาจแสดงชื่อรุ่นอัปเกรดของ Ethereum ต่อท้าย เช่น Remix VM (Cancun)) ช่อง Account มีบัญชีทดสอบหลายบัญชีพร้อม ETH ปลอม เลือก Contract เป็น Counter แล้วกด Deploy
  4. ใต้หัวข้อ Deployed Contracts จะมี Counter พร้อม address ใหม่ กดขยายเพื่อดูปุ่มของแต่ละฟังก์ชัน ปุ่มสีฟ้าคือ count และ getCount ปุ่มสีส้มคือ increment และ decrement
  5. ทดลองตามตารางด้านล่าง แล้วสังเกตผลใน Console ใต้หน้าต่างแก้โค้ด

เปลี่ยน Account เป็นบัญชีอื่น แล้วกด incrementสำเร็จ และ count เพิ่มขึ้นฟังก์ชันเป็น public และไม่ได้ตรวจสิทธิ์ผู้เรียก ใครก็เรียกได้ ตัวนับผู้ลงชื่อต้องเปิดให้ทุกคนเพิ่มค่าได้อยู่แล้ว แต่ฟังก์ชันที่อันตรายกว่า เช่น การล้างค่า ต้องจำกัดสิทธิ์ (หัวข้อ 6.5 ใช้ onlyOwner กับ reset())
กด decrement จนเหลือ 0 แล้วกดอีกครั้งธุรกรรม revert และ count ยังเป็น 0Solidity 0.8 ตรวจการลบจนติดลบให้อัตโนมัติ (หัวข้อ 6.1)
ดูยอด ETH ของบัญชีในช่อง Accountลดลงเล็กน้อยหลังทุกธุรกรรม แต่ไม่ลดเมื่อกดปุ่มสีฟ้าธุรกรรมต้องจ่ายค่า gas แม้แต่ธุรกรรมที่ revert ก็ยังจ่ายส่วนที่ใช้ไปแล้ว ส่วน call ไม่เสีย gas

ตัวเลข gas ในตารางเป็นค่าประมาณ ค่าจริงขึ้นกับรุ่นคอมไพเลอร์ การตั้งค่า optimizer และรุ่นของ EVM ที่ Remix VM จำลอง สิ่งที่ควรสังเกตคือครั้งแรกแพงกว่าครั้งต่อไปชัดเจน

อ่านผลใน Console

เมื่อกดขยายรายการธุรกรรมใน Console จะเห็นฟิลด์เดียวกับที่หัวข้อ 5.4 อธิบายไว้ ฟิลด์ที่ควรรู้จักมีดังนี้

  • status: ธุรกรรมสำเร็จหรือ revert
  • from / to: บัญชีที่เรียก และ contract กับฟังก์ชันที่เรียก ถ้าเป็นธุรกรรม deploy ช่อง to จะแสดงว่าเป็นการสร้าง contract
  • transaction cost / execution cost: transaction cost คือ gas ทั้งหมดที่ธุรกรรมใช้ ส่วน execution cost คือ gas ของการรันโค้ดบน EVM ไม่รวมค่าพื้นฐาน 21,000 และค่าของ data ที่ส่งมา
  • input / decoded input: data ที่ส่งไปจริง เช่น 0xd09de08a สำหรับ increment() และค่าที่ Remix แปลกลับให้อ่านง่าย
  • decoded output: ค่าที่ฟังก์ชันคืน เห็นได้ใน Remix VM เพราะ Remix รันธุรกรรมเองในเบราว์เซอร์ แต่แอปจริงที่ส่งธุรกรรมผ่านโหนดไม่ได้รับค่านี้ (หัวข้อ 6.3)
  • logs: event ที่ธุรกรรมบันทึกไว้ Counter รุ่นแรกยังไม่มี event ช่องนี้จึงว่าง

ย้ายไป Sepolia และเผยแพร่ซอร์สโค้ด

เมื่อทดสอบบน Remix VM ผ่านแล้ว ขั้นต่อไปคือ testnet สาธารณะ เพื่อดูพฤติกรรมบนเครือข่ายจริงที่มีหลายโหนด มีค่า gas และต้องรอบล็อก ค่า gas ที่เห็นบน Sepolia จะไม่ตรงกับตารางข้างบน เพราะ Sepolia เปิดใช้ Glamsterdam แล้ว (หัวข้อ 6.2)

  1. เปิด MetaMask ด้วยบัญชีสำหรับทดสอบ เลือกเครือข่าย Sepolia และขอ SepoliaETH จาก faucet (หัวข้อ 5.7)
  2. ใน Remix เปลี่ยน Environment เป็น Injected Provider - MetaMask แล้วกด Deploy MetaMask จะแสดงค่าธรรมเนียมโดยประมาณและขอให้ยืนยัน
  3. รอให้ธุรกรรมเข้าบล็อก แล้วนำ address ของ contract ไปค้นใน sepolia.etherscan.io
  4. ลองกด increment MetaMask จะขึ้นหน้าต่างทุกครั้ง แต่เมื่อกด count จะไม่มีหน้าต่างขึ้น เพราะเป็น call
  5. ลองกด decrement ตอนที่ count เป็น 0 ก่อนส่ง Remix จะเรียก eth_estimateGas ให้โหนดจำลองธุรกรรมล่วงหน้า เมื่อพบว่าธุรกรรมจะ revert Remix จะเปิดหน้าต่าง Gas estimation ถามว่าจะบังคับส่ง (force send) หรือไม่ MetaMask บางรุ่นก็เตือนซ้ำในหน้ายืนยัน ผู้ใช้ยังกดยืนยันส่งได้ แต่ธุรกรรมจะเข้าบล็อกในสถานะล้มเหลว และยังเสียค่า gas ส่วนที่ใช้ไป

หน้า contract บน Etherscan แสดงเพียง bytecode เพราะ chain เก็บไว้แค่ bytecode ผู้ใช้ทั่วไปอ่าน bytecode ไม่ออก จึงตรวจไม่ได้ว่า contract ทำอะไรจริง ผู้ deploy ที่ต้องการให้ผู้อื่นเชื่อใจ contract จึงควร verify ซอร์สโค้ด คือส่งโค้ด รุ่นคอมไพเลอร์ และการตั้งค่าที่ใช้ให้ Etherscan คอมไพล์ซ้ำ ถ้าได้ bytecode ตรงกับที่อยู่บน chain Etherscan จะแสดงซอร์สโค้ด และเปิดแท็บ Read Contract กับ Write Contract ให้เรียกฟังก์ชันจากหน้าเว็บได้ Remix ก็มี plugin สำหรับ verify ให้ใช้เช่นกัน

Counter เป็นโค้ดตัวอย่างที่มีคน deploy และ verify ไว้มาก ถ้า bytecode ตรงกับ contract อื่นที่ verify ไว้แล้ว Etherscan อาจแสดงซอร์สโค้ดแบบ Similar Match ให้ตั้งแต่ก่อน verify การแสดงผลนี้มาจากการจับคู่โดยอัตโนมัติ ไม่ใช่การยืนยันจากผู้ deploy

ประเด็นที่มักออกสอบ ธุรกรรม deploy มีฟิลด์ to ว่าง และ data คือ creation bytecode constructor รันครั้งเดียวตอน deploy และไม่อยู่ใน runtime bytecode address ของ contract ที่สร้างด้วย CREATE คำนวณจาก address ของผู้ deploy กับ nonce ของผู้ deploy ไม่ได้ขึ้นกับเนื้อหาของโค้ด
deploy ใหม่ไม่ได้แก้ contract เดิม ถ้าแก้โค้ดใน Remix แล้วกด Deploy อีกครั้ง จะได้ contract ตัวใหม่ที่ address ใหม่และ count เริ่มจาก 0 contract ตัวเดิมยังอยู่ที่ address เดิมพร้อมค่าเดิม เพราะ code ของ contract ที่ deploy แล้วแก้ไม่ได้ (หัวข้อ 5.3) แอปที่ใช้งานอยู่ต้องเปลี่ยนไปเรียก address ใหม่เอง

6.5ต่อยอดด้วย require, owner และ event

Counter รุ่นแรกยังมีปัญหาอะไร

การทดลองในหัวข้อ 6.4 แสดงปัญหาของ Counter รุ่นแรกสามข้อ ถ้าจะนำตัวนับไปใช้นับผู้ลงชื่อของชมรมจริง ต้องแก้ทั้งสามข้อ

  • error ไม่บอกสาเหตุ: เมื่อลดค่าต่ำกว่า 0 ผู้ใช้เห็นเพียง Panic code ไม่รู้ว่าทำผิดตรงไหน
  • ไม่ได้แบ่งสิทธิ์: ถ้าเพิ่มฟังก์ชัน reset() ให้ตั้งค่ากลับเป็น 0 ใครก็เรียกได้ ผู้ไม่หวังดีจะล้างตัวเลขทิ้งเมื่อใดก็ได้
  • แอปไม่รู้ว่าตัวเลขเปลี่ยน: หน้าเว็บของชมรมต้องการแสดงว่าใครลงชื่อเมื่อใด แต่ฟังก์ชันที่แก้สถานะคืนค่าให้แอปไม่ได้ (หัวข้อ 6.3) และถ้าเก็บประวัติทุกครั้งไว้ใน storage ค่า gas จะสูงมาก
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract OwnedCounter {
    uint256 public count;                        // slot 0
    address public owner;                        // slot 1

    event CountChanged(address indexed by, uint256 newCount);

    modifier onlyOwner() {
        require(msg.sender == owner, "not owner");
        _;
    }

    constructor() {
        owner = msg.sender;                      // ผู้ deploy เป็น owner
    }

    function increment() external {
        count += 1;
        emit CountChanged(msg.sender, count);
    }

    function decrement() external {
        require(count > 0, "count is already zero");
        count -= 1;
        emit CountChanged(msg.sender, count);
    }

    function reset() external onlyOwner {
        count = 0;
        emit CountChanged(msg.sender, 0);
    }
}

require: ตรวจเงื่อนไขก่อนแก้สถานะ

require(เงื่อนไข, "ข้อความ") ตรวจเงื่อนไขที่ต้องเป็นจริงก่อนทำงานต่อ ถ้าเงื่อนไขเป็นเท็จ EVM จะ revert ทันที ผลมีสี่ข้อ

  1. ทุกค่าที่ธุรกรรมนี้แก้ไว้กลับเป็นค่าเดิม
  2. event ที่ emit ไปแล้วในธุรกรรมนี้หายไปด้วย
  3. ผู้เรียกได้รับข้อความ error เช่น "count is already zero" ซึ่งอ่านเข้าใจได้กว่า Panic(0x11)
  4. ผู้เรียกจ่าย gas เฉพาะส่วนที่ใช้ไปจนถึงจุด revert ส่วนที่เหลือของ gas limit ได้คืน

EVM ย้อนทุกอย่างกลับแทนที่จะหยุดค้างไว้กลางทาง เพราะสถานะที่ทำไปครึ่งเดียวอันตรายกว่าการไม่ทำเลย ตัวอย่างเช่น ฟังก์ชันโอนเงินที่หักยอดผู้ส่งแล้วแต่ยังไม่ได้เพิ่มยอดผู้รับ ถ้าหยุดตรงนั้น เงินจะหายไปจากระบบ ธุรกรรมจึงสำเร็จทั้งหมดหรือไม่เกิดผลเลย (atomic) ควรวาง require ไว้ต้นฟังก์ชัน เพื่อให้ธุรกรรมที่จะล้มเหลวหยุดก่อนใช้ gas กับคำสั่งที่แพง

Solidity ตั้งแต่ 0.8.4 มี custom error ให้ใช้แทนข้อความ เช่น error NotOwner(); คู่กับ if (msg.sender != owner) revert NotOwner(); วิธีนี้ประหยัด gas กว่าเพราะไม่ต้องเก็บข้อความยาวไว้ใน bytecode และไม่ต้องส่งข้อความกลับ

owner: บันทึกผู้ deploy ไว้ตั้งแต่ constructor

contract ต้องรู้ว่าใครมีสิทธิ์ใช้ reset() แต่ blockchain ไม่มีระบบบัญชีผู้ใช้และรหัสผ่านแบบเว็บทั่วไป สิ่งที่ contract รู้แน่นอนคือ msg.sender ซึ่งเครือข่ายยืนยันให้แล้วจากลายเซ็นของธุรกรรม (หัวข้อ 5.6) constructor จึงบันทึก msg.sender ตอน deploy ไว้เป็น owner ใน storage จากนั้น modifier onlyOwner จะเทียบผู้เรียกกับค่านี้ทุกครั้ง

constructor รันได้ครั้งเดียว และ contract ไม่มีฟังก์ชันอื่นที่แก้ owner จึงไม่มีใครแย่งสิทธิ์ไปได้ภายหลัง ข้อเสียที่ตามมาคือถ้า owner ทำ private key หาย ก็ไม่มีใครเรียก reset() ได้อีก contract จริงจึงมักเพิ่มฟังก์ชันโอนสิทธิ์ (transfer ownership) ไว้ด้วย

owner ในที่นี้ต่างจากผู้ดูแลฐานข้อมูลในโจทย์ตอนต้นบท owner ทำได้เฉพาะสิ่งที่โค้ดอนุญาต คือตั้ง count กลับเป็น 0 แต่ตั้งเป็นตัวเลขอื่นตามใจไม่ได้ ทุกครั้งที่เรียก reset() ยังมี event บันทึกไว้ให้สมาชิกทุกคนตรวจย้อนหลังได้ ส่วน increment() และ decrement() ยังเปิดให้ทุกบัญชีเรียกได้เหมือนเดิม เพราะตัวนับผู้ลงชื่อต้องให้ทุกคนลงชื่อได้

ห้ามใช้ tx.origin ตรวจสิทธิ์ tx.origin คือ EOA ที่เริ่มธุรกรรม ส่วน msg.sender คือผู้เรียกโดยตรง ถ้าตรวจสิทธิ์ด้วย tx.origin == owner ผู้โจมตีจะสร้าง contract ขึ้นมาหนึ่งตัว แล้วล่อให้ owner ส่งธุรกรรมมาเรียก contract นั้น เมื่อ contract ของผู้โจมตีเรียก reset() ต่อ ค่า tx.origin ยังเป็น owner การตรวจสิทธิ์จึงผ่าน แม้ผู้เรียกโดยตรงจะเป็น contract ของผู้โจมตี การตรวจด้วย msg.sender ไม่มีช่องโหว่นี้ เพราะ msg.sender จะเป็น address ของ contract หลอก

event: แจ้งแอปว่าตัวเลขเปลี่ยน

emit CountChanged(msg.sender, count) บันทึกข้อมูลลงใน log ของ receipt (หัวข้อ 5.6) แอปของชมรมติดตาม event นี้แล้วแสดงรายชื่อผู้ลงชื่อได้ ส่วนเวลาได้จาก timestamp ของบล็อกที่มี log นั้นอยู่ event ถูกกว่า storage เพราะ log ไม่ได้อยู่ใน world state โหนดจึงไม่ต้องเก็บไว้ให้ธุรกรรมถัดไปอ่าน ข้อแลกเปลี่ยน (trade-off) คือ contract อ่าน event ย้อนหลังไม่ได้ ข้อมูลที่ contract ต้องใช้ตัดสินใจจึงยังต้องอยู่ใน storage

คำว่า indexed หน้า by ทำให้แอปกรองเฉพาะ event ของ address หนึ่งได้ เช่น ดูว่าสมาชิกคนหนึ่งกดเพิ่มไปกี่ครั้ง event ยังแก้ปัญหาในหัวข้อ 6.3 ที่ธุรกรรมคืนค่าให้แอปไม่ได้ เพราะ newCount อยู่ใน receipt ที่แอปอ่านได้หลังธุรกรรมเข้าบล็อก

กลไกปัญหาที่แก้ถ้าไม่มี
requireหยุดก่อนแก้สถานะเมื่อข้อมูลไม่ถูกต้อง และบอกเหตุผลผู้ใช้เห็น error ที่ไม่บอกสาเหตุ หรือ contract เก็บค่าที่ผิดเงื่อนไขไว้
owner + onlyOwnerจำกัดฟังก์ชันอันตรายให้ผู้มีสิทธิ์เท่านั้นใครก็เรียก reset() และล้างข้อมูลได้
eventแจ้งแอปนอก chain ว่าเกิดอะไรขึ้น ในราคาถูกกว่า storageแอปต้องเรียก count() ซ้ำเรื่อย ๆ เพื่อดูว่าค่าเปลี่ยนหรือไม่ และไม่รู้ว่าใครเป็นผู้เปลี่ยน

ทดลอง: จำลอง OwnedCounter

ตัวจำลองนี้ทำงานตามกติกาของ OwnedCounter ข้างบน บัญชี A เป็นผู้ deploy จึงเป็น owner ลองเรียกแต่ละฟังก์ชันจากทั้งสองบัญชี แล้วสังเกตว่าธุรกรรม revert เมื่อใด event เกิดขึ้นเมื่อใด และการเขียน count ครั้งแรกแพงกว่าครั้งต่อไปเท่าใด ค่า gas ในตัวจำลองคำนวณจากราคาของ opcode หลักเท่านั้น ค่าใน Remix จะสูงกว่าเล็กน้อย

สรุปท้ายบท

  • โจทย์: ตัวนับบนเซิร์ฟเวอร์กลางต้องเชื่อใจผู้ดูแล Counter บน Ethereum เก็บตัวเลขไว้ใน world state ทุกการแก้ค่าต้องเป็นธุรกรรมที่ลงลายเซ็นและทุกโหนดตรวจซ้ำ
  • 6.1: uint256 public count เป็น state variable ใน storage ค่าเริ่มต้น 0 และได้ getter count() อัตโนมัติ Solidity 0.8 revert เมื่อลบจนติดลบ contract ไม่มีลูปรอคำสั่ง รันเมื่อมีผู้เรียกเท่านั้น
  • 6.2: storage อยู่ถาวรและแพงที่สุด memory ใช้ชั่วคราวระหว่างการเรียก calldata เป็นข้อมูลที่ส่งมาและอ่านได้อย่างเดียว ตัวแปรชนิด reference ต้องระบุ data location และตัวแปร storage เป็นตัวอ้างอิง ส่วนตัวแปร memory เป็นสำเนา
  • 6.3: การแก้สถานะต้องให้ทุกโหนดตกลงร่วมกัน จึงต้องส่งธุรกรรม เข้าบล็อก และเสีย gas การเรียก view/pure จากภายนอกใช้ eth_call โหนดเดียวตอบได้และไม่เสีย gas แต่ถ้าเรียกภายในธุรกรรมก็เสีย gas
  • 6.4: deploy คือธุรกรรมที่ to ว่างและ data เป็น creation bytecode constructor รันครั้งเดียว address ของ contract คำนวณจากผู้ deploy กับ nonce ทดสอบใน Remix VM ก่อน แล้วจึงขึ้น Sepolia และ verify ซอร์สโค้ด
  • 6.5: require revert ทั้งธุรกรรมเมื่อเงื่อนไขไม่ผ่าน owner บันทึกจาก msg.sender ใน constructor และตรวจด้วย modifier ส่วน event แจ้งแอปว่าใครเปลี่ยนค่าเป็นเท่าใดในราคาถูกกว่า storage แต่ contract อ่าน event ย้อนหลังไม่ได้

4. ทำไมกดปุ่ม count ใน Remix ที่เชื่อม MetaMask แล้ว MetaMask ไม่ขึ้นหน้าต่างให้ยืนยัน แต่กด increment แล้วขึ้น

5. ข้อใดถูกต้องเกี่ยวกับฟังก์ชัน view

  2. ข. เขียน state variable ได้ถ้าไม่ได้ส่ง ETH
  3. ค. ถ้าฟังก์ชันที่แก้สถานะเรียกใช้ภายในธุรกรรม gas ที่ใช้จะนับรวมในธุรกรรมนั้น

ดูเฉลย

7. ใน OwnedCounter บัญชีที่ไม่ใช่ owner เรียก reset() ขณะที่ count เป็น 7 จะเกิดอะไรขึ้นกับ count, event และค่า gas
