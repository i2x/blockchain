Bitcoin Core: Mainnet, Testnet และ Regtest

บทที่ 0–3 อธิบายว่า Bitcoin ทำงานอย่างไรตาม Whitepaper บทนี้ลงมือใช้งานจริงด้วย Bitcoin Core ซอฟต์แวร์ที่ full node ส่วนใหญ่ในเครือข่ายใช้ เนื้อหาครอบคลุมส่วนประกอบของโปรแกรม เครือข่ายทดสอบแต่ละแบบ การตั้งค่า คำสั่งพื้นฐาน วิธีอ่านธุรกรรม (transaction) แบบ UTXO และรูปแบบของ address

ในบทนี้
  1. เริ่มจากโจทย์: ทดลองกับเงินที่โอนแล้วเรียกคืนไม่ได้
  2. ส่วนประกอบของ Bitcoin Core: bitcoind, bitcoin-cli และ bitcoin-qt
  3. ความแตกต่างของ Mainnet, Testnet, Signet และ Regtest
  4. ไฟล์ bitcoin.conf พอร์ต และไดเรกทอรีข้อมูลของแต่ละเครือข่าย
  5. คำสั่งพื้นฐาน: getblockchaininfo, getnewaddress, getbalance, sendtoaddress, generatetoaddress
  6. UTXO model: การอ่าน input, output, เงินทอน และค่าธรรมเนียม
  7. รูปแบบ address: Legacy (1…), P2SH (3…), SegWit (bc1q…), Taproot (bc1p…) และ Testnet (tb1…)
  8. สรุปท้ายบท
  9. แบบฝึกหัด

เริ่มจากโจทย์: ทดลองกับเงินที่โอนแล้วเรียกคืนไม่ได้

สมมุติว่าเราเขียนระบบรับชำระเงินด้วย Bitcoin ให้ร้านค้า ก่อนเปิดใช้งานต้องทดสอบหลายร้อยครั้ง ทั้งการรับเงิน การทอนเงิน และกรณีที่ผิดพลาด ถ้าทดสอบบนเครือข่ายจริงจะพบปัญหาสามข้อ

  • เสียเงินจริง: ทุกธุรกรรมต้องจ่ายค่าธรรมเนียม (fee) และถ้าโปรแกรมมีข้อผิดพลาด เช่น ลืมใส่เงินทอน (change) เงินส่วนนั้นจะตกเป็นของผู้ขุด (miner) ทันที
  • ย้อนกลับไม่ได้: บทที่ 1 อธิบายว่า Bitcoin ไม่มีตัวกลางที่ยกเลิกธุรกรรมให้ได้ ความผิดพลาดจึงแก้ไม่ได้
  • ช้า: บล็อกใหม่เกิดเฉลี่ยทุก 10 นาที ถ้ารอ 6 confirmation การทดสอบแต่ละครั้งจะใช้เวลาราวหนึ่งชั่วโมง เราจะขุดบล็อกเองเพื่อเร่งเวลาก็ไม่ได้ เพราะคอมพิวเตอร์ทั่วไปแข่งกับผู้ขุดรายใหญ่ไม่ทัน

Bitcoin Core จึงมีเครือข่ายหลายแบบที่ใช้กฎเดียวกับเครือข่ายจริง (mainnet) แต่เหรียญไม่มีมูลค่า และบางแบบสร้างบล็อกได้ทันทีตามคำสั่ง อีกเหตุผลหนึ่งที่ต้องรู้จัก Bitcoin Core มาจากบทที่ 3 บทนั้นสรุปว่าธุรกิจที่รับเงินบ่อยควรรัน full node ของตัวเอง และ full node ส่วนใหญ่ในเครือข่ายก็รัน Bitcoin Core

คำถามหัวข้อ
Bitcoin Core มีโปรแกรมอะไรบ้าง และสื่อสารกันอย่างไร4.1
ควรทดสอบบนเครือข่ายใด และแต่ละเครือข่ายต่างกันอย่างไร4.2
ตั้งค่าให้โหนดใช้เครือข่ายที่ต้องการได้อย่างไร และโหนดเก็บข้อมูลไว้ที่ใด4.3
สร้าง address ขุดบล็อก และโอนเงินด้วยคำสั่งใด4.4
ธุรกรรมที่ได้มีโครงสร้างอย่างไร เงินทอนและค่าธรรมเนียมอยู่ตรงไหน4.5
ดูจาก address ได้อย่างไรว่าเป็นของเครือข่ายใดและเป็นแบบใด4.6

4.1ส่วนประกอบของ Bitcoin Core: bitcoind, bitcoin-cli และ bitcoin-qt

ทำไมต้องแยกเป็นหลายโปรแกรม

full node ต้องทำงานตลอดเวลา ทั้งรับบล็อกจากเครือข่าย ตรวจธุรกรรม และส่งข้อมูลต่อให้โหนดอื่น แต่ผู้ใช้ต้องการสั่งงานเป็นครั้งคราว เช่น ขอ address ใหม่หรือโอนเงิน Bitcoin Core จึงแยก ตัวโหนดที่ทำงานเบื้องหลัง ออกจาก เครื่องมือสั่งงาน ทั้งสองส่วนคุยกันผ่าน JSON-RPC คือส่งคำสั่งและรับผลลัพธ์เป็น JSON ผ่าน HTTP เมื่อใช้มาตรฐานนี้ โปรแกรมที่เราเขียนเองจะเป็นภาษาใดก็สั่งงานโหนดได้เหมือนกัน

โปรแกรมหน้าที่
bitcoindตัวโหนด (daemon) ทำงานเบื้องหลังโดยไม่มีหน้าจอ เชื่อมต่อเครือข่าย ตรวจบล็อกและธุรกรรม เก็บ UTXO set และ mempool มี wallet ในตัว และเปิด JSON-RPC server ให้สั่งงาน
bitcoin-cliเครื่องมือบรรทัดคำสั่ง ส่งคำสั่ง RPC ไปยัง bitcoind ที่กำลังทำงานอยู่ แล้วแสดงผล bitcoin-cli เองไม่ได้เก็บหรือตรวจข้อมูลใด ๆ
bitcoin-qtโหนดแบบมีหน้าจอ GUI ทำงานเหมือน bitcoind และมีหน้าต่าง Console สำหรับพิมพ์คำสั่ง RPC ได้โดยตรง
bitcoin-cli รู้ได้อย่างไรว่าเราได้รับอนุญาต คำสั่ง RPC สั่งให้ wallet โอนเงินได้ ถ้าใครก็ส่งคำสั่งเข้าพอร์ต RPC ได้ เงินใน wallet ก็เสี่ยงทันที bitcoind จึงต้องตรวจว่าผู้ส่งคำสั่งได้รับอนุญาต ตามค่าเริ่มต้น ทุกครั้งที่ bitcoind เริ่มทำงาน โปรแกรมจะสร้างไฟล์ .cookie ที่มีรหัสผ่านแบบสุ่มไว้ใน data directory bitcoin-cli ที่รันบนเครื่องเดียวกันอ่านรหัสผ่านจากไฟล์นี้เพื่อยืนยันตัวตน (authentication) ผู้ที่ไม่มีสิทธิ์อ่านไฟล์ในเครื่องจึงสั่งงานโหนดไม่ได้ นอกจากนี้ ตามค่าเริ่มต้นโหนดรับคำสั่ง RPC จากเครื่องตัวเองเท่านั้น ถ้าต้องการสั่งงานจากเครื่องอื่น ต้องตั้ง rpcauth (ชื่อผู้ใช้และรหัสผ่าน) ร่วมกับ rpcbind และ rpcallowip

4.2ความแตกต่างของ Mainnet, Testnet, Signet และ Regtest

ทำไมเครือข่ายทดสอบแบบเดียวไม่พอ

เครือข่ายทดสอบ (test network) แต่ละแบบแก้ปัญหาคนละด้าน testnet ใกล้เคียงเครือข่ายจริงที่สุดแต่ไม่เสถียร signet เป็นเครือข่ายสาธารณะที่เสถียร ส่วน regtest ตัดผู้ร่วมเครือข่ายออกทั้งหมดเพื่อให้เราควบคุมได้ทุกอย่าง

  • Testnet เป็นเครือข่ายสาธารณะที่ใช้ PoW เหมือนเครือข่ายจริง ความยาก (difficulty) จึงแกว่งตามผู้ขุดที่เข้าออก เมื่อผู้ขุดรายใหญ่เลิกขุด ความยากยังสูงค้างอยู่จนกว่าจะครบรอบปรับความยาก (2,016 บล็อก) บล็อกใหม่อาจไม่เกิดเป็นวัน ๆ testnet3 จึงมีกฎพิเศษว่า ถ้าไม่มีบล็อกใหม่เกิน 20 นาที บล็อกถัดไปใช้ความยากต่ำสุดได้ แต่ผู้ขุดบางรายตั้งเวลาในบล็อก (timestamp) ให้ห่างจากบล็อกก่อนเกิน 20 นาทีเอง แล้วสร้างบล็อกความยากต่ำสุดต่อกันหลายบล็อก ถ้าบล็อกสุดท้ายของรอบปรับความยากเป็นบล็อกความยากต่ำสุด testnet3 จะคำนวณความยากของทั้งรอบถัดไปจากบล็อกนั้น ความยากจึงลดลงไปที่ค่าต่ำสุดทั้งรอบ และเกิดบล็อกหลายพันบล็อกในเวลาสั้น ๆ เรียกว่า block storm
  • Testnet4 (BIP94) เป็นเครือข่ายที่ Bitcoin Core v28 เพิ่มเข้ามาแทน testnet3 ยังมีกฎ 20 นาทีอยู่ แต่ปิดช่องที่ทำให้ความยากของทั้งรอบกลับเป็นค่าต่ำสุด (และแก้ช่องโหว่ timewarp ด้วย) รุ่นเดียวกันนี้ประกาศเลิกใช้ (deprecate) testnet3 และจะเลิกรองรับในรุ่นต่อ ๆ ไป ตอนนี้ -testnet ยังใช้ได้ แต่งานใหม่ควรใช้ testnet4 หรือ signet
  • Signet (BIP325) แก้ความไม่แน่นอนของ testnet โดยกำหนดว่านอกจาก PoW แล้ว บล็อกต้องมีลายเซ็น (signature) ของผู้ลงนาม (signer) ที่ระบุไว้ล่วงหน้าด้วย บล็อกจึงเกิดสม่ำเสมอราว 10 นาที และไม่มีใครก่อกวนเครือข่ายด้วยพลังประมวลผลได้ ข้อแลกเปลี่ยน (trade-off) คือ signet เสียความกระจายศูนย์ (decentralization) เพราะเครือข่ายต้องพึ่งผู้ลงนามกลุ่มเดียว แต่เหรียญไม่มีมูลค่าอยู่แล้ว ข้อเสียนี้จึงยอมรับได้
  • Regtest เป็นเครือข่ายส่วนตัวที่อยู่บนเครื่องเราเครื่องเดียว ชื่อมาจาก regression test คือการทดสอบซ้ำหลังแก้โค้ดว่าส่วนที่เคยทำงานถูกยังถูกอยู่ ความยากต่ำมากจนสร้างบล็อกได้ทันทีด้วยคำสั่ง ผู้ใช้จึงควบคุมได้ทุกอย่าง และการทดสอบให้ผลเหมือนเดิมทุกครั้ง เหมาะกับการเรียนและการทดสอบอัตโนมัติ

ทำไมเครือข่ายแต่ละแบบปนกันไม่ได้

ถ้าเหรียญทดสอบที่ได้ฟรีจาก faucet ไปปนกับเหรียญจริงได้ ใครก็จ่ายเงินด้วยเหรียญที่ไม่มีมูลค่าได้ และถ้าโหนดของ mainnet รับบล็อกของ testnet มาตรวจ โหนดก็เสียแรงกับข้อมูลที่ไม่เกี่ยวข้อง แต่ละเครือข่ายจึงแยกจากกันสี่ชั้น แต่ละชั้นกันปัญหาต่างกัน

  • Genesis block เป็นคนละบล็อก บล็อกของเครือข่ายหนึ่งจึงต่อเข้ากับสายของอีกเครือข่ายไม่ได้
  • ข้อความทุกข้อความในโปรโตคอล P2P ขึ้นต้นด้วย magic bytes ต่างกัน (ของ mainnet คือ F9 BE B4 D9) โหนดจึงทิ้งข้อความจากเครือข่ายอื่นได้ตั้งแต่ไบต์แรก
  • พอร์ตต่างกัน เครื่องเดียวจึงรันหลายเครือข่ายพร้อมกันได้
  • address มีคำนำหน้า (prefix) ต่างกัน wallet ของ mainnet จึงไม่ยอมส่งเงินไปยัง address ของ testnet ผู้ใช้ที่วาง address ผิดเครือข่ายก็ไม่เสียเงิน
กฎพิเศษของ regtest ที่ควรรู้ รางวัลบล็อก (block reward) เริ่มที่ 50 BTC เหมือน mainnet แต่ halving เกิดทุก 150 บล็อก แทนที่จะเป็นทุก 210,000 บล็อก เราจึงทดลองเรื่อง halving ได้ภายในไม่กี่วินาที ส่วนกฎ coinbase maturity ยังเหมือน mainnet ทุกประการ (หัวข้อ 4.4)

4.3ไฟล์ bitcoin.conf พอร์ต และไดเรกทอรีข้อมูลของแต่ละเครือข่าย

ทำไมต้องมีไฟล์ตั้งค่า

ตัวเลือก (option) ทุกตัวของ bitcoind ใส่ในบรรทัดคำสั่ง (command line) ได้ เช่น bitcoind -regtest -txindex=1 แต่ต้องพิมพ์ซ้ำทุกครั้งที่เริ่มโปรแกรม และถ้าพิมพ์ไม่ครบ โหนดจะทำงานด้วยค่าที่ไม่ตรงกับที่ตั้งใจ ถ้าเขียนค่าเหล่านี้ไว้ในไฟล์ bitcoin.conf ใน data directory โหนดจะอ่านไปใช้เองทุกครั้งที่เริ่มทำงาน

# bitcoin.conf สำหรับทดลองบน regtest
regtest=1          # ใช้เครือข่าย regtest (ไม่ใส่ = mainnet)
server=1           # เปิด JSON-RPC server (bitcoind เปิดให้อยู่แล้ว บรรทัดนี้จำเป็นเมื่อใช้ bitcoin-qt)
txindex=1          # ทำดัชนีทุกธุรกรรม เพื่อเรียกดูธุรกรรมใดก็ได้ด้วย getrawtransaction

[regtest]
fallbackfee=0.0002 # ค่าธรรมเนียมสำรอง (BTC ต่อ kvB) เพราะ regtest ไม่มีข้อมูลให้ประมาณค่าธรรมเนียม
# rpcport=18443    # ค่าเฉพาะเครือข่ายต้องอยู่ใต้ section ของเครือข่ายนั้น

ค่าที่อยู่ใต้ section [test], [testnet4], [signet], [regtest] หรือ [main] มีผลเฉพาะเครือข่ายนั้น ไฟล์เดียวจึงเก็บค่าของหลายเครือข่ายไว้ด้วยกันได้ ตัวเลือกที่ผูกกับเครือข่ายโดยตรง เช่น port และ rpcport ถ้าใส่ไว้นอก section โหนดจะใช้ค่านั้นกับ mainnet เท่านั้น เหตุผลคือ ถ้าค่าพอร์ตเดียวมีผลกับทุกเครือข่าย โหนด regtest กับโหนด mainnet บนเครื่องเดียวกันจะแย่งพอร์ตเดียวกัน และ bitcoin-cli อาจต่อผิดเครือข่ายโดยไม่รู้ตัว

ไดเรกทอรีข้อมูล (data directory)

ตำแหน่งเริ่มต้นบน Linux คือ ~/.bitcoin/ และบน macOS คือ ~/Library/Application Support/Bitcoin/ เครือข่ายทดสอบแต่ละแบบเก็บข้อมูลในไดเรกทอรีย่อยของตัวเอง ข้อมูลของแต่ละเครือข่ายจึงไม่ปนกัน

4.4คำสั่งพื้นฐาน: getblockchaininfo, getnewaddress, getbalance, sendtoaddress, generatetoaddress

หัวข้อนี้ทดลองครบวงจร ตั้งแต่เริ่มโหนด ขุดเหรียญ โอนเงิน จนถึงยืนยันธุรกรรม ตัวอย่างนี้สร้าง wallet สองใบชื่อ alice และ bob ไว้บนโหนดเดียวกัน แทนผู้ใช้สองคน ทุกคำสั่งใส่ -regtest ไว้ ถ้าตั้ง regtest=1 ใน bitcoin.conf แล้วก็ไม่ต้องใส่ ส่วน address, txid และค่าธรรมเนียมในผลลัพธ์เป็นค่าตัวอย่าง เมื่อทดลองจริงจะได้ค่าต่างออกไป

1. เริ่มโหนดและตรวจสถานะ

bitcoind -regtest -daemon
bitcoin-cli -regtest getblockchaininfo
{
  "chain": "regtest",
  "blocks": 0,
  "headers": 0,
  "bestblockhash": "0f9188f13cb7b2c71f2a335e3a4fc328bf5beb436012afca590b1a11466e2206",
  "difficulty": 4.656542373906925e-10,
  "initialblockdownload": true,
  "size_on_disk": 293,
  "pruned": false,
  ...
}

getblockchaininfo เป็นคำสั่งแรกที่ควรใช้เสมอ เพราะบอกว่าโหนดอยู่บนเครือข่ายใด (chain) และมีบล็อกกี่บล็อก (blocks) ตอนนี้มีเพียง Genesis block ที่ความสูง (height) 0 ค่า difficulty ต่ำมาก regtest จึงสร้างบล็อกได้ทันที

ค่า initialblockdownload บอกว่าโหนดยังอยู่ในช่วงดาวน์โหลดและตรวจบล็อกย้อนหลัง (initial block download) หรือไม่ บน mainnet ค่านี้เป็น true จนกว่าโหนดจะตามบล็อกล่าสุดทัน บน regtest ค่านี้ก็เป็น true เช่นกัน เพราะโหนดดูจากเวลาในบล็อกล่าสุด และ Genesis block ของ regtest มีเวลาเก่ามาก (ปี 2011) เมื่อขุดบล็อกแรก ค่านี้จะเปลี่ยนเป็น false

2. สร้าง wallet และ address

bitcoin-cli -regtest createwallet "alice"
bitcoin-cli -regtest createwallet "bob"
bitcoin-cli -regtest -rpcwallet=alice getnewaddress
bcrt1qg7x5l0r4m6s7ak8xw3... (address ของ alice)

ตั้งแต่ Bitcoin Core v0.21 โหนดไม่สร้าง wallet ให้อัตโนมัติ ต้องสร้างเองด้วย createwallet เมื่อเปิด wallet ไว้มากกว่าหนึ่งใบ ต้องระบุ -rpcwallet=ชื่อ เพื่อบอกว่าคำสั่งนี้ใช้กับ wallet ใด

ทำไมต้องขอ address ใหม่ทุกครั้ง ข้อมูลบน blockchain เปิดให้ทุกคนดู ถ้าใช้ address เดิมรับเงินทุกครั้ง ใครก็รวบรวมได้ว่า address นั้นได้รับเงินจากใครและมียอดเท่าใด Whitepaper ข้อ 10 จึงแนะนำให้ใช้คู่กุญแจ (key pair) ชุดใหม่ในทุกธุรกรรม getnewaddress ทำตามหลักนี้ คือสร้าง address ใหม่จาก wallet เดิมทุกครั้งที่เรียก ถึงแต่ละ address จะมีกุญแจคนละคู่ ก็ไม่ต้องสำรองข้อมูล (backup) ใหม่ เพราะ wallet ของ Bitcoin Core รุ่นปัจจุบันเป็นแบบ HD (hierarchical deterministic, BIP32) กุญแจทุกคู่คำนวณมาจาก seed เดียวกัน backup ครั้งเดียวจึงกู้คืน address ทุกตัวที่สร้างภายหลังได้

3. ขุดบล็อกให้ได้เหรียญ

bitcoin-cli -regtest generatetoaddress 101 bcrt1qg7x5l0r4m6s7ak8xw3...
bitcoin-cli -regtest -rpcwallet=alice getbalance
50.00000000
bitcoin-cli -regtest -rpcwallet=alice getbalances
{ "mine": { "trusted": 50.00000000, "untrusted_pending": 0.00000000, "immature": 5000.00000000 } }

generatetoaddress สร้างบล็อกตามจำนวนที่กำหนด และจ่ายรางวัลบล็อกเข้า address ที่ระบุ คำสั่งนี้ใช้ได้จริงเฉพาะบน regtest เพราะบน mainnet และ testnet CPU ของเครื่องเราหา nonce ที่ทำให้ block hash ต่ำกว่า target ได้ช้ากว่าผู้ขุดรายอื่นมาก ส่วนบน signet บล็อกต้องมีลายเซ็นของผู้ลงนาม เราจึงสร้างบล็อกเองไม่ได้เลย

ทำไมขุด 101 บล็อกแต่ใช้ได้เพียง 50 BTC

ขุดไป 101 บล็อก บล็อกละ 50 BTC รวม 5,050 BTC แต่ getbalance แสดงเพียง 50 BTC เพราะกฎ coinbase maturity กำหนดว่าเหรียญจาก coinbase transaction ต้องมีบล็อกต่อท้ายครบ 100 บล็อกก่อนจึงนำไปใช้ได้ ในตัวอย่างนี้ มีเพียงรางวัลของบล็อกที่ 1 ที่ครบเงื่อนไข รางวัลของอีก 100 บล็อกยังอยู่ในสถานะ immature รวม 5,000 BTC

กฎนี้แก้ปัญหาที่เกิดจากการแยกสายชั่วคราว (temporary fork) ในบทที่ 2 ถ้าบล็อกหนึ่งกลายเป็น stale block ธุรกรรมทั่วไปในบล็อกนั้นยังกลับเข้า mempool แล้วลงบล็อกในสายใหม่ได้ แต่ coinbase transaction ทำแบบนั้นไม่ได้ เพราะบล็อกในสายใหม่มี coinbase ของผู้ขุดคนใหม่อยู่แล้ว รางวัลของบล็อกเดิมจึงหายไปทั้งก้อน

ถ้าผู้ขุดนำรางวัลนั้นไปจ่ายให้คนอื่นแล้ว ธุรกรรมทุกทอดที่ต่อจากเหรียญนั้นจะใช้ไม่ได้ ผู้รับเงินทุกทอดจึงเสียเงินไปด้วย ทั้งที่ไม่ได้ทำอะไรผิด กฎ coinbase maturity จึงให้รอจนมีบล็อกต่อท้ายครบ 100 บล็อก ถึงตอนนั้น โอกาสที่บล็อกนั้นจะกลายเป็น stale block ต่ำจนแทบเป็นศูนย์ Whitepaper ไม่ได้กล่าวถึงกฎนี้ และคำอธิบายที่พบทั่วไปคือ ตัวเลข 100 เป็นค่าที่ตั้งไว้เผื่อเหลือมาก

4. โอนเงินและดู mempool

bitcoin-cli -regtest -rpcwallet=bob getnewaddress
bcrt1qp3n8kd0y2c... (address ของ bob)
bitcoin-cli -regtest -rpcwallet=alice sendtoaddress bcrt1qp3n8kd0y2c... 10
6c1f8e0a54b3...     (txid ของธุรกรรมใหม่)
bitcoin-cli -regtest getrawmempool
[ "6c1f8e0a54b3..." ]

sendtoaddress สั่งให้ wallet ทำหลายขั้นในคำสั่งเดียว ได้แก่ เลือก UTXO ที่จะใช้ คำนวณค่าธรรมเนียม สร้าง output เงินทอน (ทั้งสามเรื่องนี้อธิบายในหัวข้อ 4.5) ลงลายเซ็น และประกาศ (broadcast) ธุรกรรมให้เครือข่าย ขั้นสุดท้ายนี้ตรงกับขั้นตอนที่ 1 ของ Whitepaper ข้อ 5 ธุรกรรมที่ประกาศแล้วแต่ยังไม่อยู่ในบล็อกจะรออยู่ใน mempool และดูรายการได้ด้วย getrawmempool

5. ยืนยันธุรกรรมด้วยการขุดบล็อก

bitcoin-cli -regtest generatetoaddress 1 bcrt1qg7x5l0r4m6s7ak8xw3...
bitcoin-cli -regtest -rpcwallet=bob getbalance
10.00000000
bitcoin-cli -regtest -rpcwallet=alice gettransaction 6c1f8e0a54b3...
{ "amount": -10.00000000, "fee": -0.00002820, "confirmations": 1, ... }

บน regtest ไม่มีผู้ขุดรายอื่น ธุรกรรมจะอยู่ใน mempool ไปเรื่อย ๆ จนกว่าเราจะขุดบล็อกเอง หลังขุดหนึ่งบล็อก bob มีเงิน 10 BTC และธุรกรรมมี 1 confirmation

ยอดของ alice เปลี่ยนสองทาง ทางแรก alice จ่าย 10 BTC และค่าธรรมเนียม 0.0000282 BTC ทางที่สอง เมื่อถึงความสูง 102 รางวัลของบล็อกที่ 2 มีบล็อกต่อท้ายครบ 100 บล็อกพอดี alice จึงได้ 50 BTC ที่ใช้ได้เพิ่มมา getbalance ของ alice จึงเป็น 50 − 10 − 0.0000282 + 50 = 89.9999718 BTC

4.5UTXO model: การอ่าน input, output, เงินทอน และค่าธรรมเนียม

ทำไม Bitcoin ไม่เก็บยอดเงินเป็นตัวเลขในบัญชี

บทที่ 1 นิยามเหรียญว่าเป็นสายโซ่ของลายเซ็น (chain of digital signatures) ไม่ใช่ตัวเลขยอดคงเหลือ ผู้รับจึงตรวจเองได้ว่าเหรียญก้อนนี้ส่งต่อกันมาถูกต้องทุกทอด ในทางปฏิบัติ Bitcoin เก็บเงินเป็นก้อน เรียกว่า UTXO (Unspent Transaction Output) คือ output ของธุรกรรมก่อนหน้าที่ยังไม่มีใครนำไปใช้ ยอดเงินใน wallet คือผลรวมของ UTXO ทุกก้อนที่ wallet มี private key ปลดล็อกได้ ข้อดีคือโหนดตรวจการใช้จ่ายซ้ำ (double-spending) ได้ง่าย เพียงดูว่าก้อนที่ input อ้างถึงยังอยู่ใน UTXO set หรือไม่ การเก็บเงินเป็นก้อนเป็นทางเลือกในการออกแบบของ Bitcoin ไม่ใช่ข้อบังคับของระบบที่ไม่มีตัวกลาง Ethereum เลือกเก็บยอดคงเหลือของแต่ละบัญชีแทน (บทที่ 5)

กติกาของธุรกรรม

  • Input อ้างถึง UTXO เดิมด้วย txid และลำดับของ output (vout) และแนบลายเซ็นที่ปลดล็อก UTXO นั้นได้
  • UTXO แต่ละก้อนต้อง ใช้ทั้งก้อน แบ่งใช้บางส่วนไม่ได้ เหมือนธนบัตรที่ฉีกครึ่งจ่ายไม่ได้ กติกานี้ทำให้ UTXO มีแค่สองสถานะ คือยังไม่ใช้ (อยู่ใน UTXO set) หรือใช้ไปแล้ว (ลบออก) โหนดจึงไม่ต้องจำว่าแต่ละก้อนเหลืออยู่เท่าใด ถ้ายอมให้ใช้บางส่วน ธุรกรรมหลายรายการจะอ้างถึงก้อนเดียวกันได้ และการตรวจ double-spending จะซับซ้อนขึ้นมาก
  • Output คือก้อนเงินใหม่ที่ล็อกไว้ให้ผู้รับ ถ้า input รวมกันเกินยอดที่ต้องจ่าย ผู้จ่ายต้องสร้าง output เงินทอน กลับมาที่ address ของตัวเอง
  • ค่าธรรมเนียม ไม่มีช่องให้ระบุในธุรกรรม แต่เป็นส่วนต่างระหว่างผลรวม input กับผลรวม output ผู้ขุดเก็บส่วนต่างนี้ผ่าน coinbase transaction
ถ้าลืมสร้างเงินทอน ถ้าธุรกรรมใช้ UTXO 1 BTC เพื่อจ่าย 0.1 BTC โดยไม่มี output เงินทอน ส่วนต่าง 0.9 BTC จะกลายเป็นค่าธรรมเนียมของผู้ขุดทันที และเรียกคืนไม่ได้ ความผิดพลาดแบบนี้เคยเกิดขึ้นจริงกับผู้ที่ประกอบธุรกรรมเองทีละขั้น และเป็นเหตุผลหนึ่งที่ควรทดลองบน regtest ก่อน

อ่านธุรกรรมจาก getrawtransaction

ตัวอย่างนี้เป็นธุรกรรมของ Alice ตามแผนภาพด้านบน (input 0.3 และ 0.5 BTC) ไม่ใช่ธุรกรรม 10 BTC ในหัวข้อ 4.4 ผลลัพธ์ได้จาก getrawtransaction txid true และตัดบางฟิลด์ออก

  "txid": "9b7d2e41c0f8...",
  "vin": [

  ],
  "vout": [

}
  • vin แต่ละรายการชี้ไปยัง output เดิมด้วยคู่ txid กับ vout และมีลายเซ็นกับ public key อยู่ใน txinwitness (สำหรับ address แบบ SegWit) ระวังชื่อซ้ำ ฟิลด์ vout ภายใน vin เป็นเลขลำดับ output ของธุรกรรมก่อนหน้า (ตรงกับค่า n ในธุรกรรมนั้น) ไม่ใช่รายการ output ของธุรกรรมนี้
  • vin ไม่มีจำนวนเงิน เพราะจำนวนเงินบันทึกอยู่แล้วใน output เดิมที่ input อ้างถึง และโหนดค้นจาก UTXO set เองได้ ถ้าจะคำนวณค่าธรรมเนียมจากผลลัพธ์นี้ จึงต้องเปิดดูธุรกรรมก่อนหน้าด้วย ตั้งแต่ Bitcoin Core v25 ถ้าใช้ getrawtransaction txid 2 (verbosity 2) โหนดจะค้น output เดิมมาแสดงใน prevout ของแต่ละ input และคำนวณ fee ให้
  • vout แต่ละรายการมีจำนวนเงิน (value) ลำดับ (n) และสคริปต์ล็อก (locking script หรือ scriptPubKey) คือเงื่อนไขที่ผู้ใช้เงินก้อนนี้ต้องทำให้ครบ output เหล่านี้จะกลายเป็น UTXO และธุรกรรมถัดไปอ้างถึงได้ด้วย txid ของธุรกรรมนี้คู่กับค่า n
ประเด็นที่มักออกสอบ: UTXO เทียบกับ Account model Bitcoin ใช้ UTXO: เงินเป็นก้อน ใช้ทั้งก้อน มีเงินทอน และค่าธรรมเนียมคือส่วนต่างของ input กับ output Ethereum (บทที่ 5) ใช้ Account model: แต่ละบัญชีมียอดคงเหลือเป็นตัวเลข การโอนคือลดยอดของผู้ส่งแล้วเพิ่มยอดของผู้รับ และใช้ตัวนับ nonce ของบัญชี (คนละตัวกับ nonce ใน PoW ของบทที่ 2) กันไม่ให้ใครนำธุรกรรมเดิมมาส่งซ้ำ UTXO model ไม่ต้องมีตัวนับนี้ เพราะ UTXO แต่ละก้อนใช้ได้ครั้งเดียว ธุรกรรมที่ส่งซ้ำจะอ้างถึงก้อนที่ใช้ไปแล้ว โหนดจึงปฏิเสธเอง

4.6รูปแบบ address: Legacy (1…), P2SH (3…), SegWit (bc1q…), Taproot (bc1p…) และ Testnet (tb1…)

ทำไม address จึงมีหลายแบบ

address ไม่ได้เป็นแค่ตัวระบุผู้รับ แต่บอก wallet ของผู้จ่ายว่าต้องสร้าง output ด้วย สคริปต์ล็อก (locking script) แบบใด เมื่อ Bitcoin เพิ่มเงื่อนไขแบบใหม่ที่ประหยัดค่าธรรมเนียมกว่าหรือทำได้มากกว่า ก็ต้องมี address รูปแบบใหม่ให้ wallet แยกแยะได้ แบบเก่ายังใช้ต่อได้ เพราะเหรียญจำนวนมากยังล็อกไว้ด้วยเงื่อนไขเก่า ถ้ายกเลิกแบบเก่า เหรียญเหล่านั้นจะใช้ไม่ได้อีก นอกจากนี้ address ทุกแบบมี checksum อยู่ในตัว ถ้าพิมพ์ผิดหนึ่งตัว wallet จะตรวจพบและไม่ยอมส่งเงิน

แบบขึ้นต้น (mainnet)ขึ้นต้น (testnet / regtest)การเข้ารหัสลักษณะเด่น
P2PKH (Legacy)1…m… หรือ n…Base58Checkแบบแรกของ Bitcoin ล็อกด้วยแฮชของ public key ค่าธรรมเนียมสูงที่สุด
P2SH3…2…Base58Checkล็อกด้วยแฮชของสคริปต์ (script hash) ตาม BIP16 ปี 2012 ก่อนมี P2SH ผู้จ่ายต้องใส่สคริปต์ multisig ทั้งชุดลงใน output และจ่ายค่าธรรมเนียมส่วนนั้นแทนผู้รับ P2SH ให้ผู้จ่ายใส่เพียงแฮช ผู้รับเป็นคนเปิดเผยสคริปต์ตอนใช้เงิน ใช้กับ multisig และ wrapped SegWit (SegWit ที่ห่อไว้ใน P2SH เพื่อให้ wallet รุ่นเก่าส่งเงินมาได้)

ทำไมตัวอักษรหลัง bc1 จึงเป็น q หรือ p

ส่วน bc เรียกว่า human-readable part (HRP) ทำหน้าที่เป็นคำนำหน้า (prefix) ที่บอกเครือข่าย (testnet และ signet ใช้ tb ส่วน regtest ใช้ bcrt) ตัว 1 คือตัวคั่น (separator) และตัวถัดมาคือ witness version ที่เข้ารหัสแล้ว ชุดตัวอักษรของ Bech32 ใช้ q แทนค่า 0 และใช้ p แทนค่า 1 SegWit v0 จึงขึ้นต้นด้วย bc1q และ Taproot ซึ่งเป็น v1 จึงขึ้นต้นด้วย bc1p

ทำไมรูปแบบการเข้ารหัสจึงต่างกัน Base58 ตัดตัวอักษรที่ดูคล้ายกันออก ได้แก่ 0, O, I และ l เพื่อให้อ่านผิดน้อยลง Bech32 ไม่ผสมตัวพิมพ์เล็กกับตัวพิมพ์ใหญ่ (ปกติใช้ตัวพิมพ์เล็ก) จึงอ่านออกเสียงและพิมพ์ได้ง่ายกว่า และ checksum ของ Bech32 ตรวจจับข้อผิดพลาดได้ดีกว่า ภายหลังนักพัฒนาพบว่า ถ้า address ลงท้ายด้วย p แล้วมีคนเติมหรือลบตัว q หน้าตัวนั้น checksum ของ Bech32 ตรวจไม่พบ จึงออก Bech32m (BIP350) มาใช้กับ witness version 1 ขึ้นไป ส่วน SegWit v0 ยังใช้ Bech32 เหมือนเดิม
ประเด็นที่มักออกสอบ ต้องดูตัวอักษรขึ้นต้นแล้วบอกได้ทั้งเครือข่ายและชนิดของ address เช่น tb1q… คือ Native SegWit บน testnet หรือ signet ส่วน bcrt1… คือ regtest และ 3… คือ P2SH บน mainnet

สรุปท้ายบท

  • โจทย์: ธุรกรรมบน mainnet เสียเงินจริง ย้อนกลับไม่ได้ และช้า นักพัฒนาจึงต้องทดสอบบนเครือข่ายที่ใช้กฎเดียวกันแต่เหรียญไม่มีมูลค่า
  • 4.1: bitcoind คือตัวโหนด bitcoin-cli ส่งคำสั่งผ่าน JSON-RPC และ bitcoin-qt คือโหนดที่มี GUI
  • 4.2: testnet ใช้ PoW แบบสาธารณะและไม่เสถียร (testnet3 ประกาศเลิกใช้แล้ว งานใหม่ควรใช้ testnet4) signet เพิ่มลายเซ็นของผู้ลงนามเพื่อให้บล็อกสม่ำเสมอ regtest เป็นเครือข่ายส่วนตัวที่ขุดได้ทันที แต่ละเครือข่ายแยกกันด้วย Genesis block, magic bytes, พอร์ต และคำนำหน้า address
  • 4.3: ตั้งค่าใน bitcoin.conf ค่าเฉพาะเครือข่ายใส่ใต้ section [test], [testnet4], [signet] หรือ [regtest] และข้อมูลแต่ละเครือข่ายอยู่ในไดเรกทอรีย่อยของตัวเอง
  • 4.4: กฎ coinbase maturity กำหนดให้รอ 100 บล็อก บน regtest จึงต้องขุด 101 บล็อกก่อนจะใช้รางวัลของบล็อกแรกได้ ธุรกรรมที่ส่งแล้วจะรออยู่ใน mempool จนกว่าจะมีคนขุดบล็อกใหม่
  • 4.5: UTXO ต้องใช้ทั้งก้อน ส่วนเกินต้องทอนกลับ ค่าธรรมเนียมคือผลรวม input ลบผลรวม output
  • 4.6: 1… P2PKH, 3… P2SH, bc1q… SegWit v0, bc1p… Taproot ส่วน tb1… คือ testnet/signet และ bcrt1… คือ regtest
