Ethereum และ Smart Contract เบื้องต้น

Bitcoin ตอบโจทย์เงินดิจิทัลที่ไม่ต้องมีตัวกลาง Ethereum ขยายโจทย์ต่อว่า ถ้าเครือข่ายตกลงกันเรื่องยอดเงินได้ ก็ควรตกลงกันได้ด้วยว่าโปรแกรมทำงานแล้วได้ผลอะไร บทนี้อธิบายสิ่งที่ Ethereum ต้องเปลี่ยนเพื่อให้ทำเช่นนั้นได้ ได้แก่ Account model บัญชีสองประเภท EVM (Ethereum Virtual Machine) โครงสร้างของธุรกรรมและบล็อก กฎเลือกสาย (fork choice rule) ค่า gas ภาษา Solidity และเครื่องมือสำหรับทดลอง

เริ่มจากโจทย์: ทุกแอปต้องสร้าง blockchain ของตัวเองหรือไม่

หลังจาก Bitcoin ใช้งานได้จริง หลายคนต้องการนำแนวคิดเดียวกันไปใช้กับเรื่องอื่นนอกจากการโอนเงิน เช่น ระบบจดทะเบียนชื่อโดเมน การออกเหรียญของตัวเอง หรือการโหวตขององค์กร แต่ผู้ออกแบบจงใจให้ Bitcoin Script ทำได้น้อย เพราะทุกโหนดต้องรันสคริปต์ของทุกธุรกรรม ถ้าสคริปต์วนลูปได้ ผู้โจมตีก็ส่งสคริปต์ที่ไม่มีวันจบมาทำให้ทุกโหนดค้างได้ ภาษานี้จึงไม่มีลูป เก็บข้อมูลข้ามธุรกรรมไม่ได้ และทำได้เพียงกำหนดเงื่อนไขการปลดล็อกเหรียญ ในช่วงแรกจึงต้องสร้าง blockchain ใหม่สำหรับแต่ละแอป เช่น Namecoin (2011) แยกมาจาก Bitcoin เพื่อใช้จดทะเบียนชื่อโดยเฉพาะ

ปัญหาของการสร้าง blockchain ใหม่ทุกครั้ง

  • พลังขุดกระจายคนละ chain: บทที่ 2 แสดงว่าผู้โจมตีต้องมีพลังขุด (hash power) มากกว่าครึ่งของทั้งเครือข่ายจึงจะเขียนประวัติใหม่ได้ บน chain ใหม่ที่มีผู้ขุด (miner) เพียงไม่กี่ราย ผู้โจมตีหาพลังขุดเกินครึ่งได้ง่าย และโจมตีแบบ 51% ได้
  • ต้นทุนซ้ำซ้อน: ทุกแอปต้องสร้างเครือข่าย โหนด และผู้ขุดใหม่ทั้งหมด
  • แอปคุยกันไม่ได้: เหรียญบน chain หนึ่งใช้กับแอปบนอีก chain หนึ่งโดยตรงไม่ได้

ทางออกของ Ethereum: blockchain เดียวที่เขียนโปรแกรมได้

Vitalik Buterin เสนอ Ethereum ในปลายปี 2013 และเครือข่ายเปิดใช้งานในเดือนกรกฎาคม 2015 แนวคิดคือสร้าง blockchain เดียวที่มีภาษาโปรแกรมทั่วไปในตัว ใครต้องการสร้างแอปก็เขียนโปรแกรมแล้ว deploy ขึ้น chain นี้ ทุกแอปใช้ความปลอดภัยร่วมกัน และเรียกใช้กันได้โดยตรง เมื่อเครือข่ายต้องตกลงกันเรื่องผลของโปรแกรมแทนยอดเงิน ก็มีคำถามใหม่ตามมาหลายข้อ

5.1UTXO model ของ Bitcoin เทียบกับ Account model ของ Ethereum

ทำไม Ethereum ไม่ใช้ UTXO

บทที่ 4 แสดงว่า UTXO เหมาะกับเงิน เพราะเงินแต่ละก้อนใช้ได้ครั้งเดียวแล้วหมดไป จึงตรวจการใช้จ่ายซ้ำ (double-spending) ได้ง่าย แต่โปรแกรมต้องการสิ่งที่ต่างออกไป เช่น โปรแกรมนับคะแนนโหวตต้องจำว่าตอนนี้แต่ละตัวเลือกได้กี่คะแนน และแก้ตัวเลขนั้นทุกครั้งที่มีคนโหวต ถ้าเก็บคะแนนไว้ใน UTXO ก้อนหนึ่ง ทุกการโหวตต้องใช้ก้อนนั้นจนหมดแล้วสร้างก้อนใหม่ที่มีคะแนนล่าสุด เมื่อสองคนโหวตพร้อมกัน ธุรกรรมทั้งสองจะอ้างถึง UTXO ก้อนเดียวกัน เครือข่ายรับได้เพียงรายการเดียว อีกคนต้องสร้างธุรกรรมใหม่จากก้อนล่าสุด Ethereum จึงเลือก Account model และเก็บ world state (สถานะของทุกบัญชี ณ ขณะนั้น) เป็นตารางบัญชี แต่ละบัญชีมียอดคงเหลือและข้อมูลที่แก้ทับได้

ทำไม Account model ต้องมี nonce

ใน Bitcoin ธุรกรรมที่บันทึกลง chain แล้วส่งซ้ำไม่ได้ เพราะ UTXO ที่ธุรกรรมนั้นอ้างถึงหายไปแล้ว แต่ Account model ไม่มีก้อนเงินที่ใช้แล้วหมดไป ถ้าไม่มีกลไกเพิ่มเติม ใครก็ตามที่เห็นธุรกรรม "Alice โอน 0.6 ETH ให้ Bob" ซึ่ง Alice ลงลายเซ็นแล้ว ก็นำธุรกรรมเดิมไปส่งซ้ำได้เรื่อย ๆ จนเงินของ Alice หมด การโจมตีแบบนี้เรียกว่า replay attack Ethereum จึงให้ทุกบัญชีมี nonce เป็นตัวนับธุรกรรมที่บัญชีนั้นส่งไปแล้ว ธุรกรรมจะผ่านก็ต่อเมื่อระบุ nonce ตรงกับค่าปัจจุบันของบัญชี เมื่อผ่านแล้ว nonce ของบัญชีจะเพิ่มขึ้นหนึ่ง ธุรกรรมเดิมจึงใช้ซ้ำไม่ได้ นอกจากนี้ nonce ยังบังคับให้ธุรกรรมจากบัญชีเดียวกันเข้าบล็อกตามลำดับ

nonce สองความหมาย nonce ในบทที่ 2 คือตัวเลขที่ผู้ขุดเปลี่ยนไปเรื่อย ๆ จนได้ค่าแฮชของ header ต่ำกว่าเป้าหมาย (target) ส่วน nonce ของบัญชี Ethereum คือตัวนับธุรกรรม ทั้งสองใช้ชื่อเดียวกันเพราะมาจากคำว่า "number used once" แต่ทำหน้าที่คนละอย่าง
UTXO model (Bitcoin)Account model (Ethereum)
สิ่งที่บันทึกก้อนเงินที่ยังไม่ได้ใช้ (UTXO)ยอดคงเหลือ nonce code และ storage ของแต่ละบัญชี
การโอนใช้ก้อนเดิมทั้งก้อน แล้วสร้างก้อนใหม่และเงินทอน (change)ลดยอดผู้ส่ง เพิ่มยอดผู้รับ
ป้องกันการใช้ซ้ำก้อนที่อ้างถึงต้องยังอยู่ใน UTXO setnonce ต้องตรงกับค่าปัจจุบัน
ความเป็นส่วนตัวดีกว่า ใช้ address ใหม่ได้ทุกครั้งด้อยกว่า มักใช้บัญชีเดิมตลอด
ตรวจธุรกรรมแบบขนาน (parallel)ทำได้ง่าย ธุรกรรมที่ใช้ก้อนต่างกันไม่เกี่ยวข้องกันยากกว่า ธุรกรรมหลายรายการอาจแก้บัญชีเดียวกัน
เหมาะกับการโอนเงินโปรแกรมที่ต้องจำและแก้สถานะ

5.2บัญชีผู้ใช้ (EOA) และบัญชีสัญญา (Contract account)

ทำไมต้องมีบัญชีสองประเภท

บน Ethereum โปรแกรมต้องถือเงินได้ เช่น โปรแกรมระดมทุนต้องเก็บ ETH ไว้จนกว่าจะครบเป้า แต่โปรแกรมถือ private key เองไม่ได้ ถ้าให้ใครคนหนึ่งถือ private key แทน คนนั้นก็ถอนเงินออกไปได้ตามใจ ผู้ใช้จึงต้องกลับไปเชื่อใจคนคนนั้น Ethereum จึงแบ่งบัญชีเป็นสองประเภท ได้แก่ บัญชีที่ควบคุมด้วย private key และบัญชีที่ควบคุมด้วยโค้ด

EOA (Externally Owned Account)Contract account
ควบคุมโดยprivate key ของผู้ใช้โค้ดของ contract
มี code และ storageไม่มีมี
เริ่มธุรกรรมเองได้ได้ ทุกธุรกรรมต้องเริ่มจาก EOAไม่ได้ ทำงานเมื่อมีผู้เรียกเท่านั้น
ที่มาของ address20 ไบต์สุดท้ายของค่าแฮช Keccak-256 ของ public keyคำนวณจาก address ของผู้สร้างกับ nonce ของผู้สร้าง (ถ้าสร้างด้วย CREATE2 จะใช้ address ผู้สร้าง, salt และค่าแฮชของ init code แทน nonce)
จ่ายค่า gasผู้ส่งธุรกรรมเป็นผู้จ่ายไม่ได้จ่าย ใช้ gas ที่ EOA ผู้เรียกจ่ายมา

address ของ Ethereum ทั้งสองประเภทมีรูปแบบเดียวกัน คือ 0x ตามด้วยเลขฐานสิบหก 40 ตัว (20 ไบต์) ดูจาก address อย่างเดียวจึงแยกไม่ได้ว่าเป็นบัญชีประเภทใด ต้องตรวจว่ามี code อยู่ที่ address นั้นหรือไม่ ส่วน address ที่เขียนตัวพิมพ์ใหญ่ปนเล็กคือ checksum ตาม EIP-55 ตัวพิมพ์ใหญ่เล็กเหล่านี้ใช้จับการพิมพ์ผิด เช่นเดียวกับ checksum ของ address ใน Bitcoin

ข้อมูลเพิ่มเติม การอัปเกรด Pectra (พฤษภาคม 2025) เพิ่ม EIP-7702 ให้ EOA ตั้งค่าให้ใช้โค้ดของ contract ได้ เส้นแบ่งระหว่างบัญชีสองประเภทจึงไม่ชัดเท่าเดิม แต่หลักที่ว่าทุกธุรกรรมเริ่มจากผู้ถือ private key ยังเป็นจริง และข้อสอบพื้นฐานถามหลักข้อนี้ ผลข้างเคียงอีกข้อคือ EOA ที่ตั้งค่าตาม EIP-7702 จะมี code สั้น ๆ ที่ชี้ไปยัง contract อื่น การตรวจว่ามี code อยู่ที่ address จึงแยกบัญชีสองประเภทได้ไม่แน่นอนเหมือนเดิม

5.3Smart contract และการทำงานบน EVM

Smart contract คืออะไร

Nick Szabo เสนอคำว่า smart contract ในช่วงทศวรรษ 1990 ตัวอย่างที่เขาใช้คือ ตู้ขายของอัตโนมัติ (vending machine) เมื่อใส่เงินครบและกดเลือก ตู้ก็ส่งสินค้าออกมาตามกติกาที่ตั้งไว้ในเครื่อง ผู้ซื้อไม่ต้องพึ่งพนักงานและไม่ต้องเชื่อใจผู้ขาย บน Ethereum smart contract คือโปรแกรมที่ deploy ไว้ที่ address หนึ่งบน blockchain เมื่อมีธุรกรรมเรียก โปรแกรมจะทำงานตามโค้ดและแก้สถานะได้ ไม่มีใครแก้กติกาหรือหยุดโปรแกรมได้ เว้นแต่โค้ดจะเขียนเปิดช่องไว้

ทำไมต้องมี virtual machine

ใน Bitcoin ทุกโหนดตรวจลายเซ็นของทุกธุรกรรมเอง ใน Ethereum ทุกโหนดต้อง รันโปรแกรมของทุกธุรกรรมเอง แล้วเทียบว่าได้สถานะใหม่ตรงกับที่ผู้สร้างบล็อกประกาศ ถ้าผลต่างกันแม้บิตเดียว เครือข่ายจะตกลงกันไม่ได้ แต่แต่ละโหนดใช้ CPU ระบบปฏิบัติการ และภาษาโปรแกรมต่างกัน Ethereum จึงกำหนด EVM (Ethereum Virtual Machine) เป็นคอมพิวเตอร์จำลองที่ทุกโหนดใช้กติกาเดียวกัน ทุกคำสั่ง (opcode) ให้ผลแน่นอนตามที่กำหนดไว้ (deterministic)

ลักษณะของ EVM

  • คอมไพเลอร์แปลโค้ด Solidity เป็น bytecode ซึ่งก็คือลำดับของ opcode เช่น ADD, SSTORE, CALL สิ่งที่เก็บไว้บน chain คือ bytecode นี้ ไม่ใช่โค้ด Solidity
  • เป็น stack machine ข้อมูลแต่ละช่องมีขนาด 256 บิต และ stack ลึกได้ไม่เกิน 1,024 ช่อง
  • มีพื้นที่เก็บข้อมูลหลายแบบ ได้แก่ storage อยู่ถาวรบน chain และแพงที่สุด memory ใช้ชั่วคราวระหว่างการเรียกหนึ่งครั้ง และ calldata คือข้อมูลที่ส่งมากับการเรียก รายละเอียดอยู่ในบทที่ 6
  • เป็น Turing-complete จึงเขียนลูปได้ แต่ก็มีปัญหาลูปไม่รู้จบตามมา Ethereum แก้ปัญหานี้ด้วย gas (หัวข้อ 5.5 และบทที่ 7)

ทำไม contract จึงทำบางอย่างไม่ได้

ทุกโหนดต้องได้ผลตรงกัน ข้อกำหนดนี้ทำให้ contract ทำบางอย่างไม่ได้

  • contract เรียกเว็บไซต์หรือ API ภายนอกไม่ได้ เพราะแต่ละโหนดเรียกในเวลาต่างกันและอาจได้คำตอบต่างกัน
  • contract สุ่มตัวเลขแบบปลอดภัยไม่ได้ เพราะทุกโหนดต้องสุ่มได้ค่าเดียวกัน ค่าตั้งต้น (seed) จึงต้องมาจากข้อมูลบน chain เช่น ข้อมูลของบล็อก ผู้เสนอบล็อกและผู้เล่นเห็นข้อมูลนี้ได้ก่อน และทำนายผลได้
  • EVM ไม่มีเลขทศนิยมแบบ floating point เพราะการปัดเศษอาจให้ผลต่างกันในแต่ละเครื่อง

เมื่อ contract ดึงข้อมูลภายนอกเองไม่ได้ ข้อมูลเหล่านั้นต้องมีคนส่งเข้ามาผ่านธุรกรรม และนี่คือที่มาของ Oracle ในบทที่ 13

ประเด็นที่มักออกสอบ Contract ที่ deploy แล้ว แก้โค้ดไม่ได้ (immutable) ข้อดีคือผู้ใช้มั่นใจได้ว่าไม่มีใครเปลี่ยนกติกาภายหลัง ข้อเสียคือถ้าโค้ดมีช่องโหว่ก็แก้ไม่ได้ โครงการที่ต้องการอัปเกรดได้จึงใช้รูปแบบ proxy ผู้ใช้เรียก contract ตัวกลาง (proxy) ซึ่งส่งต่อการเรียกไปยัง contract ที่เก็บ logic ไว้ โค้ดของแต่ละ contract ยังแก้ไม่ได้ แต่ผู้ดูแลเปลี่ยน address ของ contract ปลายทางได้ ผู้ใช้จึงต้องเชื่อใจผู้ที่มีสิทธิ์อัปเกรดแทน

5.4ธุรกรรมและบล็อกของ Ethereum: ฟิลด์ของธุรกรรม, state root และการเลือกสายโซ่

หัวข้อ 5.1–5.3 อธิบายว่า Ethereum เก็บสถานะอะไรและรันโปรแกรมอย่างไร หัวข้อนี้ตอบคำถามที่บทที่ 0–3 เคยตอบให้ Bitcoin มาแล้ว คือธุรกรรมมีข้อมูลอะไร บล็อกผูกกันอย่างไร และเมื่อเครือข่ายแตกเป็นสองสาย โหนดจะเชื่อสายไหน คำตอบหลายข้อต่างจาก Bitcoin และข้อสอบมักถามความแตกต่างนี้

ทำไมธุรกรรมต้องมีฟิลด์เหล่านี้

ธุรกรรมของ Ethereum ต้องบอกได้ครบว่าใครสั่ง สั่งให้ใครทำอะไร ยอมจ่ายเท่าใด และต้องใช้ซ้ำไม่ได้ ฟิลด์แต่ละตัวตอบโจทย์ข้อหนึ่ง

ฟิลด์เนื้อหามีไว้เพื่อ
nonceลำดับธุรกรรมของผู้ส่งกัน replay attack ภายในเครือข่ายเดียวกัน และกำหนดลำดับ (หัวข้อ 5.1)
chainIdหมายเลขเครือข่าย เช่น 1 คือ mainnetกันการนำธุรกรรมไปส่งซ้ำบนเครือข่ายอื่น (EIP-155)
toaddress ผู้รับ หรือ contract ที่ต้องการเรียกถ้าว่าง หมายถึงการสร้าง contract ใหม่
valueจำนวน ETH ที่ส่ง (หน่วย wei)โอนเงิน หรือส่งเงินเข้าฟังก์ชัน payable
dataข้อมูลสำหรับ contractระบุฟังก์ชันและพารามิเตอร์ที่ต้องการเรียก หรือ bytecode ของ contract ที่จะสร้าง
gasLimit, maxFeePerGas, maxPriorityFeePerGasเพดาน gas และราคาจำกัดค่าใช้จ่ายสูงสุดที่ผู้ส่งยอมจ่าย (หัวข้อ 5.5)
ลายเซ็น (yParity, r, s)ลายเซ็น ECDSA ของผู้ส่ง (ธุรกรรมแบบ legacy ใช้ v แทน yParity)พิสูจน์ว่าเจ้าของ private key อนุญาตธุรกรรมนี้

ธุรกรรม ไม่มีฟิลด์ from เพราะเครือข่ายคำนวณ address ของผู้ส่งกลับจากลายเซ็นได้เอง ถ้าใส่ฟิลด์ from ไว้ โหนดก็ยังต้องตรวจว่าตรงกับลายเซ็นอยู่ดี ฟิลด์นี้จึงซ้ำซ้อนและเปลืองพื้นที่ ค่า tx.origin ใน Solidity มาจากการคำนวณนี้ ในการเรียกชั้นแรกจาก EOA ค่า msg.sender ก็เป็น address เดียวกัน แต่ถ้า contract A เรียก contract B ต่อ ค่า msg.sender ใน B จะเป็น address ของ A (หัวข้อ 5.6)

chainId มาจากเหตุการณ์จริง ในปี 2016 Ethereum แยกเป็นสอง chain คือ Ethereum และ Ethereum Classic (บทที่ 9) บัญชีและ nonce ของทั้งสอง chain เหมือนกันทุกประการ ธุรกรรมที่ลงลายเซ็นบน chain หนึ่งจึงนำไปส่งบนอีก chain ได้ และผู้ใช้หลายคนเสียเงินบน chain ที่ไม่ได้ตั้งใจโอน EIP-155 แก้โดยนำ chainId ไปรวมไว้ในข้อมูลที่ลงลายเซ็น ลายเซ็นสำหรับ chain หนึ่งจึงใช้กับอีก chain ไม่ได้

data เรียกฟังก์ชันได้อย่างไร

contract หนึ่งมีหลายฟังก์ชัน ธุรกรรมจึงต้องระบุว่าต้องการเรียกฟังก์ชันใด แต่ถ้าส่งชื่อฟังก์ชันเป็นข้อความยาว ๆ จะเปลือง gas Ethereum จึงใช้ function selector แทนชื่อ selector คือ 4 ไบต์แรกของค่าแฮช Keccak-256 ของ function signature คือชื่อฟังก์ชันตามด้วยชนิดพารามิเตอร์ เช่น transfer(address,uint256) (คำนี้ไม่เกี่ยวกับลายเซ็นดิจิทัลของธุรกรรม) data จะเริ่มด้วย selector แล้วตามด้วยพารามิเตอร์ที่เข้ารหัส (encode) ตามรูปแบบ ABI (Application Binary Interface) ตัวอย่างที่พบบ่อยที่สุดคือฟังก์ชันโอนเหรียญ ERC-20

วงจรชีวิตของธุรกรรม (transaction lifecycle)

  1. wallet เช่น MetaMask สร้างธุรกรรม ลงลายเซ็นด้วย private key แล้วส่งให้โหนด
  2. โหนดตรวจลายเซ็นและ nonce และตรวจว่ายอดเงินพอจ่ายค่า gas สูงสุด (gasLimit × maxFeePerGas) รวมกับจำนวน ETH ที่ส่ง (value) จากนั้นกระจายธุรกรรมต่อให้โหนดอื่น ธุรกรรมรออยู่ใน mempool เหมือนใน Bitcoin
  3. เวลาของ Ethereum แบ่งเป็นช่วงละ 12 วินาที เรียกว่า slot ในแต่ละ slot เครือข่ายเลือก validator หนึ่งรายเป็นผู้เสนอบล็อก (proposer) validator คือผู้ที่วาง ETH เป็นเงินค้ำประกัน (stake) เพื่อได้สิทธิ์สร้างและรับรองบล็อก proposer เลือกธุรกรรมจาก mempool โดยมักเรียงตาม priority fee แล้วรันทีละรายการบน EVM
  4. proposer ประกาศบล็อกพร้อม state root ใหม่ โหนดอื่นรันธุรกรรมทั้งหมดซ้ำเอง ถ้าได้ state root ไม่ตรงกับที่ประกาศ โหนดจะปฏิเสธบล็อกนั้น
  5. validator รายอื่นส่งคะแนนรับรอง (attestation) ให้บล็อก ช่วงเวลา 32 slot (6.4 นาที) เรียกว่าหนึ่ง epoch เมื่อผ่านไปราว 2 epoch หรือ 12.8 นาที บล็อกจะ finalized

ทำไม header ของ Ethereum จึงมี root หลักสามค่า

header ของ Bitcoin ผูก (commit) กับข้อมูลชุดเดียว คือธุรกรรม ผ่าน Merkle root (บทที่ 3) SPV จึงพิสูจน์ได้ว่าธุรกรรมอยู่ในบล็อก แต่พิสูจน์ยอดเงินคงเหลือไม่ได้ เพราะ header ไม่มีค่าใดผูกกับยอดเงิน ใน Ethereum ผู้ใช้ต้องการถามได้มากกว่านั้น เช่น ตอนนี้บัญชีนี้มีเงินเท่าใด หรือ contract เก็บค่าอะไรไว้ header จึงผูกกับข้อมูลสามชุดผ่าน root สามค่า ได้แก่ transactionsRoot, stateRoot และ receiptsRoot ตารางด้านล่างใส่ parentHash ไว้ด้วยเพื่อเทียบกับ Bitcoin

ฟิลด์ใน headerผูกกับใช้พิสูจน์
parentHashheader ของบล็อกก่อนหน้าลำดับของบล็อก เหมือน hash chain ในบทที่ 0
transactionsRootธุรกรรมทั้งหมดในบล็อกธุรกรรมอยู่ในบล็อกนี้ เทียบเท่า Merkle root ของ Bitcoin
stateRootworld state ทั้งหมดหลังรันบล็อกนี้ยอดเงิน nonce code และค่าใน storage ของบัญชีใดก็ได้
receiptsRootผลการรันของแต่ละธุรกรรม รวมถึง event logธุรกรรมสำเร็จหรือไม่ และเกิด event ใดบ้าง

ทั้งสามค่าเป็น root ของ Merkle Patricia Trie โครงสร้างนี้ต่อยอดจาก Merkle tree ให้ค้นหาด้วย key ได้ เช่น ค้นด้วย address แล้วได้ข้อมูลบัญชี หลักการยังเหมือนบทที่ 3 คือ ถ้าข้อมูลส่วนใดเปลี่ยน root ก็เปลี่ยนตาม และพิสูจน์ข้อมูลหนึ่งรายการได้ด้วยค่าแฮชตามเส้นทางขึ้นไปถึง root

header รุ่นปัจจุบันมี root เพิ่มขึ้นอีก เช่น withdrawalsRoot ที่เพิ่มในการอัปเกรด Shanghai (2023) สำหรับรายการถอน stake ค่าเหล่านี้อยู่นอกเนื้อหาของบทนี้ root หลักที่ใช้พิสูจน์ธุรกรรม สถานะ และผลการรันยังเป็นสามค่าข้างต้น

เมื่อเกิด fork โหนดเชื่อสายไหน

หัวข้อ 2.3 แสดงว่า Bitcoin เลือกสายที่มีงานสะสมมากที่สุด กฎนี้ใช้ได้เพราะงานปลอมไม่ได้ ผู้ที่ต้องการสร้างสายแซงต้องลงพลังประมวลผลจริง Ethereum มีสองยุค และแต่ละยุคมีเหตุผลให้ต้องปรับกฎนี้

  • ยุค PoW (2015–2022): ยังเลือกสายที่มีความยากสะสม (total difficulty) สูงที่สุดเหมือน Bitcoin แต่บล็อกเกิดทุก 13–15 วินาที จึงมีบล็อกเกิดพร้อมกันบ่อย และกลายเป็น stale block บ่อยกว่า Bitcoin มาก ผู้ที่เสียเปรียบคือผู้ขุดรายเล็ก pool ใหญ่รู้บล็อกที่ตัวเองเพิ่งขุดได้ทันทีและขุดต่อจากบล็อกนั้นได้เลย ส่วนผู้ขุดรายเล็กต้องรอให้บล็อกใหม่กระจายมาถึง ระหว่างรอก็อาจขุดบนบล็อกที่กำลังจะกลายเป็น stale block ถ้าปล่อยไว้ ผู้ขุดจะย้ายไปรวมกับ pool ใหญ่และการขุดจะรวมศูนย์ Ethereum จึงให้บล็อกถัดไปอ้างถึง stale block ในฐานะ uncle (ommer) และให้รางวัลบางส่วนแก่ผู้ขุด uncle แนวคิดนี้มาจากงานวิจัย GHOST
  • ยุค PoS (ตั้งแต่ The Merge กันยายน 2022): เมื่อการสร้างบล็อกไม่ต้องลงงานแล้วและแทบไม่มีต้นทุน ความยาวของสายก็ไม่สะท้อนต้นทุนที่ผู้สร้างลงไปเหมือนใน PoW Ethereum จึงเปลี่ยนไปนับ การรับรอง (attestation) ของ validator แทน กฎ LMD-GHOST เลือกกิ่งที่ได้ attestation ล่าสุดจาก validator หนักกว่า โดยถ่วงน้ำหนักตามจำนวน stake ของแต่ละราย ส่วน Casper FFG กำหนดจุดที่ย้อนกลับไม่ได้ validator ไม่ได้ลงคะแนน FFG ให้ทุกบล็อก แต่ลงคะแนนที่ checkpoint คือบล็อกแรกของแต่ละ epoch เงื่อนไขคือ validator ที่ถือ stake รวมกันอย่างน้อยสองในสามของทั้งระบบต้องรับรอง checkpoint นั้น เมื่อ checkpoint ถัดไปผ่านเงื่อนไขเดียวกันต่อกันทันที checkpoint แรกจะ finalized โหนดจะไม่ย้อนกลับไปก่อนจุดนั้นอีก ถ้าจะย้อนบล็อกที่ finalized แล้ว validator ที่ถือ stake รวมกันอย่างน้อยหนึ่งในสามต้องลงคะแนนขัดกันเอง โปรโตคอลจะลงโทษ validator เหล่านั้นด้วย slashing คือยึด stake ส่วนหนึ่ง รายละเอียดอยู่ในบทที่ 8

ทำไมต้องมี gas

เมื่อใครก็ deploy โปรแกรมที่มีลูปได้ ผู้ไม่หวังดีก็ส่งโปรแกรมที่วนไม่รู้จบมาทำให้ทุกโหนดทั่วโลกค้างได้ และไม่มีวิธีตรวจล่วงหน้าว่าโปรแกรมใดจะหยุดทำงาน (Halting problem ในบทที่ 7) Ethereum แก้ปัญหานี้ด้วยการ คิดราคาทุกขั้นของการคำนวณ opcode แต่ละตัวมีราคาเป็นหน่วย gas ผู้ส่งธุรกรรมกำหนดเพดาน gas ไว้ล่วงหน้า และจ่ายตามจำนวน gas ที่ใช้จริง โปรแกรมที่วนไม่รู้จบจะใช้ gas จนหมดเพดานแล้วหยุด ผู้ส่งเสียค่าธรรมเนียมตามที่ใช้ไป การโจมตีจึงมีต้นทุนจริง ค่าธรรมเนียมนี้ยังชดเชยทรัพยากรที่โหนดต้องใช้ด้วย

คำศัพท์ของ gas

  • Gas limit ของธุรกรรม: จำนวน gas สูงสุดที่ผู้ส่งยอมให้ใช้ ถ้าใช้ไม่หมด ผู้ส่งไม่ต้องจ่ายส่วนที่เหลือ ถ้าใช้หมดก่อนทำงานเสร็จ จะเกิด Out of gas และ EVM ย้อนสถานะทั้งหมดกลับ (revert) แต่ไม่คืนค่า gas ที่ใช้ไปแล้ว เพราะทุกโหนดได้รันคำสั่งเหล่านั้นไปแล้วจริง ถ้าคืนเงิน ผู้โจมตีก็ส่งลูปไม่รู้จบมาได้ฟรี (บทที่ 7)
  • Block gas limit: เพดานรวมของ gas ในหนึ่งบล็อก มีไว้จำกัดงานต่อบล็อก โหนดทั่วไปจึงรันและเก็บข้อมูลได้ทันเวลา validator ปรับเพดานนี้ขึ้นลงได้ทีละเล็กน้อย ค่าเป้าหมาย (target) อยู่ที่ครึ่งหนึ่งของเพดาน เมื่อความต้องการสูงขึ้น บล็อกรับธุรกรรมเกิน target ได้ชั่วคราว และส่วนที่เกินนี้เป็นสัญญาณให้ base fee ปรับขึ้น
  • Base fee: ราคาขั้นต่ำต่อ gas ที่โปรโตคอลคำนวณเองในแต่ละบล็อก โปรโตคอลจะ เผาทิ้ง (burn) ส่วนนี้
  • Priority fee (tip): ราคาต่อ gas ที่ผู้ส่งจ่ายเพิ่มให้ validator เพื่อจูงใจให้ validator รวมธุรกรรมของผู้ส่งเข้าบล็อกก่อนธุรกรรมอื่น
  • Max fee per gas: ราคาสูงสุดต่อ gas ที่ผู้ส่งยอมจ่าย ผู้ส่งไม่ต้องจ่ายส่วนที่เกินจาก base fee บวก priority fee

ทำไม base fee จึงปรับเองและต้องเผาทิ้ง

ก่อนการอัปเกรด London (สิงหาคม 2021) ผู้ใช้ต้องประมูลราคา gas แข่งกัน (first-price auction) และเดาไม่ได้ว่าต้องเสนอเท่าใดจึงจะได้เข้าบล็อก ผู้ใช้จึงมักเสนอเผื่อไว้และจ่ายเกินจำเป็น EIP-1559 เปลี่ยนให้โปรโตคอลกำหนด base fee เอง ถ้าบล็อกก่อนหน้าใช้ gas เกินเป้าหมาย base fee เพิ่มขึ้น ถ้าต่ำกว่าเป้าหมาย base fee ลดลง base fee ปรับได้ไม่เกิน 12.5% ต่อบล็อก ผู้ใช้จึงคาดการณ์ค่าธรรมเนียมได้ ส่วนเหตุผลที่ต้องเผา base fee แทนที่จะให้ validator คือ ถ้า validator ได้ส่วนนี้ ก็จะมีแรงจูงใจใส่ธุรกรรมปลอมของตัวเองให้บล็อกเต็ม เพื่อดัน base fee ให้สูงขึ้น

5.6พื้นฐานภาษา Solidity: ชนิดข้อมูล, visibility, modifier และ event

Solidity เป็นภาษาหลักสำหรับเขียน smart contract บน EVM ไวยากรณ์ (syntax) คล้าย JavaScript และ C++ ต่างกันตรงที่ต้องระบุชนิดข้อมูลของตัวแปรทุกตัว และทุกคำสั่งที่รันมีค่าใช้จ่ายเป็น gas ตัวอย่างต่อไปนี้คือ TipJar กล่องรับทิปที่รวมองค์ประกอบหลักของภาษาไว้ ส่วนบทที่ 6 จะเขียน Counter contract ทีละบรรทัด

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;                       // ใช้คอมไพเลอร์รุ่น 0.8.20 ขึ้นไป (ไม่ถึง 0.9)

contract TipJar {
    address public owner;                      // state variable: เก็บใน storage ถาวร
    uint256 public total;                      // ยอดทิปสะสม (หน่วย wei)
    mapping(address => uint256) public tipsBy; // ยอดทิปของแต่ละ address

    event Tipped(address indexed from, uint256 amount, string message);

    modifier onlyOwner() {
        require(msg.sender == owner, "not owner");
        _;                                     // คอมไพเลอร์แทรกโค้ดของฟังก์ชันตรงนี้
    }

    constructor() {
        owner = msg.sender;                    // ทำงานครั้งเดียวตอน deploy
    }

    function tip(string calldata message) external payable {
        require(msg.value > 0, "send some ETH");
        tipsBy[msg.sender] += msg.value;
        total += msg.value;
        emit Tipped(msg.sender, msg.value, message);
    }

    function withdraw() external onlyOwner {
        (bool ok, ) = payable(owner).call{value: address(this).balance}("");
        require(ok, "transfer failed");
    }

    function toGwei(uint256 weiAmount) public pure returns (uint256) {
        return weiAmount / 1 gwei;
    }
}

Visibility: ใครเรียกได้

ฟังก์ชันบางตัวตั้งใจให้ใช้ภายใน contract เท่านั้น เช่น ฟังก์ชันที่แก้ยอดเงิน ถ้าเปิดให้คนนอกเรียกได้ ใครก็ส่งธุรกรรมมาเรียกฟังก์ชันนั้นตรง ๆ และแก้ยอดเงินได้ Solidity รุ่นเก่าถือว่าฟังก์ชันที่ไม่ระบุ visibility เป็น public และเคยทำให้เกิดช่องโหว่จริง ตั้งแต่รุ่น 0.5 Solidity จึงบังคับให้ระบุ visibility ของทุกฟังก์ชัน

คำเรียกจากภายนอกเรียกภายใน contractcontract ที่สืบทอด
publicได้ได้ได้
external (ใช้กับฟังก์ชันเท่านั้น)ได้ไม่ได้โดยตรงไม่ได้โดยตรง
internalไม่ได้ได้ได้
privateไม่ได้ได้ไม่ได้

external ใช้กับฟังก์ชันที่มีไว้ให้คนนอกเรียกเท่านั้น เช่น tip ในตัวอย่าง ฟังก์ชันนี้รับข้อความเป็น calldata จึงอ่านจากข้อมูลที่ส่งมาได้โดยตรง ไม่ต้องคัดลอกลง memory และประหยัด gas

state variable ที่ประกาศเป็น public จะได้ฟังก์ชันสำหรับอ่านค่า (getter) โดยอัตโนมัติ เช่น owner() และ tipsBy(address) ในตัวอย่าง

private ไม่ได้แปลว่าเป็นความลับ private ห้ามเพียง contract อื่นเรียกใช้ แต่ข้อมูลทุกอย่างบน blockchain เปิดให้ทุกคนอ่านได้ ใครก็อ่านค่าใน storage ของ contract ได้โดยตรงจากโหนด จึงห้ามเก็บรหัสผ่านหรือคำตอบของเกมไว้ในตัวแปร private

State mutability: ฟังก์ชันแก้สถานะหรือไม่

  • (ไม่ระบุ) อ่านและแก้สถานะได้ การเรียกต้องส่งธุรกรรมและเสีย gas
  • view อ่านสถานะได้แต่แก้ไม่ได้
  • pure ไม่อ่านและไม่แก้สถานะ คำนวณจากพารามิเตอร์อย่างเดียว เช่น toGwei
  • payable รับ ETH มากับการเรียกได้ ถ้ามีคนส่ง ETH มากับการเรียกฟังก์ชันที่ไม่ได้ระบุคำนี้ ฟังก์ชันนั้นจะ revert เพื่อกันเงินเข้าผิดที่

การเรียก view และ pure จากภายนอกไม่แก้สถานะ เครือข่ายจึงไม่ต้องตกลงผลร่วมกัน โหนดที่เราเชื่อมต่ออยู่รันฟังก์ชันให้ในเครื่องแล้วตอบกลับได้เลย ไม่ต้องส่งธุรกรรมและไม่เสีย gas รายละเอียดอยู่ในบทที่ 6

ตัวแปรพิเศษที่มากับการเรียก

msg.sender คือ address ที่เรียกฟังก์ชันนี้โดยตรง msg.value คือจำนวน wei ที่ส่งมา และ block.timestamp คือเวลาของบล็อก contract ใช้ตัวแปรเหล่านี้เพื่อรู้ว่าใครเรียกและส่งอะไรมา โดยไม่ต้องตรวจลายเซ็นเอง เพราะเครือข่ายตรวจลายเซ็นของธุรกรรมให้แล้ว

Modifier: ทำไมต้องมี

ฟังก์ชันหลายตัวมักต้องตรวจเงื่อนไขเดียวกัน เช่น ต้องเป็นเจ้าของเท่านั้น ถ้าเขียน require ซ้ำทุกฟังก์ชัน วันหนึ่งนักพัฒนาอาจลืมใส่ในบางฟังก์ชัน และใน smart contract ความผิดพลาดแบบนี้ทำให้เงินถูกขโมยได้ modifier รวมเงื่อนไขไว้ที่เดียว แล้วนำไปติดกับฟังก์ชันใดก็ได้ เครื่องหมาย _; คือตำแหน่งที่คอมไพเลอร์แทรกโค้ดของฟังก์ชันเข้าไป ในตัวอย่าง withdraw จึงตรวจ msg.sender == owner ก่อนทำงานเสมอ

Event: ทำไมต้องมี

หน้าเว็บของแอปต้องการรู้ว่ามีใครให้ทิปบ้าง แต่ storage แพงและไม่เหมาะกับการเก็บประวัติยาว ๆ event บันทึกข้อมูลลงใน log ของธุรกรรมแทน log เก็บอยู่ใน receipt (ผูกกับ receiptsRoot ในหัวข้อ 5.4) ไม่ได้อยู่ใน world state โหนดไม่ต้องเตรียม log ไว้ให้ contract อ่านระหว่างรัน ค่า gas ของ log จึงถูกกว่า storage มาก แอปภายนอกติดตามและค้นหา log ได้ และใช้พารามิเตอร์ที่ระบุ indexed เป็นตัวกรอง เช่น ค้นทิปทั้งหมดจาก address หนึ่ง ข้อจำกัดที่มาจากเหตุผลเดียวกันคือ contract อ่าน log ไม่ได้ event จึงมีไว้สื่อสารกับโลกภายนอกเท่านั้น

แบบฝึกหัด

1. ทำไมบัญชีใน Ethereum ต้องมี nonce ทั้งที่ Bitcoin ไม่ต้องมีตัวนับในลักษณะนี้

ดูเฉลย
ใน Bitcoin ธุรกรรมใช้ UTXO จนหมด ธุรกรรมเดิมจึงส่งซ้ำไม่ได้เพราะ UTXO นั้นไม่อยู่แล้ว แต่ใน Account model ธุรกรรมแก้เพียงยอดเงิน ถ้าไม่มี nonce ผู้อื่นก็นำธุรกรรมที่ลงลายเซ็นแล้วไปส่งซ้ำได้ (replay attack) nonce บังคับให้แต่ละธุรกรรมใช้ได้ครั้งเดียวและเรียงตามลำดับ

2. ข้อใดที่ Contract account ทำไม่ได้

  1. ก. ถือ ETH
  2. ข. เก็บข้อมูลใน storage
  3. ค. เริ่มธุรกรรมด้วยตัวเอง
  4. ง. เรียก contract อื่น
ดูเฉลย
ค. contract ไม่มี private key จึงลงลายเซ็นธุรกรรมไม่ได้ และทำงานเมื่อมีผู้เรียกเท่านั้น แต่ระหว่างทำงานก็เรียก contract อื่นต่อได้ (ข้อ ง)

3. ธุรกรรมใช้ gas 50,000 ขณะที่ base fee 20 Gwei ผู้ส่งตั้ง priority fee 1.5 Gwei และ max fee 30 Gwei ค่าธรรมเนียมรวมเป็นเท่าใด เผาไปเท่าใด และ validator ได้เท่าใด

ดูเฉลย
ราคาต่อ gas จริง = 20 + 1.5 = 21.5 Gwei (ไม่เกิน 30) ค่าธรรมเนียมรวม = 50,000 × 21.5 = 1,075,000 Gwei = 0.001075 ETH เผา 50,000 × 20 = 1,000,000 Gwei (0.001 ETH) validator ได้ 50,000 × 1.5 = 75,000 Gwei (0.000075 ETH)

  1. ก. 10-6 ETH
  2. ข. 10-9 ETH
  3. ค. 10-12 ETH
  4. ง. 10-18 ETH
ดูเฉลย
ข. 1 Gwei = 109 wei และ 1 ETH = 1018 wei ดังนั้น 1 Gwei = 10-9 ETH ข้อ ง คือค่าของ 1 wei

5. นักพัฒนาเก็บคำตอบของเกมทายคำไว้ในตัวแปร string private answer ผู้เล่นจะรู้คำตอบได้หรือไม่

ดูเฉลย
ได้ private ห้ามเพียง contract อื่นเรียกใช้ แต่ข้อมูลใน storage เปิดให้ทุกคนอ่านได้ผ่านโหนด และค่าที่ส่งมาตอน deploy ก็อยู่ในธุรกรรมที่ทุกคนเห็น

6. ทำไม smart contract จึงเรียก API ภายนอกเพื่อดึงราคาหุ้นโดยตรงไม่ได้

ดูเฉลย
ทุกโหนดต้องรัน contract แล้วได้ผลตรงกัน แต่แต่ละโหนดเรียก API ในเวลาต่างกันและอาจได้ค่าต่างกัน หรือ API อาจล่มระหว่างนั้น ถ้าเป็นเช่นนั้น เครือข่ายจะตกลงเรื่องสถานะกันไม่ได้ ข้อมูลภายนอกจึงต้องส่งเข้ามาด้วยธุรกรรมผ่าน Oracle (บทที่ 13)

7. ทำไม EIP-1559 จึงเผา base fee แทนที่จะมอบให้ validator

ดูเฉลย
ถ้า validator ได้ base fee ก็จะมีแรงจูงใจใส่ธุรกรรมปลอมของตัวเองให้บล็อกเต็ม เพื่อดัน base fee ให้สูงขึ้นและเก็บเงินจากผู้ใช้มากขึ้น เมื่อเผา base fee ทิ้ง การปั่นแบบนี้ก็ไม่มีประโยชน์ ส่วน priority fee ยังเป็นของ validator เพื่อจูงใจให้รวมธุรกรรมเข้าบล็อก

8. ใน modifier ด้านล่าง เครื่องหมาย _; มีความหมายว่าอะไร และถ้าลบบรรทัดนั้นทิ้งจะเกิดอะไรขึ้น

modifier onlyOwner() {
    require(msg.sender == owner, "not owner");
    _;
}
ดูเฉลย
_; คือตำแหน่งที่คอมไพเลอร์แทรกโค้ดของฟังก์ชันที่ใช้ modifier นี้ ถ้าลบบรรทัดนั้นทิ้ง ฟังก์ชันจะตรวจ require แล้วจบไปโดยไม่ได้ทำงานส่วนของตัวเองเลย

9. ทำไม Ethereum ยุค PoS จึงไม่ใช้กฎ "เชื่อสายที่ยาวที่สุด" แบบ Bitcoin

ดูเฉลย
กฎของ Bitcoin ใช้ได้เพราะแต่ละบล็อกต้องลงงานจริง ความยาวจึงปลอมไม่ได้ ใน PoS การสร้างบล็อกไม่ต้องลงงานแล้วและแทบไม่มีต้นทุน ความยาวของสายจึงไม่สะท้อนต้นทุนที่ผู้สร้างลงไปเหมือนใน PoW Ethereum เลือกกิ่งตามน้ำหนัก attestation ของ validator ซึ่งผูกกับ stake (LMD-GHOST) และใช้ Casper FFG กำหนดจุด finalized ผู้ที่จะย้อนกลับไปก่อนจุดนั้นต้องยอมให้ validator ที่ถือ stake รวมกันอย่างน้อยหนึ่งในสามโดน slashing

10. ธุรกรรมของ Ethereum มีทั้ง nonce และ chainId ทั้งสองป้องกันการโจมตีต่างกันอย่างไร

ดูเฉลย
nonce ป้องกันการนำธุรกรรมเดิมไปส่งซ้ำ บนเครือข่ายเดียวกัน เพราะใช้ได้เฉพาะเมื่อตรงกับลำดับปัจจุบันของบัญชี chainId ป้องกันการนำธุรกรรมไปส่งซ้ำ บนเครือข่ายอื่น ที่มีบัญชีและ nonce เหมือนกัน เช่น Ethereum กับ Ethereum Classic หลังการแยก chain ในปี 2016
