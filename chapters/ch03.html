เริ่มจากโจทย์: บัญชีที่ทุกคนต้องเก็บทั้งเล่ม

ระบบในบทที่ 1 และ 2 ปลอดภัยได้เพราะทุกโหนดตรวจทุกอย่างด้วยตัวเอง ก่อนรับธุรกรรมใหม่ โหนดต้องรู้ว่าเหรียญที่นำมาจ่ายมีอยู่จริงและยังไม่มีใครใช้ไป (unspent) จึงต้องมีประวัติย้อนหลังทั้งหมดอยู่ในมือ บัญชี (ledger) นี้มีแต่เพิ่มขึ้น ไม่มีวันลดลง ปัจจุบันมีขนาดหลายร้อยกิกะไบต์ ภาระนี้ตกอยู่กับคนสองกลุ่ม

ผู้ที่รันโหนด: พื้นที่ดิสก์โตไม่หยุด

ถ้าการรันโหนดแพงขึ้นทุกปี สุดท้ายจะเหลือเพียงบริษัทใหญ่ไม่กี่รายที่รับภาระได้ ผู้ใช้ทั่วไปต้องเชื่อข้อมูลจากบริษัทเหล่านั้น เท่ากับกลับไปพึ่งตัวกลาง (trusted third party) ที่ Bitcoin ตั้งใจเลิกใช้ ระบบจึงต้องมีวิธี ลบข้อมูลที่ไม่จำเป็นทิ้ง

ผู้ใช้ทั่วไป: ต้องการรู้ว่าได้รับเงินจริง

ร้านกาแฟที่รับชำระด้วย Bitcoin ผ่านโทรศัพท์มือถือดาวน์โหลดข้อมูลหลายร้อยกิกะไบต์ไม่ไหว ทางเลือกที่ง่ายที่สุดคือถามเซิร์ฟเวอร์ของบริษัทหนึ่งว่าเงินเข้าแล้วหรือยัง แต่ร้านต้องเชื่อคำตอบนั้นโดยตรวจเองไม่ได้ ระบบจึงต้องมีวิธี ตรวจด้วยตัวเองโดยใช้ข้อมูลเพียงเล็กน้อย

ข้อจำกัดที่ห้ามละเมิด

ทั้งสองวิธีต้องไม่ทำให้หลักฐานเดิมใช้ไม่ได้ แม้ลบข้อมูลบางส่วนไปแล้ว ค่าแฮชของบล็อกต้องคำนวณได้ตรงเหมือนเดิม และถ้ามีใครแก้ธุรกรรมใดในบล็อก Proof-of-Work ของบล็อกนั้นต้องใช้ไม่ได้ทันที แนวคิดที่ตอบโจทย์นี้คือ แยกข้อมูลขนาดเล็กที่ทุกคนเก็บไว้ตลอด (block header) ออกจากข้อมูลก้อนใหญ่ที่ลบหรือไม่ดาวน์โหลดก็ได้ (ธุรกรรม) แล้วใส่ค่าแฮชของธุรกรรมไว้ใน header เพื่อผูกสองส่วนนี้เข้าด้วยกัน

ทุกคนรู้ว่าส่วนที่ต้องเก็บไว้ตลอดมีขนาดเท่าใดการคำนวณขนาด header3.3
ผู้ใช้บนมือถือตรวจว่าธุรกรรมของตนอยู่ในบล็อกโดยไม่ต้องเก็บทุกบล็อกSPV และ Merkle proof3.4

3.1Merkle Tree และ Merkle Root

ทำไมไม่แฮชธุรกรรมทั้งหมดรวดเดียว

วิธีแรกที่นึกถึงคือนำธุรกรรมทั้งบล็อกมาต่อกัน แฮชครั้งเดียว แล้วใส่ค่าแฮช 32 ไบต์นั้นไว้ใน header วิธีนี้ผูกธุรกรรมทุกรายการไว้ได้จริง แต่ใช้กับโจทย์ของบทนี้ไม่ได้ เพราะถ้าจะคำนวณค่าแฮชนั้นซ้ำ ต้องมีธุรกรรม ครบทุกรายการ ผู้ที่ต้องการพิสูจน์ว่ามีธุรกรรมของตนอยู่ในบล็อกต้องดาวน์โหลดทั้งบล็อก และเมื่อลบธุรกรรมใดออกไป ก็จะตรวจไม่ได้อีกว่าธุรกรรมที่เหลือตรงกับค่าแฮชใน header

วิธีผูกธุรกรรมกับ headerขนาดใน headerพิสูจน์ว่ามีธุรกรรมหนึ่งอยู่ในบล็อก ต้องใช้ลบธุรกรรมเก่าได้หรือไม่
ใส่ธุรกรรมทั้งหมดไว้ใน headerเท่ากับทั้งบล็อกทั้งบล็อกไม่ได้
นำธุรกรรมทั้งหมดมาต่อกันแล้วแฮชครั้งเดียว32 ไบต์ธุรกรรมทั้งบล็อก (ราว 1–2 MB)ไม่ได้ เพราะคำนวณค่าแฮชซ้ำไม่ได้
Merkle tree32 ไบต์ค่าแฮชเพียง log2(n) ค่า ปัดขึ้นเป็นจำนวนเต็ม (ที่มาอยู่ท้ายหัวข้อนี้) เช่น 4,000 ธุรกรรม log2 ≈ 11.97 จึงใช้ 12 ค่า รวม 384 ไบต์ได้ โดยเก็บค่าแฮชบนสุดของกิ่งย่อยที่ตัดไว้แทน (หัวข้อ 3.2)

วิธีสร้าง Merkle tree

Merkle tree ตั้งชื่อตาม Ralph Merkle ผู้เสนอโครงสร้างนี้ในปี 1979 การสร้างมีขั้นตอนดังนี้

  1. แฮชธุรกรรมแต่ละรายการ ได้ค่าแฮชชั้นล่างสุด ใน Bitcoin ค่านี้คือ txid ซึ่งคำนวณด้วย SHA-256 สองรอบ
  2. จับคู่ค่าแฮชทีละสองค่าจากซ้ายไปขวา นำมาต่อกันแล้วแฮช ได้ค่าแฮชชั้นถัดขึ้นไป ชั้นใหม่จึงมีจำนวนค่าแฮชเหลือครึ่งหนึ่ง
  3. ทำซ้ำจนเหลือค่าเดียว ค่านี้เรียกว่า Merkle root
  4. ใส่ Merkle root ไว้ใน block header
เมื่อจำนวนค่าแฮชเป็นเลขคี่ ทุกค่าต้องมีคู่จึงจะแฮชขึ้นไปชั้นถัดไปได้ Bitcoin จึงทำสำเนาค่าแฮชตัวสุดท้ายของชั้นนั้นมาเป็นคู่ของตัวเอง เช่น บล็อกที่มี 5 ธุรกรรม ชั้นล่างมี 5 ค่า ค่าที่ 5 จับคู่กับสำเนาของตัวเอง ชั้นถัดไปจึงมี 3 ค่า ชั้นนี้เป็นเลขคี่อีก ค่าที่ 3 จึงจับคู่กับสำเนาของตัวเอง ได้ 2 ค่า แล้วจึงได้ Merkle root

ทำไม Merkle root ต้องอยู่ใน header

Proof-of-Work ในบทที่ 2 คำนวณจาก block header ขนาด 80 ไบต์เท่านั้น ไม่ได้แฮชธุรกรรมโดยตรง Whitepaper ไม่ได้บอกเหตุผลไว้ เหตุผลที่มักอธิบายกันมีสองข้อ ข้อแรก ผู้ขุดต้องเปลี่ยน nonce แล้วแฮชซ้ำจำนวนมหาศาล การแฮชเพียง 80 ไบต์ใช้เวลาน้อยกว่าการแฮชทั้งบล็อกมาก ข้อสอง ผู้ที่มีเพียง header ก็ตรวจ PoW ได้ ข้อนี้เป็นพื้นฐานของ SPV ในหัวข้อ 3.4

แต่ถ้าไม่มีสิ่งใดผูก header กับธุรกรรม ผู้โจมตีจะเปลี่ยนธุรกรรมในบล็อกได้โดยที่ PoW ยังใช้ได้ Merkle root คือค่าที่ผูก header ไว้กับธุรกรรม เมื่อแก้ธุรกรรมใดแม้เพียงไบต์เดียว txid ของธุรกรรมนั้นจะเปลี่ยน ค่าแฮชทุกชั้นที่อยู่เหนือขึ้นไปจะเปลี่ยนตามจนถึง Merkle root เมื่อ Merkle root เปลี่ยน ค่าแฮชของ header ก็เปลี่ยน PoW ที่หามาจึงใช้ไม่ได้ทันที ผู้โจมตีที่แก้ธุรกรรมใดในบล็อกจึงต้องทำ PoW ของบล็อกนั้นใหม่ทั้งหมด

หมายเหตุเรื่อง SegWit ย่อหน้าข้างบนอธิบายตามรูปแบบธุรกรรมใน Whitepaper หลัง SegWit (Segregated Witness, BIP141) ธุรกรรมแยกข้อมูลลายเซ็นไปไว้ในส่วน witness และ txid ไม่นำส่วนนี้มาคิด ถ้าแก้เฉพาะ witness ค่า txid จึงไม่เปลี่ยน แต่ Bitcoin ผูกส่วนนี้ไว้อีกทางหนึ่ง โดยสร้างต้นไม้อีกชุดจาก wtxid (ค่าแฮชที่รวม witness) แล้วใส่ root ของต้นไม้นั้นไว้ในธุรกรรมแรกของบล็อก (coinbase transaction) ค่านี้เรียกว่า witness commitment เมื่อ witness เปลี่ยน coinbase ก็เปลี่ยน และ Merkle root ใน header ก็เปลี่ยนตาม ข้อสรุปเรื่อง PoW จึงยังเหมือนเดิม

เพื่อให้อ่านง่าย ตัวอย่างนี้แฮชข้อความด้วย SHA-256 รอบเดียว และนำค่าแฮชในรูปเลขฐานสิบหกมาต่อกันเป็นข้อความก่อนแฮช ส่วน Bitcoin จริงใช้ SHA-256 สองรอบกับข้อมูลแบบไบต์ แต่โครงสร้างของต้นไม้เหมือนกัน

ประเด็นที่มักออกสอบ Merkle root เป็นค่าแฮชค่าเดียวที่ผูกธุรกรรมทั้งบล็อกไว้กับ header แก้ธุรกรรมใดก็ตาม root จะเปลี่ยน ส่วนการพิสูจน์ว่ามีธุรกรรมหนึ่งอยู่ในบล็อก ใช้ค่าแฮชเพียง log2(n) ค่า เพราะต้นไม้แต่ละชั้นมีจำนวนค่าแฮชลดลงครึ่งหนึ่ง จึงต้องจับคู่ log2(n) ครั้งจนเหลือ root และการจับคู่แต่ละครั้งใช้ค่าแฮชคู่ข้างเพียงค่าเดียว เช่น 8 ธุรกรรมใช้ 3 ค่า และ 1,024 ธุรกรรมใช้ 10 ค่า ถ้า n ไม่ใช่กำลังของ 2 ให้ปัดขึ้น เช่น 4,000 ธุรกรรม log2 ≈ 11.97 จึงใช้ 12 ค่า

3.2การตัดข้อมูลธุรกรรมเก่า (Pruning) โดยไม่กระทบค่าแฮชของบล็อก

ทำไมจึงลบธุรกรรมเก่าได้

เมื่อโหนดตรวจธุรกรรมใหม่ คำถามที่ต้องตอบมีเพียงข้อเดียว คือเหรียญที่นำมาจ่าย ยังไม่มีใครใช้ไป หรือไม่ เหรียญจากธุรกรรมเก่าส่วนใหญ่มีผู้นำไปใช้ต่อแล้ว ธุรกรรมเหล่านั้นจึงไม่จำเป็นต่อคำถามนี้อีก Whitepaper ข้อ 7 จึงเสนอว่า เมื่อธุรกรรมล่าสุดของเหรียญหนึ่งมีบล็อกต่อท้ายมากพอ ก็ลบธุรกรรมที่ใช้ไปแล้วก่อนหน้านั้นทิ้งได้ เพื่อประหยัดพื้นที่ดิสก์ ที่ต้องรอให้มีบล็อกต่อท้ายมากพอก่อน เพราะบล็อกที่เพิ่งเกิดอาจหลุดจากสายที่ยาวที่สุด (longest chain) เมื่อเกิดการแยกสาย (fork) ตามที่อธิบายไว้ในบทที่ 2 ถ้าลบเร็วเกินไปแล้วสายเปลี่ยน โหนดอาจต้องใช้ธุรกรรมที่ลบไปแล้วมาตรวจบล็อกในสายใหม่ แต่ไม่มีข้อมูลนั้นเหลืออยู่

ทำไมลบแล้วค่าแฮชของบล็อกไม่เปลี่ยน

ค่าแฮชของบล็อกคำนวณจาก header เท่านั้น และ header ผูกกับธุรกรรมผ่าน Merkle root ค่าเดียว ลบธุรกรรมไปจึงไม่กระทบค่าแฮชของบล็อก แต่โหนดยังต้องตรวจได้ว่าธุรกรรมที่เหลืออยู่ตรงกับ root ถ้าตรวจไม่ได้ โหนดจะไม่รู้ว่าธุรกรรมที่เก็บไว้ในดิสก์ หรือธุรกรรมที่ส่งให้โหนดอื่น ยังเป็นฉบับเดิมหรือมีใครแก้ไขไปแล้ว

วิธีของ Whitepaper คือ ตัดกิ่งย่อย (subtree) ที่ไม่ต้องการ แล้วเก็บเฉพาะค่าแฮชบนสุดของกิ่งนั้นไว้แทน เช่น เก็บ Hash01 ค่าเดียวแทน Tx0, Tx1, Hash0 และ Hash1 คำว่ากิ่งในหัวข้อนี้หมายถึงส่วนของต้นไม้ที่ตัดออก ต่างจาก Merkle branch ในหัวข้อ 3.4 ซึ่งเป็นชุดค่าแฮชที่ใช้พิสูจน์

หลังตัดกิ่งแล้ว โหนดตรวจได้ดังนี้ เริ่มจากแฮช Tx3 ได้ Hash3 จากนั้นนำ Hash2 ที่เก็บไว้มาต่อกับ Hash3 แล้วแฮชได้ Hash23 สุดท้ายนำ Hash01 ที่เก็บไว้มาต่อกับ Hash23 แล้วแฮชได้ Root Hash ถ้าค่าที่ได้ตรงกับใน header แสดงว่าไม่มีใครแก้ไข Tx3 แม้จะลบธุรกรรมอีกสามรายการไปแล้วก็ตาม

Bitcoin Core จริงไม่ได้ตัดกิ่งแบบนี้ โหมด pruning ของ Bitcoin Core ทำงานต่างจาก Whitepaper โหนดดาวน์โหลดทุกบล็อกตั้งแต่ต้นและตรวจครบทุกกฎ จากนั้นเก็บ header ทุกบล็อก รายการเหรียญที่ยังไม่ได้ใช้ (UTXO set ดูรายละเอียดในบทที่ 4) และบล็อกล่าสุดจำนวนหนึ่ง แล้วลบไฟล์บล็อกเก่าทิ้งทั้งไฟล์ วิธีนี้ทำได้เพราะ UTXO set มีข้อมูลครบสำหรับตรวจธุรกรรมใหม่ โหนดจึงไม่ต้องเก็บค่าแฮชของกิ่งที่ตัดแบบใน Whitepaper ผู้ใช้เปิดโหมดนี้ด้วย prune=550 ในไฟล์ bitcoin.conf โดย 550 MiB เป็นค่าต่ำสุดที่ตั้งได้ โหนดแบบนี้ยังตรวจทุกอย่างเองเหมือน full node แต่ส่งบล็อกเก่าให้โหนดอื่นไม่ได้ ถ้าข้อสอบถามตาม Whitepaper ให้ตอบเรื่องการตัดกิ่งของ Merkle tree

3.3การคำนวณขนาด Block header: 80 ไบต์ต่อบล็อก ประมาณ 4.2 MB ต่อปี

ทำไมต้องคำนวณเรื่องนี้

หลังจากลบธุรกรรมได้แล้ว สิ่งที่ทุกคนยังต้องเก็บไว้ตลอดคือ block header ของทุกบล็อก เพราะ header คือสายโซ่ของ PoW ที่โหนดใช้ตัดสินว่าสายใดเป็นสายที่ยาวที่สุด (longest chain) ถ้าส่วนนี้ยังโตเร็วเกินไป ปัญหาในหัวข้อเริ่มต้นก็ยังแก้ไม่ได้ Satoshi จึงคำนวณให้เห็นว่าส่วนที่ต้องเก็บไว้ตลอดมีขนาดเล็กเพียงใด ตัวเลขนี้ยังเป็นพื้นฐานของ SPV ในหัวข้อ 3.4 ด้วย

3.4Simplified Payment Verification (SPV) และ Merkle proof

ทำไมต้องมีวิธีตรวจแบบย่อ

กลับไปที่ร้านกาแฟในหัวข้อเริ่มต้น ร้านมีทางเลือกสองทาง ทางแรกคือรัน full node ซึ่งต้องเก็บข้อมูลหลายร้อยกิกะไบต์ ทางที่สองคือเชื่อคำตอบของเซิร์ฟเวอร์รายเดียว SPV เป็นทางเลือกที่สาม ร้านไม่ต้องเก็บทุกบล็อก และไม่ต้องเชื่อคำตอบของเซิร์ฟเวอร์ เพราะตรวจคำตอบเองได้ด้วยค่าแฮช แต่ร้านยังต้องพึ่งให้ full node ส่งข้อมูลมาครบ (ดูตารางท้ายหัวข้อนี้) สิ่งที่ร้านต้องเชื่อแทนคือ พลังประมวลผล (CPU power) ส่วนใหญ่ของเครือข่ายซื่อสัตย์ สมมุติฐานนี้เป็นข้อเดียวกับที่ทั้งระบบใช้อยู่แล้ว

สิ่งที่ light client เก็บ

ซอฟต์แวร์ที่ตรวจแบบ SPV เรียกว่า light client ซอฟต์แวร์นี้เก็บเพียง block header ของสายโซ่ PoW ที่ยาวที่สุด light client ขอ header จากหลายโหนดในเครือข่าย แล้วเลือกสายที่มีงานสะสมมากที่สุด (most cumulative work) ตามกฎในบทที่ 2 ไม่ได้นับเพียงจำนวนบล็อก light client ตรวจ header แต่ละบล็อกเองได้ด้วยต้นทุนต่ำ การตรวจมีสามข้อ

  • Prev Hash ของ header ต้องชี้ไปยัง header ก่อนหน้าได้ถูกต้อง
  • ค่า Bits (target) ของ header ต้องตรงกับกฎการปรับความยาก (บทที่ 2 หัวข้อ 2.2) ถ้าไม่ตรวจข้อนี้ ผู้ปลอมจะตั้ง target ให้ง่ายมาก แล้วสร้าง header ที่ผ่านข้อถัดไปได้ด้วยงานเพียงเล็กน้อย
  • ค่าแฮชของ header ต้องผ่าน target นั้น

เมื่อตรวจครบสามข้อ ผู้ที่ต้องการปลอม header จึงต้องทำ PoW จริงตามความยากของเครือข่าย

ขั้นตอนการตรวจ

  1. ขอตัวธุรกรรมพร้อม Merkle branch (หรือ Merkle proof) จาก full node และให้ full node ระบุว่าธุรกรรมอยู่ในบล็อกใด Merkle branch คือชุดค่าแฮชคู่ข้าง (sibling hash) ชั้นละหนึ่งค่า ตามเส้นทางจากธุรกรรมขึ้นไปถึง root
  2. แฮชธุรกรรม แล้วนำผลที่ได้ไปต่อกับค่าแฮชใน branch และแฮชซ้ำทีละชั้นจนได้ root
  3. เทียบ root ที่คำนวณได้กับ Merkle root ใน header ที่เก็บไว้ ถ้าตรงกัน แสดงว่าธุรกรรมอยู่ในบล็อกนั้นจริง full node ที่ต้องการโกงต้องหาค่าแฮชชุดอื่นที่คำนวณแล้วได้ root เดิม แต่ SHA-256 มีคุณสมบัติ collision resistance (บทที่ 0) งานนี้จึงทำไม่ได้ในทางปฏิบัติ
  4. นับจำนวน confirmation โดยบล็อกที่มีธุรกรรมนับเป็น 1 และแต่ละบล็อกที่ต่อท้ายเพิ่มอีก 1 ยิ่งมีมาก ก็ยิ่งมั่นใจได้ว่าเครือข่ายยอมรับธุรกรรมนี้แล้ว

ทำไมผลการตรวจนี้เชื่อถือได้

light client ไม่ได้ตรวจตัวธุรกรรมเอง จึงไม่รู้ว่าลายเซ็น (digital signature) ถูกต้องหรือไม่ และไม่รู้ว่าผู้จ่ายใช้จ่ายซ้ำ (double-spending) หรือไม่ แต่เมื่อพบว่าธุรกรรมอยู่ในบล็อกหนึ่งของสายที่ยาวที่สุด light client ก็รู้ได้ว่า มีโหนดในเครือข่ายยอมรับธุรกรรมนี้แล้ว ทุกบล็อกที่ต่อท้ายยังบอกด้วยว่าผู้ขุดรายอื่นยอมรับบล็อกที่มีธุรกรรมนี้ และทำ PoW สร้างบล็อกต่อจากบล็อกนั้นแล้ว ผู้ที่ต้องการหลอก light client จึงต้องสร้างบล็อกที่ผ่าน PoW จริง และต้องสร้างต่อไปเรื่อย ๆ ให้เร็วกว่าเครือข่ายส่วนที่ซื่อสัตย์ เพราะการหลอกแบบนี้มีต้นทุนสูง ผู้ใช้ SPV จึงเชื่อผลการตรวจได้

ข้อมูลที่ต้องส่งก็มีขนาดเล็ก บล็อกที่มีราว 4,000 ธุรกรรมใช้ Merkle branch เพียง 12 ค่าแฮช (log2 4,000 ≈ 11.97 ปัดขึ้นเป็น 12) หรือ 384 ไบต์ ขณะที่ทั้งบล็อกมีขนาดราว 1–2 MB

SPV ยืนยันได้SPV ยืนยันไม่ได้
ธุรกรรมอยู่ในบล็อกที่ผ่าน PoW และอยู่ในสายที่ยาวที่สุดลายเซ็นของธุรกรรมถูกต้อง และผู้จ่ายไม่ได้ใช้จ่ายซ้ำ
จำนวน confirmationบล็อกทำตามกฎอื่นครบ เช่น ผู้ขุดไม่ได้จ่ายรางวัลบล็อก (block reward) ให้ตัวเองเกินกำหนด
ไม่มีใครแก้ไขธุรกรรม เพราะคำนวณ root ได้ตรงfull node ไม่ได้ซ่อนธุรกรรมที่จ่ายให้ผู้ใช้ light client ถ้า full node ไม่ส่งธุรกรรมนั้นมา light client ก็ไม่รู้ว่ามีธุรกรรมนั้นอยู่

3.5ข้อจำกัดของ SPV: Full node เทียบกับ Light client

SPV ปลอดภัยตราบที่พลังประมวลผลส่วนใหญ่ซื่อสัตย์

Whitepaper ระบุว่าการตรวจแบบ SPV เชื่อถือได้ตราบที่โหนดซื่อสัตย์ควบคุมเครือข่าย แต่ถ้าผู้โจมตีมีพลังประมวลผลมากกว่า ผู้ใช้ SPV จะถูกหลอกได้ง่ายขึ้น สมมุติว่าผู้โจมตีที่คุมพลังประมวลผลส่วนใหญ่สร้างบล็อกที่มีธุรกรรมจ่ายเหรียญที่ไม่มีอยู่จริงให้ร้านค้า บล็อกนั้นผ่าน PoW และคำนวณ Merkle proof ได้ถูกต้อง

  • Full node ตรวจธุรกรรมทุกรายการเอง จึงปฏิเสธบล็อกนั้นทันที ไม่ว่าบล็อกจะมี PoW มากเพียงใด
  • Light client ตรวจได้เพียงว่าบล็อกมี PoW และมีธุรกรรมอยู่จริง จึงถูกหลอกได้ตลอดเวลาที่ผู้โจมตียังเอาชนะเครือข่ายได้

ทางป้องกันที่ Whitepaper เสนอ

Whitepaper เสนอให้ light client รับ การแจ้งเตือน (alert) จาก full node เมื่อ full node พบบล็อกที่ไม่ถูกต้อง เมื่อ full node แจ้งเตือนมา ซอฟต์แวร์ของผู้ใช้จะดาวน์โหลดบล็อกนั้นและธุรกรรมที่ full node ระบุ แล้วตรวจเองว่าผิดจริงหรือไม่

Bitcoin จริงยังไม่ได้นำแนวคิดนี้มาใช้ เหตุผลที่มักอธิบายกันมีสองข้อ ข้อแรก ผู้ไม่หวังดีส่งการแจ้งเตือนปลอมจำนวนมากได้ light client จึงต้องดาวน์โหลดบล็อกตามทุกครั้ง ข้อสอง ความผิดบางแบบพิสูจน์ด้วยข้อมูลเพียงเล็กน้อยไม่ได้ เช่น การใช้เหรียญที่ไม่มีอยู่จริง

Whitepaper ยังแนะนำว่า ธุรกิจที่รับชำระเงินบ่อยควรรันโหนดของตัวเอง เพราะจะปลอดภัยโดยไม่ต้องพึ่งผู้อื่น และตรวจได้เร็วกว่า

ประเด็นที่มักสับสน Pruned node ไม่ใช่ light client เพราะ pruned node ดาวน์โหลดและตรวจทุกบล็อกเองครบเหมือน full node เพียงแต่ลบไฟล์บล็อกเก่าทิ้งหลังตรวจเสร็จ ส่วน light client ไม่เคยตรวจธุรกรรมของผู้อื่นเลย
ในทางปฏิบัติ light client ต้องขอธุรกรรมที่เกี่ยวกับตนจาก full node วิธีแรกคือ BIP37 (bloom filter) ในวิธีนี้ light client สร้างตัวกรอง (filter) จาก address ของตนแล้วส่งไปให้ full node จากนั้น full node คัดธุรกรรมที่ตรงกับตัวกรองส่งกลับมา วิธีนี้มีปัญหาสองข้อ ข้อแรก full node นำตัวกรองไปวิเคราะห์ได้ว่า address ใดเป็นของผู้ใช้ ข้อสอง full node ต้องคัดข้อมูลให้ light client ทีละราย จึงรับภาระเพิ่ม Bitcoin Core จึงปิดบริการนี้เป็นค่าเริ่มต้น (default) ตั้งแต่รุ่น 0.19

วิธีที่ใหม่กว่าคือ BIP157/158 (compact block filters) วิธีนี้สลับฝ่ายที่สร้างตัวกรอง full node สร้างตัวกรองของแต่ละบล็อกแบบเดียวกันสำหรับทุกคน light client นำตัวกรองนั้นมาตรวจเองว่าบล็อกใดอาจมีธุรกรรมของตน แล้วจึงดาวน์โหลดเฉพาะบล็อกนั้น full node เห็นเพียงว่า light client ขอบล็อกใด จึงรู้ได้ยากกว่าเดิมมากว่า address ใดเป็นของผู้ใช้ และไม่ต้องคัดข้อมูลให้ผู้ใช้ทีละราย

สรุปท้ายบท

  • โจทย์: ทุกโหนดต้องเก็บข้อมูลที่โตขึ้นตลอด และผู้ใช้บนมือถือต้องตรวจได้ว่าได้รับเงินจริงโดยไม่ต้องเก็บข้อมูลทั้งหมด ทางแก้ของทั้งสองข้อต้องไม่ทำให้หลักฐานเดิมใช้ไม่ได้
  • ข้อ 7: Merkle tree แฮชธุรกรรมทีละคู่ขึ้นไปจนเหลือ Merkle root ค่าเดียว แล้วใส่ไว้ใน header ถ้าแก้ธุรกรรมใด root จะเปลี่ยน และ PoW ของบล็อกจะใช้ไม่ได้
  • ข้อ 7: เมื่อมีบล็อกต่อท้ายมากพอ ธุรกรรมที่ใช้ไปแล้วลบทิ้งได้ โดยเก็บค่าแฮชบนสุดของกิ่งย่อย (subtree) ที่ตัดไว้แทน ค่าแฮชของบล็อกไม่เปลี่ยน เพราะคำนวณจาก header เท่านั้น
  • ข้อ 7: header ซึ่งไม่รวมธุรกรรมมีขนาด 80 ไบต์ ทั้งปีจึงเพิ่มขึ้น 80 × 6 × 24 × 365 ≈ 4.2 MB
  • ข้อ 8: light client เก็บเฉพาะ header ของสายที่ยาวที่สุด แล้วขอ Merkle branch จาก full node มาคำนวณ root เทียบกับ header Merkle branch มีค่าแฮช log2(n) ค่า (ปัดขึ้น) จำนวน confirmation นับบล็อกที่มีธุรกรรมเป็น 1 แล้วเพิ่มอีก 1 ต่อบล็อกที่ต่อท้าย
  • ข้อ 8: SPV ไม่ได้ตรวจธุรกรรมเอง จึงปลอดภัยตราบที่พลังประมวลผลส่วนใหญ่ซื่อสัตย์ ทางป้องกันที่ Whitepaper เสนอคือการแจ้งเตือน (alert) จาก full node และให้ธุรกิจที่รับเงินบ่อยรันโหนดเอง

แบบฝึกหัด

1. ถ้าแก้ธุรกรรมเพียงรายการเดียวในบล็อกเก่า เหตุใด PoW ของบล็อกนั้นจึงใช้ไม่ได้ ทั้งที่ PoW คำนวณจาก header เท่านั้น

ดูเฉลย
เพราะ header มี Merkle root ซึ่งคำนวณจากธุรกรรมทุกรายการ เมื่อแก้ธุรกรรม txid จะเปลี่ยน ค่าแฮชทุกชั้นที่อยู่เหนือขึ้นไปจะเปลี่ยนตาม จนถึง Merkle root ค่าแฮชของ header จึงเปลี่ยน และไม่ผ่าน target อีกต่อไป

2. บล็อกที่มี 8 ธุรกรรม ต้องใช้ค่าแฮชกี่ค่าใน Merkle branch เพื่อพิสูจน์ว่ามีธุรกรรมหนึ่งอยู่ในบล็อก

  1. ก. 2 ค่า
  2. ข. 3 ค่า
  3. ค. 7 ค่า
  4. ง. 8 ค่า
ดูเฉลย
ข. 3 ค่า เพราะ log2(8) = 3 ค่าแฮชลดจาก 8 เป็น 4, 2 และ 1 จึงต้องจับคู่ 3 ครั้ง แต่ละครั้งใช้ค่าแฮชคู่ข้างหนึ่งค่า

3. บล็อกหนึ่งมี 5 ธุรกรรม Bitcoin สร้าง Merkle tree อย่างไรเมื่อจำนวนค่าแฮชเป็นเลขคี่

ดูเฉลย
ทำสำเนาค่าแฮชตัวสุดท้ายของชั้นนั้นมาจับคู่กับตัวเอง ชั้นล่างมี 5 ค่า ค่าที่ 5 จับคู่กับสำเนาของตัวเอง ได้ชั้นถัดไป 3 ค่า ค่าที่ 3 จับคู่กับสำเนาของตัวเองอีกครั้ง ได้ 2 ค่า แล้วได้ Merkle root

4. แสดงการคำนวณว่า header ของ Bitcoin เพิ่มขึ้นประมาณ 4.2 MB ต่อปีได้อย่างไร และถ้าบล็อกเกิดทุก 5 นาที header จะเพิ่มขึ้นปีละเท่าใด

ดูเฉลย
80 ไบต์ × 6 บล็อกต่อชั่วโมง × 24 × 365 = 4,204,800 ไบต์ ≈ 4.2 MB ถ้าบล็อกเกิดทุก 5 นาที จะมีชั่วโมงละ 12 บล็อก ได้ 80 × 12 × 24 × 365 = 8,409,600 ไบต์ ≈ 8.4 MB ต่อปี

5. ข้อใดอธิบาย pruning ตาม Whitepaper ข้อ 7 ได้ถูกต้อง

  1. ก. ลบ header ของบล็อกเก่าเพื่อประหยัดพื้นที่
  2. ข. ลบธุรกรรมที่ใช้ไปแล้ว โดยเก็บค่าแฮชของกิ่งที่ตัดไว้ ค่าแฮชของบล็อกจึงไม่เปลี่ยน
  3. ค. ลบธุรกรรมแล้วคำนวณ Merkle root ใหม่ใส่ใน header
  4. ง. ลบธุรกรรมที่เหรียญยังไม่มีใครใช้ เพราะยังไม่มีใครต้องการตรวจ
ดูเฉลย
ข. ข้อ ก ผิด เพราะ header คือส่วนที่ต้องเก็บไว้ตลอด ข้อ ค ผิด เพราะถ้า root เปลี่ยน ค่าแฮชของบล็อกจะเปลี่ยน และ PoW เดิมจะใช้ไม่ได้ ข้อ ง ผิด เพราะโหนดยังต้องใช้ธุรกรรมเหล่านี้ตรวจธุรกรรมใหม่ที่นำเหรียญนั้นมาจ่าย

6. ผู้โจมตีที่คุมพลังประมวลผลเกินครึ่งสร้างบล็อกที่จ่ายเหรียญปลอมให้ร้านค้า ร้านค้าใดถูกหลอกได้

  1. ก. ร้านที่รัน full node
  2. ข. ร้านที่รัน pruned node
  3. ค. ร้านที่ใช้ light client แบบ SPV
  4. ง. ถูกหลอกทั้งสามแบบ
ดูเฉลย
ค. Full node และ pruned node ตรวจธุรกรรมทุกรายการเอง จึงปฏิเสธบล็อกที่ผิดกฎ ไม่ว่าบล็อกนั้นจะมี PoW มากเพียงใด ส่วน light client ตรวจได้เพียงว่าบล็อกมี PoW และธุรกรรมอยู่ในบล็อก จึงถูกหลอกได้ตลอดเวลาที่ผู้โจมตียังเอาชนะเครือข่ายได้

7. light client ต้องเก็บข้อมูลใดไว้กับตัว และต้องขอข้อมูลใดจาก full node เมื่อต้องการตรวจธุรกรรมหนึ่ง

ดูเฉลย
เก็บ block header ของสายโซ่ PoW ที่ยาวที่สุด และขอ ตัวธุรกรรมพร้อม Merkle branch ที่เชื่อมธุรกรรมนั้นกับ Merkle root ของบล็อก พร้อมหมายเลขบล็อกที่ธุรกรรมอยู่ จากนั้นคำนวณ root เทียบกับ header และนับจำนวน confirmation
