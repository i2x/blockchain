Oracle

Smart contract ตรวจได้ทุกอย่างที่อยู่บนเชน เช่น ยอดเงิน ลายเซ็น และสถานะของ contract อื่น แต่แอปจำนวนมากต้องรู้เรื่องนอกเชนด้วย เช่น ราคา ETH เป็นดอลลาร์ ผลการแข่งขัน หรือเที่ยวบินล่าช้าหรือไม่ บทนี้อธิบายว่าทำไม contract จึงดึงข้อมูลเหล่านี้เองไม่ได้ Oracle นำข้อมูลเข้ามาด้วยรูปแบบใด ทำไมต้องกระจายศูนย์ ความเสี่ยงที่เกิดขึ้นจริง และตัวอย่างการใช้งาน ได้แก่ price feed ประกันภัย และการสุ่มเลขด้วย VRF

เริ่มจากโจทย์: contract ที่มองไม่เห็นโลกภายนอก

สมมติว่าเราเขียน contract ให้กู้ยืม (lending) ผู้กู้ฝาก ETH เป็นหลักประกัน (collateral) แล้วกู้ stablecoin ที่มีมูลค่าเท่ากับดอลลาร์ออกไป กติกาคือ ถ้ามูลค่าหลักประกันลดลงจนเกือบเท่ายอดหนี้ ใครก็ได้มาชำระหนี้แทนแล้วรับหลักประกันไปในราคาลด เพื่อให้ผู้ให้กู้ไม่ขาดทุน กติกานี้เขียนเป็นโค้ดได้ทุกบรรทัด ยกเว้นตัวเลขเดียว คือ ตอนนี้ 1 ETH มีค่ากี่ดอลลาร์

ราคานี้ไม่ได้อยู่บน Ethereum ราคาเกิดจากการซื้อขายในตลาดจำนวนมากทั่วโลก ทั้งตลาดแบบรวมศูนย์ (centralized exchange) และตลาดบนเชนอื่น ๆ โจทย์เดียวกันเกิดกับแอปอีกหลายแบบ

  • ประกันเที่ยวบินล่าช้า: ต้องรู้ว่าเที่ยวบินลงจอดช้ากว่ากำหนดกี่ชั่วโมง
  • ประกันพืชผล: ต้องรู้ปริมาณน้ำฝนของพื้นที่หนึ่งในฤดูกาลนี้
  • เกมและการแจก NFT: ต้องการตัวเลขสุ่มที่ไม่มีใครทำนายหรือเลือกได้ (บทที่ 12)
  • สะพานข้ามเชน (cross-chain bridge): ต้องรู้ว่ามีธุรกรรมเกิดขึ้นบน blockchain อีกสายหนึ่ง

ส่วนประกอบที่นำข้อมูลนอกเชนเข้ามาให้ contract ใช้ เรียกว่า Oracle ชื่อนี้มาจากผู้ทำนายในตำนานกรีกที่ผู้คนไปถามคำตอบ คำตอบของ oracle มีผลกับเงินใน contract โดยตรง ใครคุมคำตอบได้ก็คุมเงินได้ บทนี้จึงไล่ตอบคำถามต่อไปนี้

ทำไม contract จึงเรียก API ราคาเองไม่ได้ทุกโหนดต้องรันได้ผลเดียวกัน (deterministic) ข้อมูลภายนอกจึงต้องเข้ามาเป็นธุรกรรม13.1
ข้อมูลไหลเข้าออกแบบใด และใครเป็นผู้เริ่มInbound / Outbound และ Push / Pull13.2
ถ้าผู้ส่งข้อมูลโกง จะป้องกันอย่างไรใช้หลายโหนดและหลายแหล่งข้อมูล แล้วรวมด้วยค่ามัธยฐาน (median)13.3

13.1Oracle problem: เหตุที่ smart contract ดึงข้อมูลภายนอกเองไม่ได้

ทุกโหนดต้องรันซ้ำแล้วได้ผลเดียวกัน

หัวข้อ 5.3 อธิบายว่า Ethereum ไม่ได้เชื่อผลที่ผู้สร้างบล็อกประกาศ ทุกโหนดรันทุกธุรกรรมเองบน EVM แล้วเทียบว่าได้ state root ตรงกับที่อยู่ใน header หรือไม่ การตรวจนี้ใช้ได้ก็ต่อเมื่อการรันเป็นแบบ deterministic คือ ข้อมูลตั้งต้นชุดเดียวกันต้องให้ผลเดียวกันเสมอ ไม่ว่าจะรันที่เครื่องใดหรือเมื่อใด

ลองนึกว่า EVM มีคำสั่งเรียก API ได้ แล้ว contract ขอราคา ETH จากเว็บไซต์หนึ่ง จะเกิดปัญหาสามข้อ

  • คนละเวลา คนละคำตอบ: โหนดแต่ละเครื่องได้รับบล็อกในเวลาต่างกันเล็กน้อย ราคาในตลาดเปลี่ยนทุกวินาที โหนดแต่ละเครื่องจึงได้ราคาต่างกัน และได้ state root ต่างกัน
  • โหนดที่เข้ามาทีหลังต้องรันซ้ำ: โหนดใหม่ที่ sync ย้อนหลังต้องรันธุรกรรมเก่าทุกรายการ ถ้าธุรกรรมของปีที่แล้วเรียก API อีกครั้ง โหนดนั้นจะได้ราคาของวันนี้ หรือพบว่าเว็บไซต์ปิดไปแล้ว
  • เจ้าของ API มีอำนาจเหนือเครือข่าย: เจ้าของเว็บไซต์ตอบแต่ละโหนดไม่เหมือนกันได้ และทำให้เครือข่ายแตกเป็นหลายสายได้

Ethereum จึงไม่มี opcode สำหรับเรียกเครือข่ายภายนอกเลย contract อ่านได้เฉพาะ state บนเชนและข้อมูลที่มากับธุรกรรม ข้อมูลภายนอกจึงต้องมีผู้ส่งเข้ามา เป็นธุรกรรม เมื่อค่าเข้าไปอยู่ในบล็อกแล้ว ทุกโหนดในทุกเวลาก็อ่านได้ค่าเดียวกัน

ปัญหาที่แท้จริงคือความไว้ใจ

การส่งข้อมูลเข้ามาเป็นธุรกรรมแก้ได้แค่เรื่อง deterministic ยังเหลือคำถามที่ยากกว่า คือ ค่าที่ส่งเข้ามาตรงกับความจริงหรือไม่ Blockchain ตรวจได้ว่าธุรกรรมนี้มีลายเซ็นของ address ใด แต่ตรวจไม่ได้ว่าราคา ETH ตอนนี้เป็น 2,001.5 ดอลลาร์จริง contract จึงต้องเชื่อผู้ส่งข้อมูล ปัญหานี้เรียกว่า oracle problem

Bitcoin ไม่ต้องเจอปัญหานี้ เพราะข้อมูลทั้งหมดที่ใช้ตัดสินอยู่บนเชนอยู่แล้ว ใครเป็นเจ้าของเหรียญใดตรวจได้จาก UTXO set และลายเซ็น (บทที่ 1) ไม่มีข้อเท็จจริงใดที่ต้องถามคนนอก แต่เมื่อ contract ตัดสินใจจากเหตุการณ์ภายนอก ความปลอดภัยของระบบจะไม่เกินความน่าเชื่อถือของข้อมูลที่ได้รับ ถ้าข้อมูลเข้ามาผิด contract ก็ทำงานผิดตามกติกาอย่างแม่นยำ นักพัฒนามักสรุปเรื่องนี้ด้วยวลี garbage in, garbage out

ประเด็นที่มักออกสอบ Oracle problem มีสองชั้น ชั้นแรกเป็นเรื่องเทคนิค: contract ต้อง deterministic จึงเรียก API เองไม่ได้ ข้อมูลต้องเข้ามาเป็นธุรกรรม ชั้นที่สองเป็นเรื่องความไว้ใจ: เมื่อมีผู้ส่งข้อมูลเข้ามา contract ก็ต้องเชื่อผู้ส่ง ระบบที่ตั้งใจไม่พึ่งตัวกลาง (trustless) จึงกลับมามีตัวกลางที่จุดนี้ Oracle ไม่ใช่แหล่งข้อมูล แต่เป็นตัวเชื่อมระหว่างแหล่งข้อมูลกับเชน

13.2รูปแบบการทำงาน: Inbound / Outbound และ Push / Pull

ทำไมต้องแยกทิศทาง

โจทย์ใน 13.1 คือการนำข้อมูลภายนอกเข้ามาในเชน แต่บางแอปต้องการทิศกลับกัน เช่น contract เช่าห้องพักรับค่าเช่าแล้ว และต้องสั่งให้กลอนประตูอัจฉริยะ (smart lock) ปลดล็อก contract ส่ง HTTP request ออกไปเองไม่ได้ด้วยเหตุผลเดียวกับที่รับเข้ามาเองไม่ได้ ทั้งสองทิศจึงต้องมี oracle

  • Inbound oracle: นำข้อมูลจากนอกเชนเข้าสู่เชน เช่น ราคา ผลกีฬา สภาพอากาศ
  • Outbound oracle: นำเหตุการณ์บนเชนออกไปสั่งระบบนอกเชน oracle เฝ้าดู event ที่ contract ปล่อยออกมา (หัวข้อ 5.6) แล้วไปเรียกระบบภายนอก เช่น สั่งปลดล็อกประตู หรือสั่งโอนเงินผ่านธนาคาร

ทำไมต้องแยกว่าใครเป็นผู้เริ่ม

อีกมิติหนึ่งคือฝ่ายใดเป็นผู้เริ่มส่งข้อมูล ทางเลือกนี้กำหนดว่าใครจ่าย gas ข้อมูลสดเพียงใด และ contract ได้คำตอบทันทีหรือต้องรอ

  • Push: ฝ่ายที่มีข้อมูลส่งออกไปเองเมื่อมีข้อมูลใหม่ ฝ่ายรับไม่ต้องร้องขอ
  • Pull: ฝ่ายที่ต้องการข้อมูลเป็นผู้ร้องขอ แล้วอีกฝ่ายจึงตอบกลับ

Push inbound: ข้อมูลพร้อมใช้ แต่ต้องมีคนจ่ายค่าอัปเดต

contract ด้าน DeFi ต้องใช้ราคาทันทีในธุรกรรมเดียวกัน เช่น ตอนผู้ใช้กู้เงินหรือตอนชำระบัญชี (liquidation) ถ้าต้องส่งคำขอแล้วรอคำตอบ ราคาอาจเปลี่ยนไปมากระหว่างรอ รูปแบบ push จึงเก็บราคาล่าสุดไว้ใน contract ของ oracle ล่วงหน้า contract อื่นเรียกฟังก์ชัน view อ่านค่าได้ทันที

ข้อเสียคือทุกครั้งที่อัปเดตต้องเสีย gas แม้ไม่มีใครอ่านค่านั้น ถ้าอัปเดตทุกบล็อก ค่า gas จะสูงเกินไป ถ้าอัปเดตตามเวลาอย่างเดียว ราคาอาจล้าหลังตลาดมากในช่วงที่ราคาผันผวน price feed จึงมักใช้เงื่อนไขสองข้อร่วมกัน

  • Deviation threshold: อัปเดตเมื่อราคาใหม่ต่างจากค่าบนเชนเกินร้อยละที่กำหนด เช่น 0.5% เงื่อนไขนี้ทำให้ราคาตามตลาดทันในช่วงผันผวน
  • Heartbeat: อัปเดตเมื่อครบระยะเวลาที่กำหนด เช่น ทุกหนึ่งชั่วโมง แม้ราคาไม่เปลี่ยน เงื่อนไขนี้ให้ contract แยกได้ว่า ราคานิ่งจริง หรือ feed หยุดทำงาน ถ้าเวลาอัปเดตล่าสุดเก่ากว่ารอบ heartbeat แสดงว่า feed มีปัญหา

Pull inbound: ข้อมูลสด แต่ต้องแยกเป็นสองธุรกรรม

ข้อมูลบางอย่างใช้นาน ๆ ครั้ง เช่น ผลการแข่งขันนัดหนึ่ง หรือเลขสุ่มสำหรับการเปิดกล่อง NFT หนึ่งกล่อง การอัปเดตข้อมูลเหล่านี้ไว้ล่วงหน้าทุกบล็อกสิ้นเปลืองโดยใช่เหตุ contract จึงส่งคำขอเมื่อต้องการเท่านั้น แต่ contract รอคำตอบกลางธุรกรรมไม่ได้ เพราะ oracle อยู่นอกเชนและต้องส่งคำตอบมาในธุรกรรมใหม่ ขั้นตอนจึงแบ่งเป็นสองธุรกรรม

การแบ่งเป็นสองธุรกรรมมีผลตามมาสามข้อ ข้อแรก ผู้ใช้ไม่ได้ผลลัพธ์ในธุรกรรมที่ตนส่ง ต้องรอธุรกรรมของ oracle ข้อสอง contract ต้องจำว่าคำขอหมายเลขใดเป็นของใคร เพื่อนำคำตอบไปใช้ให้ถูกคน ข้อสาม ฟังก์ชัน callback ต้องตรวจว่าผู้เรียกเป็น oracle จริง ถ้าไม่ตรวจ ใครก็เรียก fulfill แล้วส่งค่าปลอมเข้ามาได้

คำว่า pull oracle อีกความหมายหนึ่ง oracle รุ่นใหม่บางระบบ เช่น Pyth ใช้คำว่า pull ในอีกความหมายหนึ่ง ผู้ให้บริการลงลายเซ็นราคาไว้นอกเชนตลอดเวลา เมื่อผู้ใช้ต้องการราคา ผู้ใช้ดึงรายงานที่ลงลายเซ็นแล้วแนบมาในธุรกรรมของตนเอง contract ตรวจลายเซ็นแล้วใช้ราคานั้นในธุรกรรมเดียวกัน ผู้ใช้จ่าย gas เฉพาะตอนที่ต้องการ และไม่ต้องรอธุรกรรมที่สอง เมื่อพบคำว่า pull จึงควรดูบริบทว่าหมายถึงแบบใด

13.3Oracle แบบรวมศูนย์กับแบบกระจายศูนย์ (Chainlink)

Oracle แบบรวมศูนย์: ง่าย แต่ย้อนกลับไปเชื่อคนคนเดียว

วิธีที่ง่ายที่สุดคือให้บริษัทหนึ่งเปิดเซิร์ฟเวอร์ ดึงราคาจากตลาด แล้วใช้ private key ของตนส่งราคาเข้า contract contract ยอมรับเฉพาะค่าที่มาจาก address นี้ วิธีนี้เร็ว ถูก และเขียนง่าย แต่ลองดูว่าใครทำให้ระบบพังได้บ้าง

  • ผู้ดูแล oracle ส่งราคาปลอมเอง เพื่อชำระบัญชีของผู้กู้แล้วเก็บหลักประกันไปในราคาถูก
  • ผู้โจมตีขโมย private key ของ oracle แล้วส่งราคาปลอม
  • เซิร์ฟเวอร์ล่ม หรือ API ต้นทางล่ม ราคาจึงหยุดอัปเดต
  • หน่วยงานรัฐหรือผู้มีอำนาจกดดันให้ผู้ดูแลหยุดส่งข้อมูลให้บางแอป

contract ที่ถือเงินหลายร้อยล้านดอลลาร์จึงปลอดภัยได้เพียงเท่ากับ key ดอกเดียว ผู้ใช้ไม่ต้องเชื่อธนาคาร แต่ต้องเชื่อผู้ดูแล oracle แทน บริการรวมศูนย์บางรายพยายามลดความไว้ใจด้วยหลักฐานทางเทคนิค เช่น Oraclize (ภายหลังเปลี่ยนชื่อเป็น Provable) แนบหลักฐานว่าข้อมูลมาจากเว็บไซต์ต้นทางจริง แต่ก็ยังพึ่งผู้ให้บริการรายเดียวในการส่งข้อมูลให้ทันเวลา

Oracle แบบกระจายศูนย์: ไม่ต้องเชื่อรายใดรายหนึ่ง

แนวคิดเดียวกับ blockchain คือ ให้หลายฝ่ายที่เป็นอิสระต่อกันทำงานเดียวกัน แล้วรวมผลด้วยกติกาที่ผู้โกงส่วนน้อยเปลี่ยนผลไม่ได้ ระบบแบบนี้เรียกว่า decentralized oracle network (DON) และต้องกระจายศูนย์อย่างน้อยสองชั้น

  • ชั้นแหล่งข้อมูล: ดึงราคาจากหลายตลาดและหลายผู้รวบรวมข้อมูล (data aggregator) ถ้าทุกโหนดอ่านจาก API เดียวกัน API นั้นก็ยังเป็นจุดล้มเหลวเดียว
  • ชั้นโหนด: ให้ผู้ให้บริการโหนด (node operator) หลายรายที่ไม่เกี่ยวข้องกันรายงานราคาแยกกัน

ทำไมใช้ค่ามัธยฐาน ไม่ใช้ค่าเฉลี่ย

จากภาพ ถ้าใช้ค่าเฉลี่ย ผลจะเป็น (2,000 + 2,001 + 2,001 + 2,002 + 9,999) / 5 = 3,600.6 โหนดที่โกงเพียงรายเดียวดันราคาขึ้นได้เกือบสองเท่า ค่ามัธยฐานคือค่าที่อยู่ตรงกลางหลังเรียงลำดับ ถ้าโหนดที่โกงมีน้อยกว่าครึ่ง ค่ามัธยฐานจะอยู่ในช่วงของค่าที่โหนดสุจริตรายงานเสมอ ผู้โจมตีจึงต้องคุมโหนดให้ได้เกินครึ่ง ไม่ใช่แค่รายเดียว

13.4ความเสี่ยง: การปั่นราคา และจุดล้มเหลวเดียว (Single point of failure)

ความเสียหายจาก oracle ส่วนใหญ่ไม่ได้มาจากบั๊กในโค้ดของ contract โค้ดทำงานตามกติกาทุกบรรทัด แต่ได้ราคาที่ผิดเข้ามา ราคาผิดได้สองทาง คือ มีผู้จงใจปั่น (manipulation) หรือระบบที่ส่งราคาล้มเหลว

ทำไมราคาจาก DEX pool เดียวจึงอันตราย

นักพัฒนาบางรายไม่อยากพึ่ง oracle ภายนอก จึงอ่านราคาจากตลาดแลกเปลี่ยนบนเชน (DEX) โดยตรง เพราะดูเหมือนข้อมูลอยู่บนเชนอยู่แล้วและไม่ต้องเชื่อใคร DEX แบบ AMM (automated market maker) เช่น Uniswap กำหนดราคาจากอัตราส่วนของเหรียญสองชนิดใน pool ถ้า pool มีเหรียญ X 1,000,000 เหรียญ กับ USDC 1,000,000 เหรียญ ราคาของ X คือ 1 USDC ใครซื้อ X ออกจาก pool จำนวนมาก X ใน pool จะเหลือน้อยลงและราคาจะสูงขึ้นทันที

ราคาแบบนี้เรียกว่า spot price คือราคา ณ ขณะนั้นของ pool เดียว ใครมีเงินมากพอก็เปลี่ยนได้ด้วยการซื้อขายครั้งเดียว ผู้โจมตีต้องใช้ทุนมาก จึงอาจคิดว่าเสี่ยงต่ำ แต่ flash loan ทำให้เงื่อนไขข้อนี้หายไป

Flash loan: ยืมเงินก้อนใหญ่โดยไม่ต้องมีหลักประกัน

Flash loan คือการกู้ที่ต้องคืนเงินภายในธุรกรรมเดียวกัน ถ้าถึงท้ายธุรกรรมแล้วยังคืนไม่ครบ ธุรกรรมทั้งหมดจะ revert เหมือนไม่เคยกู้ ผู้ให้กู้จึงไม่มีความเสี่ยงและไม่ต้องขอหลักประกัน เครื่องมือนี้มีประโยชน์ เช่น ใช้ทำ arbitrage หรือย้ายหนี้ระหว่างโปรโตคอล แต่ผลข้างเคียงคือ ใครก็ได้เข้าถึงเงินหลายสิบล้านดอลลาร์ได้ชั่วคราวโดยไม่ต้องมีทุน ขอเพียงคืนได้ก่อนธุรกรรมจบ

ตัวอย่างที่เกิดขึ้นจริง ได้แก่ การโจมตี bZx ในเดือนกุมภาพันธ์ 2020 ซึ่งใช้ flash loan บิดราคาบน DEX ที่โปรโตคอลใช้อ้างอิง และกรณี Mango Markets ในเดือนตุลาคม 2022 ผู้โจมตีดันราคาโทเคน MNGO ในตลาดที่มีสภาพคล่องต่ำ แล้วกู้เงินออกไปกว่า 100 ล้านดอลลาร์โดยใช้มูลค่าหลักประกันที่สูงเกินจริง ทั้งสองกรณี contract ทำงานตามโค้ด แต่เชื่อราคาที่ผู้โจมตีกำหนดได้

วิธีป้องกันการปั่นราคา

วิธีทำไมได้ผลข้อจำกัด
ใช้ DON ที่รวมราคาจากหลายตลาดผู้โจมตีต้องบิดราคาในตลาดส่วนใหญ่พร้อมกัน ซึ่งแพงกว่าการบิด pool เดียวมากยังต้องเชื่อ DON และเหรียญที่ซื้อขายน้อยอาจมีแหล่งข้อมูลไม่พอ
TWAP (time-weighted average price)เฉลี่ยราคาตามเวลา เช่น 30 นาที flash loan ต้องคืนในธุรกรรมเดียว จึงค้างราคาข้ามบล็อกไม่ได้ ถ้าจะบิดค่าเฉลี่ยต้องค้างราคาไว้หลายบล็อก ระหว่างนั้นผู้ทำ arbitrage จะเข้ามาซื้อขายดึงราคากลับ ผู้โจมตีจึงเสียเงินมากราคาล้าหลังตลาด ในช่วงตลาดผันผวนแรง ระบบอาจชำระบัญชีช้าเกินไป
ตรวจความเก่าของราคา (staleness check)ปฏิเสธราคาที่อัปเดตล่าสุดนานเกินรอบ heartbeatต้องมีแผนสำรองเมื่อ feed หยุด เช่น หยุดรับธุรกรรมบางประเภทชั่วคราว
Circuit breakerถ้าราคาเปลี่ยนเกินร้อยละที่กำหนดในเวลาสั้น ๆ ให้หยุดชั่วคราวหรือเทียบกับ oracle ตัวที่สองในวันที่ราคาร่วงจริง ระบบอาจหยุดในเวลาที่ผู้ใช้ต้องการมากที่สุด
หน่วงเวลาก่อนใช้ราคาใหม่MakerDAO ใช้ Oracle Security Module หน่วงราคาใหม่หนึ่งชั่วโมงก่อนนำไปใช้ ถ้าพบราคาผิด ผู้ดูแลมีเวลาหยุดระบบก่อนเกิดความเสียหายราคาที่ใช้จริงช้ากว่าตลาดหนึ่งชั่วโมงเสมอ

จุดล้มเหลวเดียว (Single point of failure)

Single point of failure คือส่วนประกอบที่ถ้าล้มเพียงจุดเดียว ทั้งระบบจะล้มตาม blockchain ตั้งใจกำจัดจุดแบบนี้ด้วยโหนดหลายพันเครื่อง แต่ถ้า contract พึ่ง oracle ที่มีจุดอ่อนจุดเดียว ทั้งระบบก็ยังล้มได้จากจุดนั้น จุดที่ควรตรวจมีดังนี้

  • ผู้ส่งข้อมูลรายเดียว: oracle รวมศูนย์ หรือ DON ที่มีโหนดน้อยและเจ้าของเดียวกันหลายโหนด
  • แหล่งข้อมูลเดียว: โหนดสิบรายที่อ่าน API เดียวกัน ก็ยังพังพร้อมกันเมื่อ API นั้นผิด
  • สิทธิ์ผู้ดูแล: ถ้า key ของผู้ที่เปลี่ยนรายชื่อโหนดหรือค่าตั้งของ feed หลุด ผู้โจมตีก็เปลี่ยน feed ทั้งชุดได้ ระบบจึงมักใช้ multisig ที่ต้องมีลายเซ็นหลายรายร่วมกัน
  • ความต่อเนื่อง (liveness): feed ที่หยุดอัปเดตไม่ได้ส่งค่าผิด แต่ค่าเดิมค้างอยู่ ถ้า contract ไม่ตรวจเวลาอัปเดต ก็จะใช้ราคาเก่าต่อไปโดยไม่รู้ตัว
ค่าที่ถูกต้องตามกติกา แต่ไม่ตรงกับตลาด ในเดือนพฤษภาคม 2022 ราคาเหรียญ LUNA ร่วงจากหลายสิบดอลลาร์จนเหลือไม่ถึงเศษเสี้ยวของเซนต์ภายในไม่กี่วัน price feed ของ LUNA ที่ใช้อยู่ตอนนั้นมีค่าต่ำสุดที่ยอมรายงาน (minimum answer) ราว 0.10 ดอลลาร์ เมื่อราคาตลาดต่ำกว่านั้น feed ยังรายงาน 0.10 ผู้ใช้บางรายจึงซื้อ LUNA ราคาถูกในตลาด แล้วนำไปฝากเป็นหลักประกันในโปรโตคอลที่ใช้ feed นี้ โปรโตคอลตีราคา LUNA สูงกว่าตลาดหลายเท่า ผู้ใช้เหล่านั้นจึงกู้เงินออกไปได้มากเกินมูลค่าจริง บทเรียนคือ contract ควรตรวจว่าราคาชนขอบเขตของ feed หรือไม่ และควรมีกลไกหยุดรับหลักประกันชนิดนั้นเมื่อตลาดผิดปกติ
ประเด็นที่มักออกสอบ ความปลอดภัยของ DApp เท่ากับจุดที่อ่อนที่สุด ถ้า blockchain กระจายศูนย์ แต่ oracle รวมศูนย์ ระบบทั้งหมดก็เป็นระบบรวมศูนย์ ผู้คุม oracle ได้อำนาจเหนือเงินทุกบาทใน contract นอกจากนี้ spot price จาก DEX pool เดียวไม่ใช่ oracle ที่ปลอดภัย เพราะ flash loan ทำให้ใครก็บิดราคาได้ภายในธุรกรรมเดียว ทางแก้ที่ควรตอบได้คือ DON ที่ใช้หลายแหล่งข้อมูล และ TWAP

Price feed ใน DeFi

DeFi (decentralized finance) คือบริการทางการเงินที่ทำงานด้วย smart contract เช่น การกู้ยืม stablecoin และสัญญาซื้อขายล่วงหน้า (derivatives) แทบทุกบริการต้องรู้ราคาสินทรัพย์ เพราะต้องตีมูลค่าหลักประกันและตัดสินว่าใครต้องถูกชำระบัญชี

  • Lending: ใช้ราคาตีมูลค่าหลักประกัน และหาว่าบัญชีใดเข้าเกณฑ์ชำระบัญชี (liquidation)
  • Stablecoin ที่มีหลักประกันเป็นคริปโต: เช่น DAI ต้องรู้มูลค่าหลักประกันเทียบกับดอลลาร์ เพื่อคุมให้มูลค่ารวมของหลักประกันสูงกว่าจำนวน DAI ที่ออก
  • Derivatives: ใช้ราคาอ้างอิงคำนวณกำไรขาดทุนของแต่ละฝั่ง

ตัวอย่างโค้ดด้านล่างอ่านราคา ETH/USD จาก price feed ของ Chainlink ผ่าน interface AggregatorV3Interface และตรวจสองเรื่องที่หัวข้อ 13.4 เตือนไว้ คือ ราคาต้องมากกว่าศูนย์ และต้องไม่เก่าเกินกำหนด

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

interface AggregatorV3Interface {
    function decimals() external view returns (uint8);
    function latestRoundData() external view returns (
        uint80 roundId,
        int256 answer,        // ราคา เป็นจำนวนเต็มที่คูณ 10^decimals ไว้แล้ว
        uint256 startedAt,
        uint256 updatedAt,    // เวลาที่อัปเดตล่าสุด (Unix time)
        uint80 answeredInRound
    );
}

contract PriceReader {
    AggregatorV3Interface public immutable feed;
    uint256 public constant MAX_AGE = 2 hours;   // ตั้งให้ยาวกว่า heartbeat ของ feed ที่ใช้

    constructor(address feedAddress) {
        feed = AggregatorV3Interface(feedAddress); // address ของ feed ดูได้จากเอกสารของ Chainlink
    }

    function ethUsd() public view returns (uint256) {
        (, int256 answer, , uint256 updatedAt, ) = feed.latestRoundData();
        require(answer > 0, "bad price");
        require(block.timestamp - updatedAt <= MAX_AGE, "stale price");
        return uint256(answer);  // ETH/USD มีทศนิยม 8 หลัก: 2,001.5 USD = 200150000000
    }
}

EVM ไม่มีเลขทศนิยม (หัวข้อ 5.3) feed จึงส่งราคาเป็นจำนวนเต็มที่คูณ 10decimals ไว้แล้ว feed ราคาเทียบ USD ส่วนใหญ่ใช้ทศนิยม 8 หลัก ส่วน ETH มีทศนิยม 18 หลัก (wei) ผู้เขียน contract ต้องปรับหลักให้ตรงกันก่อนคูณหรือหาร ถ้าลืมปรับ มูลค่าที่คำนวณได้จะผิดไปเป็นหลักสิบยกกำลัง

ราคาจาก oracle ตัดสินการชำระบัญชีอย่างไร

lending ส่วนใหญ่ใช้ตัวเลขที่เรียกว่า health factor วัดความปลอดภัยของบัญชีผู้กู้

health factor = (จำนวน ETH × ราคาจาก oracle × liquidation threshold) / ยอดหนี้
ถ้า health factor < 1  →  ใครก็ได้ชำระหนี้แทนบางส่วน แล้วรับหลักประกันในราคาลด

liquidation threshold คือสัดส่วนของมูลค่าหลักประกันที่นับเป็นความสามารถในการค้ำหนี้ เช่น 80% โปรโตคอลกันส่วนที่เหลือไว้เป็นกันชนสำหรับช่วงที่ราคาผันผวน ลองเปลี่ยนราคาที่ oracle รายงานด้านล่าง แล้วดูว่าราคาเพียงตัวเดียวเปลี่ยนสถานะของบัญชีได้อย่างไร ถ้า oracle รายงานต่ำเกินจริง บัญชีที่ปลอดภัยจะถูกชำระบัญชีโดยไม่สมควร ถ้ารายงานสูงเกินจริง ผู้กู้จะกู้ได้เกินมูลค่าหลักประกัน และโปรโตคอลจะมีหนี้เสีย

ประกันภัยแบบ parametric

ประกันแบบเดิมต้องให้ผู้เอาประกันยื่นเคลม และให้บริษัทประกันตรวจความเสียหาย ขั้นตอนนี้ช้า และผู้เอาประกันต้องเชื่อว่าบริษัทจะจ่ายจริง ประกันแบบ parametric เปลี่ยนเงื่อนไขการจ่ายเป็นค่าที่วัดได้ เช่น "ถ้าเที่ยวบินนี้ลงจอดช้ากว่ากำหนดเกิน 2 ชั่วโมง จ่าย 200 USDC" หรือ "ถ้าปริมาณฝนในอำเภอนี้ทั้งฤดูต่ำกว่า 300 มิลลิเมตร จ่าย 500 USDC ต่อไร่"

เมื่อเงื่อนไขเป็นตัวเลข smart contract ก็จัดการได้ทั้งหมด ผู้ซื้อจ่ายเบี้ยเข้า contract บริษัทประกันล็อกเงินชดเชยไว้ใน contract ทุกคนจึงตรวจได้ว่ามีเงินพอจ่าย เมื่อ oracle รายงานเวลาลงจอดหรือปริมาณฝน contract ก็จ่ายเงินทันทีโดยไม่ต้องยื่นเคลม และบริษัทปฏิเสธการจ่ายไม่ได้ ความน่าเชื่อถือของประกันจึงย้ายจากบริษัทประกันไปอยู่ที่ oracle ข้อจำกัดคือ basis risk ความเสียหายจริงอาจไม่ตรงกับค่าที่วัด เช่น สถานีวัดฝนบันทึกฝนปกติ แต่ไร่ของเกษตรกรที่อยู่ห่างออกไปแห้งแล้ง ผู้เอาประกันจึงไม่ได้เงินชดเชย

การสุ่มเลขด้วย VRF

เกมบนเชน ลอตเตอรี และการสุ่มคุณสมบัติของ NFT ตอน mint (บทที่ 12) ต้องการเลขสุ่มที่ไม่มีใครทำนายหรือเลือกได้ หัวข้อ 5.3 อธิบายว่า contract สุ่มเองอย่างปลอดภัยไม่ได้ เพราะทุกโหนดต้องได้ผลเดียวกัน ค่าตั้งต้นจึงต้องมาจากข้อมูลบนเชน ลองดูว่าค่าบนเชนแต่ละแบบมีจุดอ่อนอย่างไร

แหล่งค่าสุ่มใครโกงได้ และโกงอย่างไร
block.timestampผู้สร้างบล็อกเลือกเวลาได้ในช่วงหนึ่ง และทุกคนเห็นค่านี้ทันทีที่ธุรกรรมเข้าบล็อก
blockhash หรือ block.prevrandaoproposer เห็นค่าก่อนเผยแพร่บล็อก ถ้าผลไม่ถูกใจ proposer ไม่เสนอบล็อกนั้นก็ได้ โดยยอมเสียรางวัลของ slot นั้น (RANDAO ในหัวข้อ 8.3) ถ้ารางวัลจากเกมสูงกว่ารางวัลบล็อก การโกงแบบนี้ก็คุ้ม
ค่าบนเชนใด ๆ ที่อ่านในธุรกรรมเดียวกันผู้เล่นเขียน contract ของตัวเองมาเรียกเกม แล้วตรวจผลในธุรกรรมเดียวกัน ถ้าแพ้ก็สั่ง revert ทั้งธุรกรรม เสียแค่ค่า gas แล้วลองใหม่จนกว่าจะชนะ
เจ้าของเกมสุ่มนอกเชนแล้วส่งเข้ามาเจ้าของเกมเลือกเลขที่ตัวเองได้ประโยชน์ได้ และผู้เล่นตรวจไม่ได้

VRF (Verifiable Random Function) แก้ปัญหานี้ด้วยการเข้ารหัส oracle มีคู่กุญแจ private key (sk) และ public key (pk) ที่ลงทะเบียนไว้บนเชน เมื่อได้รับคำขอ oracle นำ seed ของคำขอนั้นมาคำนวณด้วย sk ได้ผลสองอย่าง คือ ค่าสุ่ม และหลักฐาน (proof) ว่าค่าสุ่มนี้คำนวณจาก seed และ sk จริง contract บนเชนใช้ pk ตรวจหลักฐานก่อนรับค่า VRF มีคุณสมบัติสามข้อที่แก้จุดอ่อนในตารางได้

  • ทำนายไม่ได้ (unpredictable): ผู้ที่ไม่มี sk คำนวณค่าสุ่มล่วงหน้าไม่ได้ ทั้งผู้เล่นและ proposer จึงไม่รู้ผลก่อน
  • ตรวจสอบได้ (verifiable): ใครก็ใช้ pk ตรวจได้ว่าค่าสุ่มมาจาก seed และ sk จริง oracle จึงส่งเลขที่แต่งขึ้นเองไม่ได้
  • มีผลเดียว (unique): seed หนึ่งค่ากับ sk หนึ่งดอกให้ค่าสุ่มที่ผ่านการตรวจได้เพียงค่าเดียว oracle จึงลองหลายค่าแล้วเลือกค่าที่ชอบไม่ได้

seed ต้องรวมข้อมูลที่ oracle รู้ล่วงหน้าไม่ได้ เช่น ค่าแฮชของบล็อกที่คำขอเข้าไปอยู่ ถ้าไม่เป็นเช่นนั้น oracle อาจคำนวณผลไว้ก่อน แล้วร่วมมือกับผู้เล่นบางราย

สิ่งที่ VRF ป้องกันไม่ได้ oracle ยังเลือกไม่ตอบได้เมื่อเห็นผลแล้วไม่ถูกใจ VRF ไม่ได้ป้องกันการไม่ตอบ แต่การไม่ตอบเห็นได้บนเชนและทำให้ oracle เสียชื่อเสียงและรายได้ ฝั่ง contract ต้องเขียนให้รัดกุมด้วย อย่าให้ผู้ใช้หรือเจ้าของขอเลขสุ่มใหม่ได้เมื่อไม่พอใจผลรอบแรก และอย่าให้ผู้เล่นยกเลิกหรือเปลี่ยนเดิมพันหลังส่งคำขอแล้ว ถ้าทำได้ ผู้ที่เห็นผลก่อนจะเลือกได้ว่าจะยอมรับผลรอบไหน

การใช้งานอื่น

การใช้งานโจทย์ที่แก้รูปแบบ
Proof of Reserveโทเคนที่อ้างว่ามีทรัพย์สินจริงหนุนหลัง เช่น stablecoin หรือ wrapped BTC ต้องให้ผู้ใช้ตรวจได้ว่ามีทรัพย์สินหนุนครบ oracle รายงานยอดทรัพย์สินสำรองขึ้นเชน contract หยุดออกโทเคนใหม่ได้ถ้ายอดสำรองไม่พอPush inbound
Automation (keeper)contract เริ่มทำงานเองไม่ได้ (หัวข้อ 5.2) งานที่ต้องทำตามเวลา เช่น ชำระบัญชีหรือปิดรอบลอตเตอรี จึงต้องมีบริการนอกเชนเฝ้าเงื่อนไขแล้วส่งธุรกรรมเข้ามาเรียกนอกเชนเรียกเข้าเชน
Cross-chain messagingcontract บนเชนหนึ่งต้องรู้ว่าเกิดอะไรขึ้นบนอีกเชนหนึ่ง เช่น ผู้ใช้ล็อกเหรียญไว้บนเชนต้นทางแล้ว เชนปลายทางจึงออกเหรียญตัวแทนให้ได้Inbound จากอีกเชน
ผลกีฬาและตลาดคาดการณ์ตัดสินผลเดิมพันหรือตลาดคาดการณ์ (prediction market) ตามผลจริงPull inbound หรือ optimistic oracle

สรุปท้ายบท

  • โจทย์: contract ตรวจได้เฉพาะสิ่งที่อยู่บนเชน แต่แอปจำนวนมากต้องรู้ราคา ผลการแข่งขัน สภาพอากาศ หรือเลขสุ่ม Oracle คือตัวเชื่อมที่นำข้อมูลเหล่านี้เข้ามา และใครคุม oracle ได้ก็คุมเงินใน contract ได้
  • 13.1: ทุกโหนดต้องรันธุรกรรมซ้ำแล้วได้ผลเดียวกัน (deterministic) EVM จึงไม่มีคำสั่งเรียกเครือข่ายภายนอก ข้อมูลต้องเข้ามาเป็นธุรกรรม เมื่อเป็นเช่นนั้น contract ก็ต้องเชื่อผู้ส่ง นี่คือ oracle problem
  • 13.2: Inbound นำข้อมูลเข้าเชน Outbound นำเหตุการณ์บนเชนออกไปสั่งระบบภายนอก Push คือฝ่ายที่มีข้อมูลส่งเอง เช่น price feed ที่อัปเดตตาม deviation threshold และ heartbeat Pull คือฝ่ายที่ต้องการข้อมูลร้องขอ เช่น request-response ที่ต้องแยกเป็นสองธุรกรรม
  • 13.3: Oracle รวมศูนย์ทำให้ทั้งระบบขึ้นกับ key ดอกเดียว DON ใช้หลายแหล่งข้อมูลและหลายโหนด แล้วรวมด้วยค่ามัธยฐาน ผู้โกงที่มีน้อยกว่าครึ่งจึงเปลี่ยนผลไม่ได้ Chainlink ใช้ OCR รวมรายงานนอกเชนแล้วส่งธุรกรรมเดียว
  • 13.4: Spot price จาก DEX pool เดียวบิดได้ด้วย flash loan ภายในธุรกรรมเดียว ป้องกันด้วย DON, TWAP, staleness check และ circuit breaker จุดล้มเหลวเดียวมีได้ทั้งที่ผู้ส่งข้อมูล แหล่งข้อมูล key ของผู้ดูแล และ feed ที่หยุดอัปเดต
  • 13.5: Price feed ใช้ตีมูลค่าหลักประกันและตัดสินการชำระบัญชี ประกันแบบ parametric จ่ายเงินอัตโนมัติตามค่าที่วัดได้ VRF ให้เลขสุ่มพร้อม proof ที่ตรวจบนเชนได้ oracle จึงเลือกผลเองไม่ได้ และผู้อื่นทำนายผลไม่ได้

คำศัพท์ที่ควรจำ

คำศัพท์ความหมาย
Oracleส่วนประกอบที่ส่งข้อมูลระหว่างนอกเชนกับบนเชน ไม่ใช่แหล่งข้อมูลเอง
Oracle problemcontract ต้องเชื่อผู้ส่งข้อมูลภายนอก ความปลอดภัยจึงไม่เกินความน่าเชื่อถือของข้อมูล
Deterministicข้อมูลตั้งต้นเดียวกันให้ผลเดียวกันทุกครั้ง ทุกเครื่อง ทุกเวลา
Inbound / Outboundทิศของข้อมูล: เข้าสู่เชน / ออกจากเชน
Push / Pullฝ่ายที่มีข้อมูลเริ่มส่ง / ฝ่ายที่ต้องการข้อมูลร้องขอ
Deviation threshold / Heartbeatอัปเดตเมื่อราคาเปลี่ยนเกินเกณฑ์ / อัปเดตเมื่อครบเวลา แม้ราคาไม่เปลี่ยน
DONDecentralized oracle network เครือข่ายโหนด oracle หลายรายที่รวมผลด้วยกติกาที่ผู้โกงส่วนน้อยเปลี่ยนไม่ได้
OCROff-Chain Reporting ของ Chainlink โหนดรวมรายงานนอกเชนแล้วส่งธุรกรรมเดียวพร้อมลายเซ็นหลายราย
Spot price / TWAPราคา ณ ขณะนั้นของ pool / ราคาเฉลี่ยถ่วงตามเวลา ข้ามหลายบล็อก
Flash loanกู้และคืนในธุรกรรมเดียว ถ้าไม่คืน ธุรกรรมทั้งหมด revert
Single point of failureจุดเดียวที่ถ้าล้ม ทั้งระบบล้มตาม
Health factor(หลักประกัน × ราคา × liquidation threshold) / หนี้ ต่ำกว่า 1 แล้วถูกชำระบัญชีได้
Parametric insurance / Basis riskประกันที่จ่ายตามค่าที่วัดได้ / ความเสี่ยงที่ค่าที่วัดไม่ตรงกับความเสียหายจริง
VRFVerifiable Random Function ค่าสุ่มพร้อม proof ที่ทำนายไม่ได้ ตรวจได้ และมีผลเดียวต่อ seed
