ลองนึกถึงเว็บระดมทุนทั่วไป ผู้ใช้โอนเงินเข้าบัญชีธนาคารของบริษัท บริษัทเก็บรายชื่อผู้สนับสนุนและยอดเงินไว้ในฐานข้อมูลของตัวเอง และเขียนกติกาไว้บนหน้าเว็บว่าถ้าไม่ครบเป้าจะคืนเงิน ผู้ใช้ต้องเชื่อว่าบริษัทจะทำตามที่เขียนไว้ เพราะบริษัทแก้ยอดในฐานข้อมูลได้ เปลี่ยนกติกาได้ ปิดบัญชีผู้ใช้ได้ หรือปิดบริการแล้วหายไปพร้อมเงินก็ได้ ผู้ใช้ไม่มีทางตรวจเองว่าเงินยังอยู่ครบหรือไม่

บทที่ 5 แสดงว่า smart contract ย้ายกติกาและเงินไปไว้บน blockchain ได้ ทุกโหนดรันโค้ดเดียวกัน ทุกคนอ่านยอดได้ และเจ้าของแก้โค้ดหลัง deploy ไม่ได้ แต่ contract เพียงอย่างเดียวยังไม่พอสำหรับแอปที่คนทั่วไปใช้ และยังมีคำถามตามมาอีกหลายข้อ

11.1ความแตกต่างระหว่าง DApp กับแอปพลิเคชันทั่วไป

ปัญหาของแอปที่มีเจ้าของเพียงรายเดียว

แอปทั่วไปทำงานแบบ client-server ผู้ให้บริการถือทั้งเซิร์ฟเวอร์ ฐานข้อมูล และกติกา ผู้ใช้จึงอยู่ในสถานะเดียวกับลูกค้าธนาคารในบทที่ 1 คือต้องเชื่อใจตัวกลาง (trusted third party) ตัวอย่างที่เห็นบ่อยมีดังนี้

  • บัญชีโดนระงับ: ผู้ให้บริการปิดบัญชีหรืออายัดเงินได้ ผู้ใช้ทำได้เพียงร้องเรียน
  • กติกาเปลี่ยนฝ่ายเดียว: ผู้ให้บริการขึ้นค่าธรรมเนียมหรือเปลี่ยนเงื่อนไขได้ทุกเมื่อ
  • ผู้ใช้ตรวจไม่ได้: exchange ที่ประกาศว่าถือเงินของลูกค้าครบ อาจนำเงินไปใช้ทางอื่นโดยที่ลูกค้าไม่รู้ กรณี FTX ล้มละลายในปี 2022 เป็นตัวอย่างที่ชัดเจน
  • บริการปิดตัว: เมื่อบริษัทเลิกกิจการ ข้อมูลและสิทธิ์ของผู้ใช้หายไปพร้อมเซิร์ฟเวอร์

DApp ย้ายส่วนที่ต้องเชื่อใจไปไว้บน blockchain

DApp (Decentralized Application) คือแอปที่เก็บกติกาหลัก (business logic) และข้อมูลสำคัญไว้ใน smart contract ผู้ใช้ยืนยันตัวด้วยการลงลายเซ็นจาก wallet ของตัวเอง ไม่ใช้ชื่อผู้ใช้กับรหัสผ่านที่บริษัทเก็บไว้ ผลคือผู้ใช้ตรวจจาก chain ได้เองว่าเงินยังอยู่ครบหรือไม่ และกติกาเป็นอย่างไร โดยไม่ต้องเชื่อคำพูดของผู้ให้บริการ

ประเด็นแอปทั่วไปDApp
กติกาและข้อมูลอยู่ที่เซิร์ฟเวอร์และฐานข้อมูลของบริษัทsmart contract บน blockchain
การยืนยันตัวตน (authentication)ชื่อผู้ใช้และรหัสผ่าน บริษัท reset ให้ได้ลายเซ็นจาก private key ทำ key หายก็เข้าบัญชีไม่ได้อีก (บทที่ 14)
ผู้แก้กติกาได้บริษัท แก้ได้ทุกเมื่อแก้โค้ดไม่ได้ ยกเว้นออกแบบให้อัปเกรดได้ แต่แบบนั้นต้องมีผู้ถือสิทธิ์อัปเกรด
ตรวจสอบได้หรือไม่ไม่ได้ ต้องเชื่อรายงานของบริษัทได้ โค้ดและ state อ่านได้จาก chain
ผู้จ่ายค่าประมวลผลบริษัทจ่ายค่าเซิร์ฟเวอร์ผู้ใช้จ่าย gas ทุกครั้งที่แก้ state
ความเร็วตอบกลับในเสี้ยววินาทีรอเข้าบล็อกราว 12 วินาที และรอ finality ราว 13 นาที (บทที่ 8)
ความเป็นส่วนตัว (privacy)บริษัทเห็นข้อมูล คนนอกไม่เห็นทุกคนเห็นธุรกรรมและ state ทั้งหมด
แก้บั๊กแก้แล้ว deploy ใหม่ได้ทันทีต้อง deploy contract ใหม่แล้วย้ายผู้ใช้ หรืออัปเกรดผ่าน proxy (contract ตัวกลางที่เปลี่ยน address ของ contract ปลายทางได้ บทที่ 5)
ต่อยอดจากแอปอื่นผ่าน API ที่เจ้าของเปิดหรือปิดได้contract ใดก็เรียก contract อื่นได้โดยไม่ต้องขออนุญาต (composability)

ตารางนี้แสดงว่า DApp ไม่ได้ดีกว่าแอปทั่วไปในทุกด้าน DApp ยอมเสียความเร็ว ค่าใช้จ่าย และความเป็นส่วนตัว เพื่อให้ผู้ใช้ไม่ต้องเชื่อใจผู้ให้บริการ ถ้าแอปไม่มีปัญหาเรื่องความเชื่อใจตั้งแต่ต้น เช่น แอปจดบันทึกส่วนตัว ย้ายไปเป็น DApp ก็มีแต่ต้นทุนเพิ่ม

ความเป็น decentralized มีหลายระดับ DApp จำนวนมากยังมีส่วนที่รวมศูนย์ (centralized) เช่น หน้าเว็บอยู่บนเซิร์ฟเวอร์ของบริษัท ใช้ RPC node ของผู้ให้บริการรายเดียว หรือมี admin key ที่อัปเกรด contract ได้ คำถามที่ใช้ทดสอบคือ "ถ้าบริษัทหายไปพรุ่งนี้ ผู้ใช้ยังถอนเงินออกจาก contract ได้หรือไม่" ตัวอย่างเช่น ในปี 2021 Uniswap Labs เอาเหรียญบางกลุ่มออกจากหน้าเว็บของตน แต่ contract ของ Uniswap ยังซื้อขายเหรียญเหล่านั้นได้ตามเดิม ผู้ใช้ที่เรียก contract ผ่านหน้าเว็บอื่นหรือเรียกเองจึงไม่ได้รับผลกระทบ
ประเด็นที่มักออกสอบ DApp ต่างจากแอปทั่วไปที่ "ใครเป็นผู้ถือกติกาและข้อมูล" ไม่ใช่ที่หน้าตาของแอป หน้าเว็บของ DApp อาจเหมือนเว็บทั่วไปทุกอย่าง ข้อสอบมักให้เลือกข้อที่ไม่ใช่ลักษณะของ DApp เช่น "ผู้ให้บริการ reset รหัสผ่านให้ได้" หรือ "แก้บั๊กได้ทันทีโดยไม่ต้อง deploy ใหม่"

11.2สถาปัตยกรรม DApp: Frontend, Wallet, Smart contract และ IPFS

ทำไม contract อย่างเดียวไม่พอ

contract รับได้เฉพาะธุรกรรมที่ลงลายเซ็นแล้ว แต่ผู้ใช้ทั่วไปเขียน calldata เองไม่เป็น นอกจากนี้ contract ยังแสดงหน้าจอไม่ได้ เก็บไฟล์ใหญ่ไม่ไหวเพราะ storage บน chain แพงมาก และดึงข้อมูลภายนอกอย่างราคาเหรียญเองไม่ได้ ปัญหาข้อสุดท้ายแก้ด้วย oracle ในบทที่ 13 ส่วนปัญหาที่เหลือแก้ด้วยส่วนประกอบในตารางด้านล่าง แต่ละส่วนแก้ปัญหาคนละข้อ

ส่วนประกอบหน้าที่ถ้าไม่มี
Frontend (HTML, CSS, JavaScript)แสดงหน้าจอ แปลงการกดปุ่มเป็นการเรียกฟังก์ชันของ contract และแสดงผลที่อ่านกลับมาผู้ใช้ต้องเขียน calldata เองหรือใช้ Remix
Wallet (เช่น MetaMask)เก็บ private key แสดงรายละเอียดธุรกรรมให้ผู้ใช้ยืนยัน แล้วลงลายเซ็นหน้าเว็บต้องถือ private key เอง เว็บที่ไม่หวังดีก็นำ key ไปได้ทันที
RPC node (provider)โหนด Ethereum ที่รับคำขอ JSON-RPC จากแอป เช่น อ่าน state หรือส่งธุรกรรมเข้าเครือข่ายเบราว์เซอร์ติดต่อเครือข่าย peer-to-peer โดยตรงไม่ได้
Smart contractเก็บกติกาและ state ที่ต้องเชื่อถือได้ เช่น ยอดเงินและสิทธิ์กลับไปเป็นแอปที่ต้องเชื่อใจเซิร์ฟเวอร์
IPFS (InterPlanetary File System)เก็บไฟล์ใหญ่นอก chain เช่น รูป metadata หรือไฟล์ของหน้าเว็บ แล้วอ้างถึงไฟล์ด้วยค่าแฮชของเนื้อหาต้องเก็บไฟล์บน chain ซึ่งแพงเกินไป หรือเก็บบนเซิร์ฟเวอร์ที่เจ้าของเปลี่ยนไฟล์ได้
Indexer (ไม่บังคับ เช่น The Graph)เก็บ event จาก chain ลงฐานข้อมูลเพื่อค้นได้เร็ว เช่น ประวัติการโหวตทั้งหมดfrontend ต้องไล่อ่าน event ย้อนหลังจากโหนดเอง และใช้เวลานาน

RPC node: ทางเข้าสู่เครือข่าย

เบราว์เซอร์ไม่ได้เป็นโหนด Ethereum จึงต้องส่งคำขอ JSON-RPC ผ่านโหนดที่เปิดบริการไว้ คำขอที่ใช้บ่อย เช่น eth_call (จำลองการเรียกฟังก์ชันเพื่ออ่านค่า) eth_getBalance หรือ eth_sendRawTransaction (ส่งธุรกรรมที่ลงลายเซ็นแล้ว) แอปส่วนใหญ่ใช้โหนดของผู้ให้บริการ เช่น Infura หรือ Alchemy เพราะรันโหนดเองต้องใช้พื้นที่ดิสก์มากและต้องดูแลต่อเนื่อง ข้อเสียคือผู้ให้บริการกลายเป็นจุดที่ต้องเชื่อใจ โหนดที่ตอบผิดอาจแสดงยอดที่ไม่จริง แต่ปลอมลายเซ็นของผู้ใช้ไม่ได้ ผู้ให้บริการจึงย้ายเงินของผู้ใช้ไม่ได้ ทำได้เพียงไม่ส่งธุรกรรมต่อหรือแสดงข้อมูลผิด

ทำไมไม่เก็บไฟล์ไว้บน chain

EVM คิดค่าเขียน storage ช่องใหม่ราว 20,000 gas ต่อ 32 ไบต์ ไฟล์รูปขนาด 1 MB ต้องใช้ 32,768 ช่อง จึงใช้ gas ราว 655 ล้าน ส่วนเพดาน gas ของหนึ่งบล็อก (block gas limit) อยู่ในระดับหลายสิบล้าน ไฟล์นี้จึงใช้ gas เกินเพดานหลายเท่า และเก็บในบล็อกเดียวไม่ได้ ถ้า base fee เป็น 10 Gwei ค่าธรรมเนียมจะสูงถึงราว 6.5 ETH DApp จึงเก็บไฟล์ไว้นอก chain และให้ contract เก็บเพียงตัวอ้างอิงสั้น ๆ

ถ้าตัวอ้างอิงเป็น URL ธรรมดา เช่น https://example.com/cat.png เจ้าของเซิร์ฟเวอร์ก็เปลี่ยนรูปหรือลบไฟล์ได้ทุกเมื่อ การที่ข้อมูลบน chain แก้ไม่ได้จึงไม่ช่วยอะไร เพราะ URL นั้นชี้ไปยังไฟล์ที่เจ้าของเซิร์ฟเวอร์แก้ได้ IPFS แก้ปัญหานี้ด้วย content addressing คือเรียกไฟล์ด้วยค่าแฮชของเนื้อหา แทนที่จะเรียกด้วยตำแหน่งที่เก็บ

  • CID (Content Identifier): ตัวระบุไฟล์ที่คำนวณจากค่าแฮชของเนื้อหา CID รุ่นแรกขึ้นต้นด้วย Qm… รุ่นใหม่มักขึ้นต้นด้วย bafy… ไฟล์ที่ต่างกันแม้หนึ่งบิตจะได้ CID ต่างกัน ตามคุณสมบัติของฟังก์ชันแฮชในบทที่ 0
  • ตรวจได้เอง: ผู้ขอไฟล์คำนวณค่าแฮชของสิ่งที่ได้รับแล้วเทียบกับ CID จึงรับไฟล์จากโหนดใดก็ได้โดยไม่ต้องเชื่อใจโหนดนั้น สำหรับไฟล์ใหญ่ IPFS แบ่งไฟล์เป็นก้อน (chunk) ผู้ขอจึงโหลดแต่ละก้อนจากคนละโหนดได้ และตรวจทีละก้อนได้ทันทีโดยไม่ต้องรอให้ครบทั้งไฟล์ IPFS เชื่อมค่าแฮชของก้อนเหล่านี้เป็น Merkle DAG ตามแนวคิดเดียวกับ Merkle tree ในบทที่ 3
  • ไฟล์ไม่ได้อยู่ถาวรเอง: IPFS เป็นเพียงวิธีค้นหาและส่งไฟล์ โหนดที่โหลดไฟล์มาจะเก็บไว้เพียงชั่วคราว และลบทิ้งเมื่อต้องการพื้นที่คืน (garbage collection) ไฟล์จึงหายไปถ้าไม่มีโหนดใดเลือกเก็บไว้ถาวร การสั่งให้โหนดเก็บไฟล์ไว้ถาวรเรียกว่า pin (pinning) ผู้ทำ DApp จึงต้อง pin ไฟล์ไว้บนโหนดของตัวเอง ใช้บริการ pinning หรือจ่ายให้เครือข่ายอย่าง Filecoin เก็บรักษา
  • แก้ไฟล์แล้ว CID เปลี่ยน: หน้าเว็บที่ต้องอัปเดตจึงใช้ชื่อที่ชี้ไปยัง CID ล่าสุด เช่น ชื่อ ENS (Ethereum Name Service) อย่าง app.eth แล้วแก้ค่า CID ที่ชื่อนั้นชี้ไปเมื่อมีรุ่นใหม่
หน้าเว็บก็เป็นจุดโจมตีได้ ถ้า contract ปลอดภัยแต่หน้าเว็บอยู่บนเซิร์ฟเวอร์ทั่วไป ผู้โจมตีที่ยึด DNS หรือเซิร์ฟเวอร์ได้ก็เปลี่ยน JavaScript ให้ขอลายเซ็นธุรกรรมที่ส่งเงินไปให้ตัวเองได้ ผู้ใช้เห็นหน้าเว็บหน้าตาเหมือนเดิม จึงกดยืนยันโดยไม่รู้ตัว ถ้าวางหน้าเว็บไว้บน IPFS แล้วเปิดผ่าน CID ความเสี่ยงนี้จะลดลง เพราะไม่มีใครเปลี่ยนเนื้อหาของ CID เดิมได้ แต่ผู้ใช้ก็ยังต้องอ่านรายละเอียดในหน้าต่างของ wallet ก่อนยืนยันทุกครั้ง

11.3การเชื่อม Frontend กับ Contract: ABI, provider และ signer (ethers.js)

ทำไมต้องมี ABI

บน chain มีเพียง bytecode ของ contract ไม่มีชื่อฟังก์ชันหรือชนิดของพารามิเตอร์ บทที่ 5 อธิบายว่าธุรกรรมเรียกฟังก์ชันด้วย function selector คือ 4 ไบต์แรกของค่าแฮช Keccak-256 ของ function signature ค่าแฮชย้อนกลับไม่ได้ frontend จึงคำนวณชื่อฟังก์ชันจาก bytecode โดยตรงไม่ได้ ทำได้เพียงเทียบ selector กับฐานข้อมูล signature ที่มีผู้รวบรวมไว้ เช่น 4byte.directory ฐานข้อมูลนี้ไม่ครบทุกฟังก์ชัน และไม่บอกชนิดของค่าที่คืนมา นอกจากนี้ เมื่อ contract คืนค่ากลับมา frontend ได้รับเพียงข้อมูลดิบเป็นช่องละ 32 ไบต์ ถ้าไม่รู้ชนิดของค่าที่คืนมา ก็แปลข้อมูลนั้นไม่ได้

ABI (Application Binary Interface) แก้ปัญหานี้ ABI บอกว่า contract มีฟังก์ชันอะไร แต่ละฟังก์ชันรับพารามิเตอร์และคืนค่าชนิดใด มี state mutability แบบใด และ contract ปล่อย event อะไรบ้าง คอมไพเลอร์สร้าง ABI ออกมาพร้อม bytecode ในรูป JSON (ใน Remix คือปุ่มคัดลอก ABI ในแท็บ Solidity Compiler ตามบทที่ 6) chain ไม่ได้เก็บ ABI ไว้ ผู้ทำ frontend จึงต้องเอา ABI มาจากผลการคอมไพล์ หรือจากหน้า contract บน Etherscan ที่ยืนยันซอร์สโค้ดแล้ว (verified contract)

  { "type": "function", "name": "count",     "inputs": [], "outputs": [{ "type": "uint256" }], "stateMutability": "view" },
  { "type": "function", "name": "increment", "inputs": [], "outputs": [],                     "stateMutability": "nonpayable" },
  { "type": "function", "name": "decrement", "inputs": [], "outputs": [],                     "stateMutability": "nonpayable" }
]

ABI ข้างบนเป็นของ Counter contract จากบทที่ 6 (ตัดฟังก์ชัน getCount ออกเพื่อให้สั้น) เมื่อมี ABI แล้ว library ฝั่ง frontend จะแปลงการเรียกฟังก์ชันเป็นข้อมูลที่ส่งให้ EVM (encode) และแปลงค่าที่ได้กลับมา (decode) ให้เอง

ทำไมต้องแยก provider กับ signer

การอ่านกับการเขียนต้องการสิ่งต่างกัน การอ่าน state ต้องการเพียงโหนดที่ตอบคำถามได้ ไม่ต้องใช้ private key และไม่เสีย gas ส่วนการแก้ state ต้องมีธุรกรรมที่ลงลายเซ็นด้วย private key ของผู้ใช้ ถ้าให้หน้าเว็บถือ private key เอง เว็บที่ไม่หวังดีก็นำ key ไปได้ทันที wallet จึงเก็บ key ไว้กับตัวเอง แล้วเปิดช่องทางให้หน้าเว็บขอลายเซ็นผ่านอ็อบเจกต์ window.ethereum (มาตรฐาน EIP-1193) ผู้ใช้ต้องกดยืนยันในหน้าต่างของ wallet ทุกครั้ง library อย่าง ethers.js แยกสองบทบาทนี้เป็นอ็อบเจกต์สองชนิด คือ provider และ signer

ProviderSigner
คืออะไรการเชื่อมต่อแบบอ่านอย่างเดียวไปยังโหนดบัญชีที่ลงลายเซ็นได้ ใน DApp คือบัญชีใน wallet ของผู้ใช้
ใช้ทำอะไรอ่าน state, ยอดเงิน, เลขบล็อก, event และเรียกฟังก์ชัน view / pure ผ่าน eth_callส่งธุรกรรมที่แก้ state, deploy contract และลงลายเซ็นข้อความ
ต้องใช้ private keyไม่ต้องต้อง แต่ key อยู่ใน wallet หน้าเว็บไม่เห็น
เสีย gasไม่เสียเสียเมื่อส่งธุรกรรม
ผู้ใช้ต้องกดยืนยันไม่ต้องต้องยืนยันใน wallet ทุกครั้ง
ตัวอย่างใน ethers v6new ethers.BrowserProvider(window.ethereum) หรือ new ethers.JsonRpcProvider(url)await provider.getSigner()

ตัวอย่างโค้ด: อ่านและเขียน Counter ด้วย ethers.js v6

import { ethers } from "ethers";                          // ethers รุ่น 6

const address = "0x…";                                   // address ของ Counter ที่ deploy แล้ว
const abi = [                                            // human-readable ABI รูปแบบย่อที่ ethers อ่านได้
  "function count() view returns (uint256)",
  "function increment()",
];

// 1) provider: เชื่อมต่อโหนดผ่าน wallet ใช้อ่านอย่างเดียว
const provider = new ethers.BrowserProvider(window.ethereum);
const counter  = new ethers.Contract(address, abi, provider);
const n = await counter.count();                         // eth_call ไม่เสีย gas ได้ค่าเป็น bigint เช่น 5n

// 2) signer: ขอสิทธิ์เข้าถึงบัญชี MetaMask จะถามผู้ใช้ในครั้งแรก
const signer = await provider.getSigner();
const tx = await counter.connect(signer).increment();   // MetaMask ขึ้นหน้าต่างให้ยืนยัน
console.log("tx hash:", tx.hash);                       // ธุรกรรมอยู่ใน mempool แล้ว แต่ยังไม่เข้าบล็อก

// 3) รอให้ธุรกรรมเข้าบล็อก แล้วอ่านค่าใหม่
const receipt = await tx.wait();                        // ได้ receipt ที่มี status, gasUsed, logs
console.log(receipt.status === 1 ? "สำเร็จ" : "ล้มเหลว", await counter.count());

โค้ดนี้แสดงขั้นตอนที่เกิดขึ้นทุกครั้งที่เขียน state ซึ่งมีสี่ขั้น

  1. frontend ใช้ ABI สร้าง calldata แล้วส่งคำขอ eth_sendTransaction ไปที่ wallet คำขอนี้ยังไม่มีลายเซ็น
  2. wallet แสดงรายละเอียดและค่า gas ให้ผู้ใช้ตรวจ
  3. เมื่อผู้ใช้ยืนยัน wallet ลงลายเซ็น แล้วส่งธุรกรรมที่ลงลายเซ็นแล้วไปที่ RPC node ด้วย eth_sendRawTransaction
  4. frontend ได้ transaction hash กลับมาทันที แต่ต้องรอ tx.wait() จนธุรกรรมเข้าบล็อกก่อน จึงจะรู้ว่าสำเร็จหรือ revert

สองคำสั่งนี้ต่างกันที่ลายเซ็น eth_sendTransaction ขอให้ผู้ถือ key ลงลายเซ็นแล้วส่งธุรกรรมให้ ส่วน eth_sendRawTransaction รับธุรกรรมที่ลงลายเซ็นเสร็จแล้ว RPC node ของผู้ให้บริการไม่ได้ถือ key ของผู้ใช้ wallet จึงลงลายเซ็นเองแล้วส่งด้วยคำสั่งหลัง

ethers v5 กับ v6 เอกสารและตัวอย่างรุ่นเก่าจำนวนมากใช้ ethers v5 ซึ่งเขียนต่างออกไป เช่น v5 ใช้ new ethers.providers.Web3Provider(window.ethereum) และ provider.getSigner() ไม่ต้อง await ส่วน v6 เปลี่ยนเป็น BrowserProvider และ await provider.getSigner() สำหรับตัวเลขขนาดใหญ่ v5 ใช้ BigNumber ส่วน v6 ใช้ bigint ของ JavaScript ถ้าโค้ดตัวอย่างรันไม่ผ่าน ให้ตรวจรุ่นของ ethers ก่อน
ลงลายเซ็นโดยไม่อ่าน (blind signing) หน้าเว็บเป็นผู้เลือกว่าจะขอให้ลงลายเซ็นธุรกรรมใด และเขียนข้อความบนหน้าเว็บอย่างไรก็ได้ หน้าเว็บที่ไม่หวังดีอาจเขียนว่า "รับของรางวัลฟรี" แต่ขอให้ผู้ใช้ลงลายเซ็นธุรกรรม approve ที่อนุญาตให้ address ของผู้โจมตีย้ายเหรียญทั้งหมดของผู้ใช้ไปได้ (หัวข้อ 12.3) signer ที่แยกไว้ใน wallet ช่วยได้เฉพาะเมื่อผู้ใช้อ่านหน้าต่างยืนยันจริง hardware wallet ในบทที่ 14 แสดงรายละเอียดบนจอของอุปกรณ์เอง จึงยังแสดงข้อมูลจริง แม้มัลแวร์ (malware) บนคอมพิวเตอร์จะแก้สิ่งที่แสดงบนจอคอมพิวเตอร์
ประเด็นที่มักออกสอบ โจทย์มักถามว่าการกระทำใดต้องใช้ signer การอ่านค่าผ่านฟังก์ชัน view ใช้ provider อย่างเดียว ไม่เสีย gas และไม่มีหน้าต่างของ wallet ขึ้น ส่วนการเรียกฟังก์ชันที่แก้ state ต้องใช้ signer เสีย gas และผู้ใช้ต้องยืนยัน อีกข้อที่พบบ่อยคือ "frontend รู้ได้อย่างไรว่า contract มีฟังก์ชันอะไร" คำตอบคือจาก ABI ไม่ใช่จาก chain

11.4DAO: การเสนอ การลงมติ และการดำเนินการตามกติกาในโค้ด

contract แก้ไม่ได้ แต่โครงการยังต้องตัดสินใจ

DApp ที่ใช้งานจริงยังต้องเปลี่ยนแปลงอยู่เสมอ เช่น ปรับอัตราค่าธรรมเนียม เพิ่มเหรียญที่รองรับ อัปเกรด contract ผ่าน proxy หรือใช้เงินกองกลาง (treasury) จ้างนักพัฒนา คำถามคือใครมีสิทธิ์สั่ง ทางเลือกหลักมีสามแบบ

ผู้ถือสิทธิ์ข้อดีปัญหา
owner key ของคนเดียว (modifier onlyOwner ในบทที่ 5)ง่าย ตัดสินใจได้เร็วถ้า key หาย ก็สั่งอะไรไม่ได้อีก ถ้า key โดนขโมยหรือเจ้าของคิดโกง ผู้ถือ key ก็ย้ายเงินทั้งหมดได้ ผู้ใช้จึงกลับไปเชื่อใจคนคนเดียว
multisig เช่น ต้องมีลายเซ็น 3 จาก 5 คนkey หายหรือโดนขโมยหนึ่งดอกยังไม่เสียหายอำนาจยังอยู่กับกลุ่มเล็ก ผู้ใช้ส่วนใหญ่ไม่มีเสียง
DAOผู้ถือเหรียญทุกคนเสนอและลงมติได้ และ contract ทำตามมติเองตัดสินใจช้า และอาจโดนโจมตีผ่านกติกาการโหวต (ดูหัวข้อย่อย "ปัญหาที่ DAO ยังต้องเผชิญ")

DAO (Decentralized Autonomous Organization) คือองค์กรที่เขียนกติกาการตัดสินใจไว้ใน smart contract คำว่า autonomous ไม่ได้แปลว่าไม่มีคนเกี่ยวข้อง คนยังเป็นผู้เสนอและโหวต แต่เมื่อมติผ่านแล้ว contract เป็นผู้ดำเนินการเอง ไม่มีใครปฏิเสธหรือแก้ผลระหว่างทางได้ และเงินกองกลางก็อยู่ใน contract ไม่ได้อยู่ในบัญชีของใคร

ส่วนประกอบของ DAO

  • Governance token: เหรียญที่ใช้นับสิทธิ์ออกเสียง (voting power) ส่วนใหญ่ใช้หลัก 1 เหรียญ = 1 เสียง หลายระบบกำหนดให้ผู้ถือ delegate สิทธิ์ให้ตัวเองหรือผู้อื่นก่อน ระบบจึงจะนับเสียงของเหรียญนั้น เหตุผลคือเหรียญแบบ ERC20Votes ต้องบันทึกยอดย้อนหลัง (checkpoint) ไว้ใช้ตอน snapshot ถ้าบันทึกทุกครั้งที่โอนเหรียญ ผู้โอนทุกคนจะเสีย gas เพิ่ม เหรียญจึงบันทึกเฉพาะบัญชีที่ delegate แล้ว ผู้ที่ไม่มีเวลาติดตามทุกข้อเสนอก็มอบเสียงให้ผู้แทนได้
  • Proposal: ข้อเสนอไม่ได้เป็นเพียงข้อความ แต่มีรายการคำสั่งที่จะให้ contract ทำ คือ target (address ปลายทาง) value (จำนวน ETH) และ calldata (ฟังก์ชันกับพารามิเตอร์) พร้อมคำอธิบาย ผู้โหวตจึงรู้แน่ชัดว่าถ้าผ่านแล้วจะเกิดอะไร
  • กติกาการลงมติ: เกณฑ์ขั้นต่ำในการเสนอ (proposal threshold) ระยะรอก่อนเริ่มโหวต (voting delay) ระยะเวลาโหวต (voting period) และองค์ประชุม (quorum)
  • Timelock: contract ที่ถือเงินกองกลางและสิทธิ์ admin คำสั่งทุกข้อที่ผ่าน timelock ต้องรอครบเวลาที่กำหนดก่อนมีผล

ทำไมแต่ละกติกาต้องมี

กติกาแต่ละข้อของ DAO ปิดช่องโจมตีหนึ่งช่อง ถ้าตัดข้อใดออก ผู้ถือเหรียญกลุ่มเล็กหรือผู้โจมตีจะยึดเงินกองกลางได้ง่ายขึ้น

กติกามีไว้เพื่อถ้าไม่มี
Proposal threshold (ต้องถือเหรียญขั้นต่ำจึงเสนอได้)กันข้อเสนอขยะ (spam proposal)ผู้โจมตีส่งข้อเสนอจำนวนมากจนผู้โหวตตรวจไม่ทัน
Voting delayให้ผู้ถือเหรียญอ่านข้อเสนอ และ delegate สิทธิ์ก่อนนับเสียงผู้เสนอเปิดโหวตทันทีขณะที่คนอื่นยังไม่รู้ว่ามีข้อเสนอ
Snapshot ของ voting power (นับยอดถือ ณ บล็อกที่เริ่มโหวต)ให้เหรียญแต่ละเหรียญโหวตได้ครั้งเดียวโหวตแล้วโอนเหรียญไปอีกบัญชีแล้วโหวตซ้ำได้ หรือยืมเหรียญมาโหวตแล้วคืน
Voting periodให้ผู้ถือเหรียญในทุกเขตเวลา (time zone) มีโอกาสโหวตผลขึ้นกับว่าใครออนไลน์อยู่ในช่วงสั้น ๆ
Quorum (เสียงรวมต้องถึงสัดส่วนขั้นต่ำของเหรียญทั้งหมด)กันข้อเสนอผ่านเมื่อมีผู้มาโหวตน้อยกลุ่มเล็กผ่านข้อเสนอได้ในช่วงที่คนส่วนใหญ่ไม่สนใจ
Timelockเว้นระยะระหว่างวันที่มติผ่านกับวันที่มีผลข้อเสนอที่ซ่อนคำสั่งอันตรายมีผลทันที ผู้ไม่เห็นด้วยถอนเงินออกไม่ทัน

ค่าตั้งต้นในตัวอย่างโค้ดของ OpenZeppelin Governor คือ voting delay 1 วัน voting period 1 สัปดาห์ และ quorum 4% ของเหรียญทั้งหมด แต่ละ DAO ตั้งค่าเหล่านี้เองตามความเหมาะสม จึงไม่ใช่ตัวเลขมาตรฐานที่ต้องจำ

contract ทำตามมติเอง

contract ด้านล่างเป็น DAO แบบย่อสำหรับทำความเข้าใจ ไม่มี timelock และกันการโจมตีไม่ครบทุกแบบ จุดที่ควรสังเกตคือ execute เรียก calldata ที่บันทึกไว้ตั้งแต่ตอนเสนอ ไม่มีใครเปลี่ยนคำสั่งหลังโหวตได้

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

interface IVotes {                                      // เหรียญที่จำยอดย้อนหลังได้ เช่น ERC20Votes
    function getPastVotes(address who, uint256 blockNumber) external view returns (uint256);
    function getPastTotalSupply(uint256 blockNumber) external view returns (uint256);
}

contract MiniDAO {
    struct Proposal {
        address target; uint256 value; bytes data;     // คำสั่งที่จะทำเมื่อผ่าน
        uint256 snapshot; uint256 deadline;             // บล็อกที่นับยอดถือ และบล็อกที่ปิดโหวต
        uint256 forVotes; uint256 againstVotes; bool executed;
    }
    IVotes public immutable token;
    Proposal[] public proposals;
    mapping(uint256 => mapping(address => bool)) public voted;

    constructor(IVotes t) { token = t; }
    receive() external payable {}                       // รับ ETH เข้ากองกลาง

    function propose(address target, uint256 value, bytes calldata data) external returns (uint256 id) {
        proposals.push(Proposal(target, value, data, block.number + 7200, block.number + 57600, 0, 0, false));
        return proposals.length - 1;                    // ตัวอย่าง: delay ราว 1 วัน โหวตราว 1 สัปดาห์ (12 วินาทีต่อบล็อก)
    }

    function vote(uint256 id, bool support) external {
        Proposal storage p = proposals[id];
        require(block.number > p.snapshot && block.number <= p.deadline, "not active");
        require(!voted[id][msg.sender], "already voted");
        uint256 weight = token.getPastVotes(msg.sender, p.snapshot);   // ยอด ณ snapshot ไม่ใช่ยอดตอนนี้
        voted[id][msg.sender] = true;
        if (support) p.forVotes += weight; else p.againstVotes += weight;
    }

    function execute(uint256 id) external {
        Proposal storage p = proposals[id];
        require(block.number > p.deadline, "voting not ended");
        require(!p.executed, "done");
        uint256 quorum = token.getPastTotalSupply(p.snapshot) * 4 / 100;
        require(p.forVotes + p.againstVotes >= quorum, "no quorum");
        require(p.forVotes > p.againstVotes, "defeated");
        p.executed = true;                              // แก้ state ก่อนเรียกภายนอก (หัวข้อ 11.5)
        (bool ok, ) = p.target.call{value: p.value}(p.data);
        require(ok, "call failed");
    }
}

ปัญหาที่ DAO ยังต้องเผชิญ

  • อำนาจกระจุกที่ผู้ถือรายใหญ่: หลัก 1 เหรียญ = 1 เสียง ทำให้ผู้ถือรายใหญ่ (whale) ไม่กี่รายตัดสินผลได้ ระบบนี้จึงมีลักษณะคล้ายบริษัทที่ผู้ถือหุ้นใหญ่คุมเสียง มากกว่าประชาธิปไตยแบบหนึ่งคนหนึ่งเสียง
  • ผู้มาโหวตน้อย: การโหวตบน chain เสียค่า gas ทุกครั้ง ผู้ถือรายย่อยจึงมักไม่โหวต ถ้าตั้ง quorum สูงเกินไป ก็จะไม่มีข้อเสนอใดผ่าน
  • โหวตนอก chain: หลาย DAO จึงโหวตนอก chain (off-chain voting) ผ่านบริการชื่อ Snapshot.org ซึ่งไม่เสีย gas (หัวข้อ 12.5) Snapshot.org เป็นชื่อบริการ คนละเรื่องกับจุด snapshot ของ voting power ข้างต้น แต่บริการนี้ก็นับยอดถือ ณ บล็อกที่กำหนดเช่นกัน ข้อเสียคือ contract ไม่ได้อ่านผลโหวตนอก chain เอง ส่วนใหญ่ต้องมี multisig นำผลไปดำเนินการ หรือใช้ oracle อย่าง oSnap ส่งผลเข้า chain ผู้ใช้จึงต้องเชื่อใจผู้ดำเนินการนั้นเพิ่มอีกชั้น
  • การโจมตีด้วย flash loan: flash loan คือการกู้เหรียญจำนวนมากโดยไม่มีหลักประกัน (collateral) แต่ต้องคืนภายในธุรกรรมเดียวกัน ถ้าคืนไม่ครบ ทั้งธุรกรรมจะ revert กรณีที่รู้จักกันดีคือโครงการ Beanstalk ในเดือนเมษายน 2022 ข้อเสนอแบบฉุกเฉินของ Beanstalk สั่งให้มีผลได้ทันทีเมื่อเข้าสองเงื่อนไข คือข้อเสนอมีอายุครบ 24 ชั่วโมง และได้เสียงอย่างน้อยสองในสาม ผู้โจมตีจึงส่งข้อเสนอที่โอนเงินกองกลางให้ตัวเองไว้ล่วงหน้าหนึ่งวัน วันต่อมาผู้โจมตีทำทุกขั้นที่เหลือในธุรกรรมเดียว คือกู้เงินด้วย flash loan นำไปฝากเพื่อรับสิทธิ์โหวตจนได้เกินสองในสาม โหวตผ่านข้อเสนอ สั่งให้ข้อเสนอมีผลทันที รับเงินกองกลาง แล้วคืนเงินกู้ ความเสียหายรวมราว 180 ล้านดอลลาร์
  • บทเรียนจาก Beanstalk: ช่องโหว่อยู่ที่กติกาสองข้อ ข้อแรก Beanstalk นับเสียงจากยอดฝาก ณ ขณะโหวต ข้อที่สอง ข้อเสนอฉุกเฉินมีผลทันทีเมื่อได้เสียงถึงเกณฑ์ โดยไม่มีช่วงรอหลังมติผ่าน Beanstalk มีระยะรอ 24 ชั่วโมงก็จริง แต่วางไว้ก่อนการนับเสียง ผู้โจมตีจึงส่งข้อเสนอรอไว้ก่อนได้ ถ้านับเสียงจากบล็อก snapshot ในอดีต ช่องแรกจะปิด เพราะ ณ บล็อกนั้นเหรียญที่กู้มายังไม่อยู่ในบัญชีของผู้โจมตี ส่วน timelock ที่วางไว้หลังมติผ่านจะปิดช่องที่สอง เพราะข้อเสนอไม่มีผลทันที ผู้ถือเหรียญจึงมีเวลาเห็นคำสั่งอันตรายและถอนเงินออกก่อน
  • สถานะทางกฎหมาย: หลายประเทศยังไม่มีกฎหมายรองรับ DAO ชัดเจน ผู้ร่วม DAO อาจต้องรับผิดร่วมกันเหมือนหุ้นส่วนที่ไม่ได้จดทะเบียน
ประเด็นที่มักออกสอบ ต้องจำลำดับ propose, vote, queue, execute ให้ได้ และอธิบายได้ว่า timelock มีไว้ให้ผู้ที่ไม่เห็นด้วยมีเวลาถอนตัวก่อนมติมีผล อีกประเด็นคือทำไม DAO นับเสียงจากยอดถือ ณ บล็อก snapshot ไม่ใช่ยอดปัจจุบัน คำตอบคือเพื่อกันผู้โหวตโอนเหรียญไปโหวตซ้ำ และกันผู้ที่ยืมเหรียญด้วย flash loan มาโหวต

11.5กรณีศึกษา The DAO (2016): ช่องโหว่ Reentrancy และผลที่ตามมา

The DAO คืออะไร

The DAO เป็น DAO ขนาดใหญ่รายแรกบน Ethereum แนวคิดคือกองทุนร่วมลงทุน (venture fund) ที่ไม่มีผู้จัดการกองทุน ผู้ร่วมลงทุนส่ง ETH เข้า contract แล้วได้เหรียญ DAO กลับมา จากนั้นใช้เหรียญโหวตว่าจะให้เงินโครงการใด ช่วงระดมทุนในเดือนเมษายนถึงพฤษภาคม 2016 The DAO รวบรวมได้มากกว่า 11 ล้าน ETH คิดเป็นราว 14% ของ ETH ทั้งหมดในเวลานั้น

ผู้ออกแบบรู้ว่าเสียงข้างมากอาจโหวตใช้เงินในทางที่เสียงข้างน้อยไม่เห็นด้วย จึงเพิ่มฟังก์ชัน splitDAO ให้ผู้ไม่เห็นด้วยแยกตัวออกไปตั้ง DAO ลูก (child DAO) แล้วนำ ETH ส่วนของตัวเองติดตัวไป แต่ splitDAO ส่ง ETH ออกไปก่อน แล้วจึงตั้งยอดเหรียญ DAO ของผู้ขอแยกตัวเป็นศูนย์ ผู้โจมตีใช้ contract ที่เรียก splitDAO กลับเข้ามาทุกครั้งที่ได้รับเงิน จึงแยกตัวซ้อนกันได้หลายชั้นด้วยยอดเหรียญเดิม และดึง ETH ออกไปมากกว่าส่วนของตัวเองหลายเท่า ช่องโหว่นี้เรียกว่า reentrancy รายละเอียดอยู่ในหัวข้อย่อยถัดไป

Reentrancy เกิดขึ้นได้อย่างไร

เมื่อ contract ส่ง ETH ให้ address ที่เป็น contract ฟังก์ชัน receive (หรือ fallback) ของผู้รับจะทำงานทันที การทำงานจึงย้ายไปอยู่ในโค้ดของผู้รับ ขณะที่ฟังก์ชันของผู้ส่งยังทำงานไม่จบ ถ้าผู้ส่งยังไม่ได้แก้ยอดในบัญชีก่อนส่งเงิน ผู้รับก็เรียกฟังก์ชันถอนเงินกลับเข้ามาได้อีก และฟังก์ชันจะเห็นยอดเดิมที่ยังไม่ลด ช่องโหว่แบบนี้เรียกว่า reentrancy เพราะ contract ปลายทางเรียกฟังก์ชันเดิมกลับเข้ามา (re-enter) ก่อน state จะอัปเดต

โค้ดของ The DAO ซับซ้อนกว่านี้มาก แต่จุดที่ผิดมีลักษณะเดียวกับตัวอย่างย่อด้านล่าง คือ contract ส่ง ETH ออกไปก่อน แล้วจึงตั้งยอดของผู้ถอนเป็นศูนย์

contract Bank {
    mapping(address => uint256) public balances;

    function deposit() external payable { balances[msg.sender] += msg.value; }

    function withdraw() external {
        uint256 amount = balances[msg.sender];
        require(amount > 0, "no balance");                     // Checks
        (bool ok, ) = msg.sender.call{value: amount}("");      // Interaction: ส่งเงิน โค้ดของผู้รับเริ่มทำงานตรงนี้
        require(ok, "send failed");
        balances[msg.sender] = 0;                              // Effects: แก้ยอดช้าเกินไป
    }
}

contract Attacker {
    Bank public bank;
    constructor(Bank b) { bank = b; }

    function attack() external payable {                      // เรียกพร้อมส่ง 1 ETH
        bank.deposit{value: 1 ether}();
        bank.withdraw();
    }

    receive() external payable {                              // ทำงานทุกครั้งที่ Bank ส่ง ETH มา
        if (address(bank).balance >= 1 ether) {
            bank.withdraw();                                   // เรียกกลับเข้าไป ขณะที่ balances ยังเป็น 1 ETH
        }
    }
}

วิธีป้องกัน reentrancy

  1. Checks-Effects-Interactions (CEI): ตรวจเงื่อนไข แก้ state แล้วจึงติดต่อ contract ภายนอก (บทที่ 7 หัวข้อ 7.5) ถ้าตั้งยอดเป็นศูนย์ก่อนส่งเงิน การเรียกซ้ำจะไม่ผ่าน require
  2. Reentrancy guard: ตัวแปรล็อกที่ตั้งค่าเมื่อเข้าฟังก์ชันและปลดเมื่อออก ถ้ามีผู้เรียกซ้อนเข้ามาระหว่างนั้น ฟังก์ชันจะ revert OpenZeppelin มี modifier สำเร็จรูปชื่อ nonReentrant ใน ReentrancyGuard วิธีนี้กันได้แม้ผู้เขียนลืมเรียงลำดับตาม CEI
  3. Pull over Push: ให้ผู้รับมาถอนเงินเองทีละคน แทนที่ contract จะส่งเงินออกไปให้หลายคนพร้อมกัน (หัวข้อ 7.5) แนวทางนี้ไม่ได้กัน reentrancy ด้วยตัวเอง ฟังก์ชันถอนเงินยังต้องเขียนตาม CEI แต่การเรียก contract ภายนอกจะอยู่ในฟังก์ชันสั้น ๆ เพียงฟังก์ชันเดียว ไม่กระจายอยู่ในโค้ดที่ซับซ้อน ผู้เขียนจึงตรวจลำดับได้ง่ายกว่า
// แก้ด้วย CEI
function withdraw() external {
    uint256 amount = balances[msg.sender];
    require(amount > 0, "no balance");               // Checks
    balances[msg.sender] = 0;                        // Effects: แก้ยอดก่อน
    (bool ok, ) = msg.sender.call{value: amount}(""); // Interactions: ส่งเงินทีหลัง
    require(ok, "send failed");
}

// แนวคิดของ reentrancy guard แบบย่อ
bool private locked;
modifier nonReentrant() {
    require(!locked, "reentrant call");
    locked = true;
    _;
    locked = false;
}
อย่าพึ่ง transfer() แทน CEI transfer และ send ส่ง gas ต่อให้ผู้รับเพียง 2,300 ซึ่งไม่พอให้ผู้รับเรียกฟังก์ชันกลับเข้ามา วิธีนี้จึงเคยเป็นวิธีที่แนะนำ แต่ราคา gas ของ opcode เปลี่ยนได้เมื่อเครือข่ายอัปเกรด เช่น EIP-1884 ในปี 2019 ขึ้นราคาบาง opcode จน contract บางตัวรับเงินผ่าน transfer ไม่ได้ และ wallet แบบ smart contract หลายตัวก็ต้องใช้ gas เกิน 2,300 เพื่อรับเงิน (gas stipend ในหัวข้อ 7.4) ปัจจุบันจึงแนะนำให้ใช้ call คู่กับ CEI หรือ nonReentrant
อย่าพึ่งการตรวจ underflow ของ Solidity 0.8 แทน CEI ถ้าโค้ดที่มีช่องโหว่ใช้ balances[msg.sender] -= amount แทนการตั้งยอดเป็นศูนย์ เมื่อชั้นที่ซ้อนกันคืนค่ากลับมาทีละชั้น ชั้นแรกลดยอดจาก 1 เป็น 0 ชั้นถัดไปต้องลดจาก 0 ลงอีก แต่ uint256 ติดลบไม่ได้ Solidity 0.8 จึงตรวจพบ underflow และ revert ทั้งธุรกรรม การโจมตีแบบง่ายจึงล้มเหลว แต่ผู้โจมตียังมีวิธีอื่น เช่น เรียกซ้ำผ่านอีกฟังก์ชันหนึ่งที่อ่านยอดเดียวกัน (cross-function reentrancy) ผู้เขียน contract จึงไม่ควรพึ่งการตรวจ underflow ของคอมไพเลอร์แทน CEI

ผลที่ตามมา

  • Ethereum แยกเป็นสองสาย: hard fork คืนเงินให้ผู้ลงทุน แต่ทำให้ chain แยกเป็น ETH กับ ETC (บทที่ 9) ช่วงแรกผู้ใช้หลายคนเสียเงินจาก replay attack ระหว่างสองสาย ต่อมา EIP-155 จึงนำ chainId ไปรวมไว้ในลายเซ็น (บทที่ 5)
  • คำถามเรื่อง "code is law": ฝ่ายหนึ่งมองว่าผู้โจมตีทำตามที่โค้ดอนุญาต การแก้ประวัติจึงทำลายหลักที่ว่า blockchain แก้ไม่ได้ อีกฝ่ายมองว่าโค้ดไม่ได้ทำตามเจตนาของผู้ลงทุน และความเสียหายใหญ่เกินกว่าจะปล่อยไว้ ข้อถกเถียงนี้ยังไม่มีข้อยุติ
  • วัฒนธรรมด้านความปลอดภัย: หลังเหตุการณ์นี้ การตรวจสอบโค้ด (audit) ก่อน deploy กลายเป็นขั้นตอนปกติ รูปแบบ CEI และ ReentrancyGuard กลายเป็นความรู้พื้นฐานของนักพัฒนา แต่ปัจจุบันก็ยังพบ reentrancy ในโครงการใหม่อยู่
  • บทเรียนสำหรับการออกแบบ DAO: DAO ที่ถือเงินจำนวนมากควรเผื่อไว้ว่าโค้ดของตัวเองอาจมีบั๊ก DAO รุ่นหลังจึงมี timelock มีช่องทางหยุดฉุกเฉิน (pause) และจำกัดจำนวนเงินที่ย้ายได้ต่อครั้ง ทีมจึงมีเวลาแก้ไขก่อนความเสียหายลุกลาม
  • มุมมองทางกฎหมาย: ในปี 2017 ก.ล.ต. สหรัฐฯ (SEC) ออกรายงานว่าเหรียญ DAO เข้าข่ายหลักทรัพย์ (security) หลังรายงานนี้ ทางการสหรัฐฯ เริ่มกำกับการระดมทุนด้วยการออกเหรียญ (Initial Coin Offering, ICO) อย่างจริงจัง
ประเด็นที่มักออกสอบ ให้โค้ดฟังก์ชันถอนเงินมาแล้วถามว่ามีช่องโหว่อะไร คำตอบที่ต้องเขียนให้ครบมีสามส่วน (1) ส่งเงินด้วย call ก่อนแก้ยอด (2) receive ของผู้รับเรียก withdraw ซ้ำได้ขณะยอดยังไม่เป็นศูนย์ (3) แก้โดยสลับให้แก้ยอดก่อนส่งเงิน (CEI) หรือใช้ nonReentrant และถ้าโจทย์ถามถึง The DAO ให้เชื่อมไปถึง hard fork ปี 2016 และการเกิด Ethereum Classic

สรุปท้ายบท

  • โจทย์: ในแอปทั่วไป ผู้ให้บริการถือกติกา ข้อมูล และเงิน ผู้ใช้จึงต้องเชื่อใจผู้ให้บริการ DApp ย้ายส่วนนี้ไปไว้ใน smart contract และ DAO ย้ายอำนาจตัดสินใจไปไว้ในกติกาที่เขียนเป็นโค้ด
  • 11.1: DApp เก็บกติกาและข้อมูลสำคัญไว้บน chain ผู้ใช้ยืนยันตัวด้วยลายเซ็น และตรวจทุกอย่างได้เอง แต่ต้องแลกด้วยค่า gas ความเร็วที่ช้าลง ความเป็นส่วนตัว และบั๊กที่แก้ได้ยาก DApp หลายตัวยังมีส่วนที่รวมศูนย์
  • 11.2: DApp ประกอบด้วย Frontend, Wallet, RPC node, Smart contract และ IPFS ซึ่งเป็นที่เก็บไฟล์นอก chain ไฟล์บน IPFS มี CID ที่คำนวณจากค่าแฮชของเนื้อหา และต้องมีผู้ pin ไว้จึงจะไม่หาย
  • 11.3: ABI บอก frontend ว่า contract มีฟังก์ชันและ event อะไร frontend จึง encode calldata และ decode ค่าที่คืนมาได้ ABI ไม่ได้อยู่บน chain provider ใช้อ่านข้อมูลโดยไม่ต้องใช้ key ส่วน signer อยู่ใน wallet และลงลายเซ็นธุรกรรมที่แก้ state เมื่อผู้ใช้ยืนยันแล้ว
  • 11.4: DAO มี governance token, proposal ที่ระบุคำสั่งจริง กติกาการโหวต และ timelock วงจรคือ propose, รอ voting delay, โหวต, queue แล้ว execute การนับเสียงจากยอด ณ snapshot กันการโหวตซ้ำและการยืมเหรียญด้วย flash loan ส่วน timelock ให้เวลาผู้ไม่เห็นด้วยถอนตัว
  • 11.5: The DAO ระดมทุนได้มากกว่า 11 ล้าน ETH แต่โค้ดส่งเงินก่อนแก้ยอด ผู้โจมตีจึงใช้ reentrancy ดึงเงินออกไปราว 3.6 ล้าน ETH ผลคือ hard fork ที่บล็อก 1,920,000 และ chain แยกเป็น ETH กับ ETC วิธีป้องกันคือ CEI, nonReentrant และ Pull over Push

ดูเฉลย

  2. ข. เป็น function selector และฟังก์ชันนี้ไม่มีพารามิเตอร์ต่อท้าย
  3. ค. เป็นลายเซ็นของผู้ส่งแบบย่อ
  4. ง. เป็น address ของ contract แบบย่อ
ดูเฉลย

7. DAO แห่งหนึ่งนับเสียงจากยอดเหรียญในบัญชี ณ ขณะที่กดโหวต ผู้โจมตีใช้ประโยชน์จากกติกานี้ได้อย่างไร และควรแก้อย่างไร

ผู้โจมตีใช้ flash loan กู้เหรียญจำนวนมาก โหวต แล้วคืนเหรียญในธุรกรรมเดียวกัน หรือโหวตแล้วโอนเหรียญไปอีกบัญชีเพื่อโหวตซ้ำ กรณี Beanstalk ในปี 2022 ใช้วิธีแรก โดยส่งข้อเสนอไว้ล่วงหน้าหนึ่งวัน แล้วกู้ โหวต สั่งให้ข้อเสนอมีผล และคืนเงินกู้ในธุรกรรมเดียว ทางแก้คือนับเสียงจากยอดถือ ณ บล็อก snapshot ในอดีต เช่น ใช้ getPastVotes เหรียญที่กู้มาภายหลังจึงไม่มีเสียง และเพิ่ม timelock ให้มติไม่มีผลทันที

8. ฟังก์ชันด้านล่างมีช่องโหว่อะไร และควรแก้อย่างไร

function withdraw() external {
    uint256 amount = balances[msg.sender];
    require(amount > 0);
    (bool ok, ) = msg.sender.call{value: amount}("");
    require(ok);
    balances[msg.sender] = 0;
}
ดูเฉลย
ช่องโหว่ reentrancy ฟังก์ชันส่งเงินด้วย call ก่อนตั้งยอดเป็นศูนย์ ถ้าผู้เรียกเป็น contract ฟังก์ชัน receive ของผู้เรียกจะทำงานและเรียก withdraw() ซ้ำได้ขณะยอดยังเท่าเดิม จึงถอนซ้ำจนเงินใน contract หมด วิธีแก้คือย้าย balances[msg.sender] = 0; ไปไว้ก่อน call (Checks-Effects-Interactions) และเพิ่ม modifier nonReentrant ได้อีกชั้น

9. ทำไมแนวทางปัจจุบันไม่แนะนำให้ใช้ transfer() ซึ่งส่ง gas ให้ผู้รับเพียง 2,300 เป็นวิธีหลักในการกัน reentrancy

ดูเฉลย
วิธีนี้พึ่งราคา gas ของ opcode ซึ่งเปลี่ยนได้เมื่อเครือข่ายอัปเกรด เช่น EIP-1884 ขึ้นราคาบาง opcode จน contract บางตัวรับเงินผ่าน transfer ไม่ได้ และ wallet แบบ smart contract หลายตัวต้องใช้ gas มากกว่า 2,300 เพื่อรับเงิน จึงแนะนำให้ใช้ call คู่กับ CEI หรือ nonReentrant แทน
