DApp และ DAO

บทที่ 5–7 เขียน smart contract และเรียกใช้ผ่าน Remix แต่ผู้ใช้ทั่วไปไม่ได้ใช้ Remix ผู้ใช้เปิดหน้าเว็บแล้วกดปุ่ม บทนี้อธิบายว่าหน้าเว็บกับ contract ทำงานร่วมกันอย่างไรจนกลายเป็น DApp (Decentralized Application) และเมื่อ contract ต้องเปลี่ยนค่าหรือใช้เงินกองกลาง ใครเป็นผู้ตัดสินใจ คำตอบของคำถามหลังคือ DAO (Decentralized Autonomous Organization) ท้ายบทศึกษากรณี The DAO ในปี 2016 ซึ่งแสดงว่ากติกาที่อยู่ในโค้ดมีข้อดีและข้อเสียอย่างไร

  7. สรุปท้ายบท
  8. แบบฝึกหัด

เริ่มจากโจทย์: ถ้าเจ้าของแอปเปลี่ยนใจ ผู้ใช้ทำอะไรได้บ้าง

ลองนึกถึงเว็บระดมทุนทั่วไป ผู้ใช้โอนเงินเข้าบัญชีธนาคารของบริษัท บริษัทเก็บรายชื่อผู้สนับสนุนและยอดเงินไว้ในฐานข้อมูลของตัวเอง และเขียนกติกาไว้บนหน้าเว็บว่าถ้าไม่ครบเป้าจะคืนเงิน ผู้ใช้ต้องเชื่อว่าบริษัทจะทำตามที่เขียนไว้ เพราะบริษัทแก้ยอดในฐานข้อมูลได้ เปลี่ยนกติกาได้ ปิดบัญชีผู้ใช้ได้ หรือปิดบริการไปพร้อมเงินได้ ผู้ใช้ไม่มีทางตรวจเองว่าเงินยังอยู่ครบหรือไม่

บทที่ 5 แสดงว่า smart contract ย้ายกติกาและเงินไปไว้บน blockchain ได้ ทุกโหนดรันโค้ดเดียวกัน ทุกคนอ่านยอดได้ และเจ้าของแก้โค้ดหลัง deploy ไม่ได้ แต่ contract เพียงอย่างเดียวยังไม่พอสำหรับแอปที่คนทั่วไปใช้ และยังมีคำถามตามมาอีกหลายข้อ

คำถามที่ตามมาคำตอบหัวข้อ
แอปที่ใช้ contract ต่างจากแอปทั่วไปตรงไหน และต้องแลกกับอะไรDApp11.1
ผู้ใช้ยังต้องมีหน้าเว็บ หน้าเว็บอยู่ที่ไหน และไฟล์ใหญ่ที่เก็บบน chain ไม่ไหวเก็บที่ใดFrontend, Wallet, RPC node และ IPFS11.2
หน้าเว็บสั่ง contract ได้อย่างไร โดยที่หน้าเว็บไม่เห็น private key ของผู้ใช้ABI, provider และ signer11.3
ถ้าต้องเปลี่ยนค่าใน contract หรือใช้เงินกองกลาง ใครตัดสินใจ ถ้าให้คนเดียวถือ owner key ก็กลับไปเชื่อใจคนคนเดียวอีกDAO11.4
ถ้าโค้ดมีบั๊ก กติกาที่แก้ไม่ได้จะกลายเป็นช่องโหว่ที่แก้ไม่ได้ด้วยหรือไม่กรณี The DAO และ reentrancy11.5

11.1ความแตกต่างระหว่าง DApp กับแอปพลิเคชันทั่วไป

ปัญหาของแอปที่มีเจ้าของเพียงรายเดียว

แอปทั่วไปทำงานแบบ client-server ผู้ให้บริการถือทั้งเซิร์ฟเวอร์ ฐานข้อมูล และกติกา ผู้ใช้จึงอยู่ในสถานะเดียวกับลูกค้าธนาคารในบทที่ 1 คือต้องเชื่อใจตัวกลาง (trusted third party) ตัวอย่างที่เห็นบ่อยมีดังนี้

  • บัญชีโดนระงับ: ผู้ให้บริการปิดบัญชีหรืออายัดเงินได้ ผู้ใช้ทำได้เพียงร้องเรียน
  • กติกาเปลี่ยนฝ่ายเดียว: ผู้ให้บริการขึ้นค่าธรรมเนียมหรือเปลี่ยนเงื่อนไขได้ทุกเมื่อ
  • ผู้ใช้ตรวจไม่ได้: exchange ที่ประกาศว่าถือเงินของลูกค้าครบ อาจนำเงินไปใช้ทางอื่นโดยที่ลูกค้าไม่รู้ กรณี FTX ล้มละลายในปี 2022 เป็นตัวอย่างที่ชัดเจน
  • บริการปิดตัว: เมื่อบริษัทเลิกกิจการ ข้อมูลและสิทธิ์ของผู้ใช้หายไปพร้อมเซิร์ฟเวอร์

DApp ย้ายส่วนที่ต้องเชื่อใจไปไว้บน blockchain

DApp (Decentralized Application) คือแอปที่เก็บกติกาหลัก (business logic) และข้อมูลสำคัญไว้ใน smart contract ผู้ใช้ยืนยันตัวด้วยการลงลายเซ็นจาก wallet ของตัวเอง ไม่ใช้ชื่อผู้ใช้กับรหัสผ่านที่บริษัทเก็บไว้ ผลที่ได้คือคำถามว่า "เงินยังอยู่ครบหรือไม่" และ "กติกาเป็นอย่างไร" ผู้ใช้ตรวจเองได้จาก chain ไม่ต้องเชื่อคำพูดของผู้ให้บริการ

ประเด็นแอปทั่วไปDApp
กติกาและข้อมูลอยู่ที่เซิร์ฟเวอร์และฐานข้อมูลของบริษัทsmart contract บน blockchain
การยืนยันตัวตนชื่อผู้ใช้และรหัสผ่าน บริษัท reset ให้ได้ลายเซ็นจาก private key ทำ key หายก็เข้าบัญชีไม่ได้อีก (บทที่ 14)
ผู้แก้กติกาได้บริษัท แก้ได้ทุกเมื่อแก้โค้ดไม่ได้ ยกเว้นออกแบบให้อัปเกรดได้ ซึ่งต้องมีผู้ถือสิทธิ์อัปเกรด
ตรวจสอบได้หรือไม่ไม่ได้ ต้องเชื่อรายงานของบริษัทได้ โค้ดและ state อ่านได้จาก chain
ผู้จ่ายค่าประมวลผลบริษัทจ่ายค่าเซิร์ฟเวอร์ผู้ใช้จ่าย gas ทุกครั้งที่แก้ state
ความเร็วตอบกลับในเสี้ยววินาทีรอเข้าบล็อกราว 12 วินาที และรอ finality ราว 13 นาที (บทที่ 8)
ความเป็นส่วนตัวบริษัทเห็นข้อมูล คนนอกไม่เห็นทุกคนเห็นธุรกรรมและ state ทั้งหมด
แก้บั๊กแก้แล้ว deploy ใหม่ได้ทันทีต้อง deploy contract ใหม่แล้วย้ายผู้ใช้ หรืออัปเกรดผ่าน proxy
ต่อยอดจากแอปอื่นผ่าน API ที่เจ้าของเปิดหรือปิดได้contract ใดก็เรียก contract อื่นได้โดยไม่ต้องขออนุญาต (composability)

ตารางนี้แสดงว่า DApp ไม่ได้ดีกว่าแอปทั่วไปในทุกด้าน DApp แลกความเร็ว ค่าใช้จ่าย และความเป็นส่วนตัว กับการที่ผู้ใช้ไม่ต้องเชื่อใจผู้ให้บริการ ถ้าแอปไม่มีปัญหาเรื่องความเชื่อใจตั้งแต่ต้น เช่น แอปจดบันทึกส่วนตัว การย้ายไปเป็น DApp ก็มีแต่ต้นทุนเพิ่ม

ความเป็น decentralized มีหลายระดับ DApp จำนวนมากยังมีส่วนที่รวมศูนย์ (centralized) เช่น หน้าเว็บอยู่บนเซิร์ฟเวอร์ของบริษัท ใช้ RPC node ของผู้ให้บริการรายเดียว หรือมี admin key ที่อัปเกรด contract ได้ คำถามที่ใช้ทดสอบคือ "ถ้าบริษัทหายไปพรุ่งนี้ ผู้ใช้ยังถอนเงินออกจาก contract ได้หรือไม่" ตัวอย่างเช่น ในปี 2021 Uniswap Labs เอาเหรียญบางกลุ่มออกจากหน้าเว็บของตน แต่ contract ของ Uniswap ยังซื้อขายเหรียญเหล่านั้นได้ตามเดิม ผู้ใช้ที่เรียก contract ผ่านหน้าเว็บอื่นหรือเรียกเองจึงไม่ได้รับผลกระทบ
ประเด็นที่มักออกสอบ DApp ต่างจากแอปทั่วไปที่ "ใครเป็นผู้ถือกติกาและข้อมูล" ไม่ใช่ที่หน้าตาของแอป หน้าเว็บของ DApp อาจเหมือนเว็บทั่วไปทุกอย่าง ข้อสอบมักให้เลือกข้อที่ไม่ใช่ลักษณะของ DApp เช่น "ผู้ให้บริการ reset รหัสผ่านให้ได้" หรือ "แก้บั๊กได้ทันทีโดยไม่ต้อง deploy ใหม่"

11.2สถาปัตยกรรม DApp: Frontend, Wallet, Smart contract และ IPFS

ทำไม contract อย่างเดียวไม่พอ

contract รับได้เฉพาะธุรกรรมที่ลงลายเซ็นแล้ว ผู้ใช้ทั่วไปเขียน calldata เองไม่เป็น contract แสดงหน้าจอไม่ได้ เก็บไฟล์ใหญ่ไม่ไหวเพราะ storage บน chain แพงมาก และติดต่อโลกภายนอกเองไม่ได้ DApp จึงต้องมีส่วนประกอบอื่นมาช่วย แต่ละส่วนแก้ปัญหาคนละข้อ

ส่วนประกอบหน้าที่ถ้าไม่มี
Frontend (HTML, CSS, JavaScript)แสดงหน้าจอ แปลงการกดปุ่มเป็นการเรียกฟังก์ชันของ contract และแสดงผลที่อ่านกลับมาผู้ใช้ต้องเขียน calldata เองหรือใช้ Remix
Wallet (เช่น MetaMask)เก็บ private key แสดงรายละเอียดธุรกรรมให้ผู้ใช้ยืนยัน แล้วลงลายเซ็นหน้าเว็บต้องถือ private key เอง เว็บใดก็ขโมย key ได้
RPC node (provider)โหนด Ethereum ที่รับคำขอ JSON-RPC จากแอป เช่น อ่าน state หรือส่งธุรกรรมเข้าเครือข่ายเบราว์เซอร์ติดต่อเครือข่าย peer-to-peer โดยตรงไม่ได้
Smart contractเก็บกติกาและ state ที่ต้องเชื่อถือได้ เช่น ยอดเงินและสิทธิ์กลับไปเป็นแอปที่ต้องเชื่อใจเซิร์ฟเวอร์
IPFS (InterPlanetary File System)เก็บไฟล์ใหญ่นอก chain เช่น รูป metadata หรือไฟล์ของหน้าเว็บ แล้วอ้างถึงไฟล์ด้วยค่าแฮชของเนื้อหาต้องเก็บไฟล์บน chain ซึ่งแพงเกินไป หรือเก็บบนเซิร์ฟเวอร์ที่เจ้าของเปลี่ยนไฟล์ได้
Indexer (ไม่บังคับ เช่น The Graph)เก็บ event จาก chain ลงฐานข้อมูลเพื่อค้นได้เร็ว เช่น ประวัติการโหวตทั้งหมดfrontend ต้องไล่อ่าน event ย้อนหลังจากโหนดเอง ซึ่งช้า

RPC node: ทางเข้าสู่เครือข่าย

เบราว์เซอร์ไม่ได้เป็นโหนด Ethereum จึงต้องส่งคำขอผ่านโหนดที่เปิดบริการ JSON-RPC เช่น eth_call (จำลองการเรียกฟังก์ชันเพื่ออ่านค่า) eth_getBalance หรือ eth_sendRawTransaction (ส่งธุรกรรมที่ลงลายเซ็นแล้ว) แอปส่วนใหญ่ใช้โหนดของผู้ให้บริการ เช่น Infura หรือ Alchemy เพราะการรันโหนดเองต้องใช้พื้นที่และดูแลต่อเนื่อง ข้อเสียคือผู้ให้บริการกลายเป็นจุดที่ต้องเชื่อใจ โหนดที่ตอบผิดอาจแสดงยอดที่ไม่จริงได้ แต่ปลอมลายเซ็นของผู้ใช้ไม่ได้ ผู้ให้บริการจึงย้ายเงินของผู้ใช้เองไม่ได้ ทำได้เพียงไม่ส่งธุรกรรมต่อหรือแสดงข้อมูลผิด

ทำไมไม่เก็บไฟล์ไว้บน chain

EVM คิดค่าเขียน storage ช่องใหม่ราว 20,000 gas ต่อ 32 ไบต์ ไฟล์รูปขนาด 1 MB มี 32,768 ช่อง จึงใช้ gas ราว 655 ล้าน ค่านี้มากกว่าเพดาน gas ของหนึ่งบล็อกซึ่งอยู่ในระดับหลายสิบล้านหลายเท่า เก็บในบล็อกเดียวไม่ได้ และถ้า base fee เป็น 10 Gwei ค่าธรรมเนียมจะสูงถึงราว 6.5 ETH DApp จึงเก็บไฟล์ไว้นอก chain และให้ contract เก็บเพียงตัวอ้างอิงสั้น ๆ

ถ้าตัวอ้างอิงเป็น URL ธรรมดา เช่น https://example.com/cat.png เจ้าของเซิร์ฟเวอร์ก็เปลี่ยนรูปหรือลบไฟล์ได้ทุกเมื่อ ข้อมูลบน chain ที่แก้ไม่ได้ก็ไม่มีความหมาย เพราะชี้ไปยังสิ่งที่แก้ได้ IPFS แก้ปัญหานี้ด้วย content addressing คือเรียกไฟล์ด้วยค่าแฮชของเนื้อหา แทนการเรียกด้วยตำแหน่งที่เก็บ

  • CID (Content Identifier): ตัวระบุไฟล์ที่คำนวณจากค่าแฮชของเนื้อหา CID รุ่นแรกขึ้นต้นด้วย Qm… รุ่นใหม่มักขึ้นต้นด้วย bafy… ไฟล์ที่ต่างกันแม้หนึ่งบิตจะได้ CID ต่างกัน เหมือนคุณสมบัติของฟังก์ชันแฮชในบทที่ 0
  • ตรวจได้เอง: ผู้ขอไฟล์คำนวณค่าแฮชของสิ่งที่ได้รับแล้วเทียบกับ CID จึงรับไฟล์จากโหนดใดก็ได้โดยไม่ต้องเชื่อใจโหนดนั้น IPFS แบ่งไฟล์ใหญ่เป็นก้อนแล้วเชื่อมด้วยค่าแฮชเป็นโครงสร้างแบบ Merkle (Merkle DAG) แนวคิดเดียวกับ Merkle tree ในบทที่ 3
  • ไฟล์ไม่ได้อยู่ถาวรเอง: IPFS เป็นเพียงวิธีค้นหาและส่งไฟล์ ไฟล์จะหายไปถ้าไม่มีโหนดใดเก็บไว้ ผู้ทำ DApp จึงต้อง pin ไฟล์ไว้บนโหนดของตัวเอง ใช้บริการ pinning หรือจ่ายให้เครือข่ายอย่าง Filecoin เก็บรักษา
  • แก้ไฟล์แล้ว CID เปลี่ยน: หน้าเว็บที่ต้องอัปเดตจึงใช้ชื่อที่ชี้ไปยัง CID ล่าสุด เช่น ชื่อ ENS (Ethereum Name Service) อย่าง app.eth แล้วแก้ค่า CID ที่ชื่อนั้นชี้ไปเมื่อมีรุ่นใหม่
หน้าเว็บก็เป็นจุดโจมตีได้ ถ้า contract ปลอดภัยแต่หน้าเว็บอยู่บนเซิร์ฟเวอร์ทั่วไป ผู้โจมตีที่ยึด DNS หรือเซิร์ฟเวอร์ได้ก็เปลี่ยน JavaScript ให้ขอลายเซ็นธุรกรรมที่ส่งเงินไปให้ตัวเองได้ ผู้ใช้เห็นหน้าเว็บเดิมทุกอย่างจึงกดยืนยันโดยไม่รู้ตัว การวางหน้าเว็บบน IPFS แล้วอ้างถึงด้วย CID ช่วยลดความเสี่ยงนี้ เพราะเนื้อหาที่ตรงกับ CID เปลี่ยนไม่ได้ แต่ผู้ใช้ก็ยังต้องอ่านรายละเอียดในหน้าต่างของ wallet ก่อนยืนยันทุกครั้ง

11.3การเชื่อม Frontend กับ Contract: ABI, provider และ signer (ethers.js)

ทำไมต้องมี ABI

บน chain มีเพียง bytecode ของ contract ไม่มีชื่อฟังก์ชันหรือชนิดของพารามิเตอร์ บทที่ 5 อธิบายว่าธุรกรรมเรียกฟังก์ชันด้วย function selector คือ 4 ไบต์แรกของค่าแฮช Keccak-256 ของ function signature ค่าแฮชย้อนกลับไม่ได้ frontend จึงเดาชื่อฟังก์ชันจาก bytecode ไม่ได้ และเมื่อ contract คืนค่ากลับมา frontend ได้รับเพียงข้อมูลดิบเป็นช่องละ 32 ไบต์ ถ้าไม่รู้ชนิดของค่าที่คืนมา ก็แปลข้อมูลนั้นไม่ได้

ABI (Application Binary Interface) แก้ปัญหานี้ ABI คือคำอธิบายรูปแบบการเรียก contract ประกอบด้วยรายชื่อฟังก์ชัน ชนิดของพารามิเตอร์และค่าที่คืน state mutability และ event คอมไพเลอร์สร้าง ABI ออกมาพร้อม bytecode ในรูป JSON (ใน Remix คือปุ่มคัดลอก ABI ในแท็บ Solidity Compiler ตามบทที่ 6) ABI ไม่ได้บันทึกไว้บน chain ผู้ทำ frontend จึงต้องนำ ABI จากผลการคอมไพล์ หรือจาก contract ที่ยืนยันซอร์สโค้ดไว้บน Etherscan แล้ว (verified contract)

ทำไมต้องแยก provider กับ signer

การอ่านกับการเขียนต้องการสิ่งต่างกัน การอ่าน state ต้องการเพียงโหนดที่ตอบคำถามได้ ไม่ต้องใช้ private key และไม่เสีย gas ส่วนการแก้ state ต้องมีธุรกรรมที่ลงลายเซ็นด้วย private key ของผู้ใช้ ถ้าหน้าเว็บถือ private key เอง เว็บใดก็ขโมย key ได้ wallet จึงเก็บ key ไว้กับตัวเอง แล้วเปิดช่องทางให้หน้าเว็บขอลายเซ็นผ่านอ็อบเจกต์ window.ethereum (มาตรฐาน EIP-1193) ผู้ใช้ต้องกดยืนยันในหน้าต่างของ wallet ทุกครั้ง library อย่าง ethers.js แยกสองบทบาทนี้ออกจากกันอย่างชัดเจน

ProviderSigner
คืออะไรการเชื่อมต่อแบบอ่านอย่างเดียวไปยังโหนดบัญชีที่ลงลายเซ็นได้ ใน DApp คือบัญชีใน wallet ของผู้ใช้
ใช้ทำอะไรอ่าน state, ยอดเงิน, เลขบล็อก, event และเรียกฟังก์ชัน view / pure ผ่าน eth_callส่งธุรกรรมที่แก้ state, deploy contract และลงลายเซ็นข้อความ
ต้องใช้ private keyไม่ต้องต้อง แต่ key อยู่ใน wallet หน้าเว็บไม่เห็น
เสีย gasไม่เสียเสียเมื่อส่งธุรกรรม
ผู้ใช้ต้องกดยืนยันไม่ต้องต้องยืนยันใน wallet ทุกครั้ง
ตัวอย่างใน ethers v6new ethers.BrowserProvider(window.ethereum) หรือ new ethers.JsonRpcProvider(url)await provider.getSigner()

ตัวอย่างโค้ด: อ่านและเขียน Counter ด้วย ethers.js v6

import { ethers } from "ethers";                          // ethers รุ่น 6

const address = "0x…";                                   // address ของ Counter ที่ deploy แล้ว
const abi = [                                            // human-readable ABI รูปแบบย่อที่ ethers อ่านได้
  "function count() view returns (uint256)",
  "function increment()",
];

// 1) provider: เชื่อมต่อโหนดผ่าน wallet ใช้อ่านอย่างเดียว
const provider = new ethers.BrowserProvider(window.ethereum);
const counter  = new ethers.Contract(address, abi, provider);
const n = await counter.count();                         // eth_call ไม่เสีย gas ได้ค่าเป็น bigint เช่น 5n

// 2) signer: ขอสิทธิ์เข้าถึงบัญชี MetaMask จะถามผู้ใช้ในครั้งแรก
const signer = await provider.getSigner();
const tx = await counter.connect(signer).increment();   // MetaMask ขึ้นหน้าต่างให้ยืนยัน
console.log("tx hash:", tx.hash);                       // ธุรกรรมอยู่ใน mempool แล้ว แต่ยังไม่เข้าบล็อก

// 3) รอให้ธุรกรรมเข้าบล็อก แล้วอ่านค่าใหม่
const receipt = await tx.wait();                        // ได้ receipt ที่มี status, gasUsed, logs
console.log(receipt.status === 1 ? "สำเร็จ" : "ล้มเหลว", await counter.count());

โค้ดนี้แสดงลำดับของการเขียน state ทุกครั้ง คือ frontend ใช้ ABI สร้าง calldata แล้วส่งคำขอ eth_sendTransaction ไปที่ wallet จากนั้น wallet แสดงรายละเอียดและค่า gas ให้ผู้ใช้ เมื่อผู้ใช้ยืนยัน wallet ลงลายเซ็นแล้วส่งธุรกรรมเข้าเครือข่าย frontend ได้ transaction hash กลับมาทันที แต่ต้องรอ tx.wait() จนธุรกรรมเข้าบล็อกก่อน จึงจะรู้ว่าสำเร็จหรือ revert

ethers v5 กับ v6 เอกสารและตัวอย่างรุ่นเก่าจำนวนมากใช้ ethers v5 ซึ่งเขียนต่างออกไป เช่น v5 ใช้ new ethers.providers.Web3Provider(window.ethereum) และ provider.getSigner() ไม่ต้อง await ส่วน v6 เปลี่ยนเป็น BrowserProvider และ await provider.getSigner() ตัวเลขขนาดใหญ่ v5 ใช้ BigNumber ส่วน v6 ใช้ bigint ของ JavaScript ถ้าโค้ดตัวอย่างรันไม่ผ่าน ให้ตรวจรุ่นของ ethers ก่อน
ลงลายเซ็นโดยไม่อ่าน (blind signing) wallet แสดงข้อมูลตามที่หน้าเว็บส่งมา หน้าเว็บที่ไม่หวังดีอาจขอให้ผู้ใช้ลงลายเซ็นธุรกรรม approve ที่อนุญาตให้ address ของผู้โจมตีย้ายเหรียญทั้งหมดของผู้ใช้ (บทที่ 12) แม้หน้าเว็บจะเขียนว่า "รับของรางวัลฟรี" การแยก signer ไว้ใน wallet ช่วยได้เฉพาะเมื่อผู้ใช้อ่านหน้าต่างยืนยันจริง hardware wallet ในบทที่ 14 แสดงรายละเอียดบนจอของอุปกรณ์เอง จึงลดความเสี่ยงที่คอมพิวเตอร์โดนแก้หน้าจอได้
ประเด็นที่มักออกสอบ โจทย์มักถามว่าการกระทำใดต้องใช้ signer การอ่านค่าผ่านฟังก์ชัน view ใช้ provider อย่างเดียว ไม่เสีย gas และไม่มีหน้าต่างของ wallet ขึ้น ส่วนการเรียกฟังก์ชันที่แก้ state ต้องใช้ signer เสีย gas และผู้ใช้ต้องยืนยัน อีกข้อที่พบบ่อยคือ "frontend รู้ได้อย่างไรว่า contract มีฟังก์ชันอะไร" คำตอบคือจาก ABI ไม่ใช่จาก chain

11.4DAO: การเสนอ การลงมติ และการดำเนินการตามกติกาในโค้ด

contract แก้ไม่ได้ แต่โครงการยังต้องตัดสินใจ

DApp ที่ใช้งานจริงยังต้องเปลี่ยนแปลงอยู่เสมอ เช่น ปรับอัตราค่าธรรมเนียม เพิ่มเหรียญที่รองรับ อัปเกรด contract ผ่าน proxy หรือใช้เงินกองกลาง (treasury) จ้างนักพัฒนา คำถามคือใครมีสิทธิ์สั่ง ทางเลือกหลักมีสามแบบ

ผู้ถือสิทธิ์ข้อดีปัญหา
owner key ของคนเดียว (modifier onlyOwner ในบทที่ 5)ง่าย ตัดสินใจได้เร็วถ้า key หาย สั่งอะไรไม่ได้อีก ถ้า key โดนขโมยหรือเจ้าของคิดโกง ก็ย้ายเงินทั้งหมดได้ ผู้ใช้จึงกลับไปเชื่อใจคนคนเดียว
multisig เช่น ต้องมีลายเซ็น 3 จาก 5 คนkey หายหรือโดนขโมยหนึ่งดอกยังไม่เสียหายอำนาจยังอยู่กับกลุ่มเล็ก ผู้ใช้ส่วนใหญ่ไม่มีเสียง
DAOผู้ถือเหรียญทุกคนเสนอและลงมติได้ ผลการลงมติมีผลผ่านโค้ดตัดสินใจช้า และอาจโดนโจมตีผ่านกติกาการโหวต (หัวข้อย่อยด้านล่าง)

DAO (Decentralized Autonomous Organization) คือองค์กรที่เขียนกติกาการตัดสินใจไว้ใน smart contract คำว่า autonomous ไม่ได้แปลว่าไม่มีคนเกี่ยวข้อง คนยังเป็นผู้เสนอและโหวต แต่เมื่อมติผ่านแล้ว contract เป็นผู้ดำเนินการเอง ไม่มีใครปฏิเสธหรือแก้ผลระหว่างทางได้ และเงินกองกลางก็อยู่ใน contract ไม่ได้อยู่ในบัญชีของใคร

ส่วนประกอบของ DAO

  • Governance token: เหรียญที่ใช้นับสิทธิ์ออกเสียง ส่วนใหญ่ใช้หลัก 1 เหรียญ = 1 เสียง หลายระบบให้ผู้ถือ delegate สิทธิ์ให้ตัวเองหรือผู้อื่นก่อน เสียงจึงจะนับ ผู้ที่ไม่มีเวลาติดตามทุกข้อเสนอจึงมอบเสียงให้ผู้แทนได้
  • Proposal: ข้อเสนอไม่ได้เป็นเพียงข้อความ แต่มีรายการคำสั่งที่จะให้ contract ทำ คือ target (address ปลายทาง) value (จำนวน ETH) และ calldata (ฟังก์ชันกับพารามิเตอร์) พร้อมคำอธิบาย ผู้โหวตจึงรู้แน่ชัดว่าถ้าผ่านแล้วจะเกิดอะไร
  • กติกาการลงมติ: เกณฑ์ขั้นต่ำในการเสนอ ระยะรอก่อนเริ่มโหวต ระยะเวลาโหวต และองค์ประชุม (quorum)
  • Timelock: contract ที่ถือเงินกองกลางและสิทธิ์ admin ทุกคำสั่งต้องรอครบเวลาที่กำหนดก่อนมีผล

ทำไมแต่ละกติกาต้องมี

กติกาแต่ละข้อของ DAO ปิดช่องโจมตีหนึ่งช่อง ถ้าตัดข้อใดออก ผู้ถือเหรียญกลุ่มเล็กหรือผู้โจมตีจะยึดเงินกองกลางได้ง่ายขึ้น

กติกามีไว้เพื่อถ้าไม่มี
Proposal threshold (ต้องถือเหรียญขั้นต่ำจึงเสนอได้)กันข้อเสนอขยะผู้โจมตีส่งข้อเสนอจำนวนมากจนผู้โหวตตรวจไม่ทัน
Voting delayให้ผู้ถือเหรียญอ่านข้อเสนอ และ delegate สิทธิ์ก่อนนับเสียงผู้เสนอเปิดโหวตทันทีขณะที่คนอื่นยังไม่รู้ว่ามีข้อเสนอ
Snapshot ของ voting power (นับยอดถือ ณ บล็อกที่เริ่มโหวต)ให้เหรียญแต่ละเหรียญมีเสียงได้ครั้งเดียวโหวตแล้วโอนเหรียญไปอีกบัญชีแล้วโหวตซ้ำได้ หรือยืมเหรียญมาโหวตแล้วคืน
Voting periodเปิดเวลาให้ผู้ถือเหรียญทุกเขตเวลาโหวตได้ผลขึ้นกับว่าใครออนไลน์อยู่ในช่วงสั้น ๆ
Quorum (เสียงรวมต้องถึงสัดส่วนขั้นต่ำของเหรียญทั้งหมด)กันข้อเสนอผ่านเมื่อมีผู้มาโหวตน้อยกลุ่มเล็กผ่านข้อเสนอได้ในช่วงที่คนส่วนใหญ่ไม่สนใจ
Timelockเปิดเวลาระหว่างมติผ่านกับวันที่มีผลข้อเสนอที่ซ่อนคำสั่งอันตรายมีผลทันที ผู้ไม่เห็นด้วยถอนเงินออกไม่ทัน

ค่าที่พบในตัวอย่างของ OpenZeppelin Governor เช่น voting delay 1 วัน voting period 1 สัปดาห์ และ quorum 4% ของเหรียญทั้งหมด แต่ละ DAO ตั้งค่าเองตามความเหมาะสม จึงไม่ใช่ตัวเลขมาตรฐานที่ต้องจำ

ผลของมติมีผลผ่านโค้ด

contract ด้านล่างเป็น DAO แบบย่อสำหรับทำความเข้าใจ ไม่มี timelock และไม่ได้ป้องกันการโจมตีทุกแบบ จุดที่ควรสังเกตคือ execute เรียก calldata ที่บันทึกไว้ตั้งแต่ตอนเสนอ ไม่มีใครเปลี่ยนคำสั่งหลังโหวตได้

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

interface IVotes {                                      // เหรียญที่จำยอดย้อนหลังได้ เช่น ERC20Votes
    function getPastVotes(address who, uint256 blockNumber) external view returns (uint256);
    function getPastTotalSupply(uint256 blockNumber) external view returns (uint256);
}

contract MiniDAO {
    struct Proposal {
        address target; uint256 value; bytes data;     // คำสั่งที่จะทำเมื่อผ่าน
        uint256 snapshot; uint256 deadline;             // บล็อกที่นับยอดถือ และบล็อกที่ปิดโหวต
        uint256 forVotes; uint256 againstVotes; bool executed;
    }
    IVotes public immutable token;
    Proposal[] public proposals;
    mapping(uint256 => mapping(address => bool)) public voted;

    constructor(IVotes t) { token = t; }

    function propose(address target, uint256 value, bytes calldata data) external returns (uint256 id) {
        proposals.push(Proposal(target, value, data, block.number + 7200, block.number + 57600, 0, 0, false));
        return proposals.length - 1;                    // ตัวอย่าง: delay ราว 1 วัน โหวตราว 1 สัปดาห์ (12 วินาทีต่อบล็อก)
    }

    function vote(uint256 id, bool support) external {
        Proposal storage p = proposals[id];
        require(block.number > p.snapshot && block.number <= p.deadline, "not active");
        require(!voted[id][msg.sender], "already voted");
        uint256 weight = token.getPastVotes(msg.sender, p.snapshot);   // ยอด ณ snapshot ไม่ใช่ยอดตอนนี้
        voted[id][msg.sender] = true;
        if (support) p.forVotes += weight; else p.againstVotes += weight;
    }

    function execute(uint256 id) external {
        Proposal storage p = proposals[id];
        require(block.number > p.deadline, "voting not ended");
        require(!p.executed, "done");
        uint256 quorum = token.getPastTotalSupply(p.snapshot) * 4 / 100;
        require(p.forVotes + p.againstVotes >= quorum, "no quorum");
        require(p.forVotes > p.againstVotes, "defeated");
        p.executed = true;                              // แก้ state ก่อนเรียกภายนอก (หัวข้อ 11.5)
        (bool ok, ) = p.target.call{value: p.value}(p.data);
        require(ok, "call failed");
    }
}

ปัญหาที่ DAO ยังต้องเผชิญ

  • อำนาจกระจุกที่ผู้ถือรายใหญ่: หลัก 1 เหรียญ = 1 เสียง ทำให้ผู้ถือรายใหญ่ (whale) ไม่กี่รายตัดสินผลได้ ระบบนี้จึงมีลักษณะคล้ายบริษัทที่ผู้ถือหุ้นใหญ่คุมเสียง มากกว่าประชาธิปไตยแบบหนึ่งคนหนึ่งเสียง
  • ผู้มาโหวตน้อย: การโหวตบน chain เสียค่า gas ทุกครั้ง ผู้ถือรายย่อยจึงมักไม่โหวต ค่า quorum ที่ตั้งสูงเกินไปทำให้ไม่มีข้อเสนอใดผ่าน หลาย DAO จึงโหวตนอก chain ผ่าน Snapshot.org ซึ่งไม่เสีย gas (บทที่ 12) แต่ผลโหวตนอก chain ไม่มีผลกับ contract เอง ต้องมี multisig นำผลไปดำเนินการ ผู้ใช้จึงต้องเชื่อใจ multisig นั้นอีกชั้น
  • การโจมตีด้วย flash loan: flash loan คือการกู้เหรียญจำนวนมากโดยไม่มีหลักประกัน แต่ต้องคืนภายในธุรกรรมเดียวกัน ถ้าคืนไม่ครบ ทั้งธุรกรรมจะ revert ในเดือนเมษายน 2022 ผู้โจมตี Beanstalk กู้เงินด้วย flash loan มาซื้อสิทธิ์โหวตเกินสองในสาม แล้วผ่านข้อเสนอที่ส่งเงินกองกลางให้ตัวเองได้ภายในธุรกรรมเดียว ความเสียหายรวมราว 180 ล้านดอลลาร์ ช่องโหว่อยู่ที่กติกาของ Beanstalk นับเสียงจากยอดถือ ณ ขณะโหวต และให้ข้อเสนอฉุกเฉินมีผลทันที การนับเสียง ณ บล็อก snapshot ในอดีตปิดช่องนี้ได้ เพราะเหรียญที่กู้มาในธุรกรรมปัจจุบันไม่มีอยู่ในบัญชี ณ บล็อกนั้น ส่วน timelock ทำให้ข้อเสนอไม่มีผลทันที
  • สถานะทางกฎหมาย: หลายประเทศยังไม่มีกฎหมายรองรับ DAO ชัดเจน ผู้ร่วม DAO อาจต้องรับผิดร่วมกันเหมือนหุ้นส่วนที่ไม่ได้จดทะเบียน
ประเด็นที่มักออกสอบ จำลำดับ propose, vote, queue, execute และเหตุผลของ timelock ได้ คือให้ผู้ที่ไม่เห็นด้วยมีเวลาถอนตัวก่อนมติมีผล อีกประเด็นคือทำไม DAO นับเสียงจากยอดถือ ณ บล็อก snapshot ไม่ใช่ยอดปัจจุบัน คำตอบคือกันการโหวตซ้ำด้วยการโอนเหรียญ และกันการยืมเหรียญด้วย flash loan มาโหวต

11.5กรณีศึกษา The DAO (2016): ช่องโหว่ Reentrancy และผลที่ตามมา

The DAO คืออะไร

The DAO เป็น DAO ขนาดใหญ่รายแรกบน Ethereum แนวคิดคือกองทุนร่วมลงทุน (venture fund) ที่ไม่มีผู้จัดการกองทุน ผู้ร่วมลงทุนส่ง ETH เข้า contract แล้วได้เหรียญ DAO กลับมา จากนั้นใช้เหรียญโหวตว่าจะให้เงินโครงการใด ช่วงระดมทุนในเดือนเมษายนถึงพฤษภาคม 2016 The DAO รวบรวมได้มากกว่า 11 ล้าน ETH เป็นสัดส่วนที่สูงมากของ ETH ทั้งหมดในเวลานั้น

ผู้ออกแบบรู้ว่าเสียงข้างมากอาจโหวตใช้เงินในทางที่เสียงข้างน้อยไม่เห็นด้วย จึงเพิ่มฟังก์ชัน splitDAO ให้ผู้ไม่เห็นด้วยแยกตัวออกไปตั้ง DAO ลูก (child DAO) แล้วนำ ETH ส่วนของตัวเองติดตัวไป ฟังก์ชันนี้มีไว้คุ้มครองเสียงข้างน้อย แต่กลายเป็นทางที่ผู้โจมตีใช้ดึงเงิน

Reentrancy เกิดขึ้นได้อย่างไร

เมื่อ contract ส่ง ETH ให้ address ที่เป็น contract ฟังก์ชัน receive (หรือ fallback) ของผู้รับจะทำงานทันที การทำงานจึงย้ายไปอยู่ในโค้ดของผู้รับ ขณะที่ฟังก์ชันของผู้ส่งยังทำงานไม่จบ ถ้าผู้ส่งยังไม่ได้แก้ยอดในบัญชีก่อนส่งเงิน ผู้รับก็เรียกฟังก์ชันถอนเงินกลับเข้ามาได้อีก และฟังก์ชันจะเห็นยอดเดิมที่ยังไม่ลด ช่องโหว่ที่ผู้ถูกเรียกเรียกฟังก์ชันเดิมกลับเข้ามา (re-enter) ก่อน state จะอัปเดตนี้เรียกว่า reentrancy

โค้ดของ The DAO ซับซ้อนกว่านี้มาก แต่จุดที่ผิดมีลักษณะเดียวกับตัวอย่างย่อด้านล่าง คือ contract ส่ง ETH ออกไปก่อน แล้วจึงตั้งยอดของผู้ถอนเป็นศูนย์

contract Bank {
    mapping(address => uint256) public balances;

    function deposit() external payable { balances[msg.sender] += msg.value; }

    function withdraw() external {
        uint256 amount = balances[msg.sender];
        require(amount > 0, "no balance");                     // Checks
        (bool ok, ) = msg.sender.call{value: amount}("");      // Interaction: ส่งเงิน โค้ดของผู้รับเริ่มทำงานตรงนี้
        require(ok, "send failed");
        balances[msg.sender] = 0;                              // Effects: แก้ยอดช้าเกินไป
    }
}

contract Attacker {
    Bank public bank;
    constructor(Bank b) { bank = b; }

    function attack() external payable {                      // เรียกพร้อมส่ง 1 ETH
        bank.deposit{value: 1 ether}();
        bank.withdraw();
    }

    receive() external payable {                              // ทำงานทุกครั้งที่ Bank ส่ง ETH มา
        if (address(bank).balance >= 1 ether) {
            bank.withdraw();                                   // เรียกกลับเข้าไป ขณะที่ balances ยังเป็น 1 ETH
        }
    }
}

วิธีป้องกัน reentrancy

  1. Checks-Effects-Interactions (CEI): ตรวจเงื่อนไข แก้ state แล้วจึงติดต่อภายนอก (บทที่ 7 หัวข้อ 7.5) เมื่อยอดเป็นศูนย์ก่อนส่งเงิน การเรียกซ้ำจะไม่ผ่าน require
  2. Reentrancy guard: ตัวแปรล็อกที่ตั้งค่าเมื่อเข้าฟังก์ชันและปลดเมื่อออก ถ้ามีการเรียกซ้อนเข้ามาระหว่างนั้น ฟังก์ชันจะ revert OpenZeppelin มี modifier สำเร็จรูปชื่อ nonReentrant ใน ReentrancyGuard วิธีนี้กันได้แม้ผู้เขียนลืมเรียงลำดับตาม CEI
  3. Pull over Push: ให้ผู้รับถอนเงินเองทีละคน (หัวข้อ 7.5) ทุกฟังก์ชันที่ส่งเงินยังต้องเขียนตาม CEI แต่จำนวนจุดที่ต้องระวังลดลง
// แก้ด้วย CEI
function withdraw() external {
    uint256 amount = balances[msg.sender];
    require(amount > 0, "no balance");               // Checks
    balances[msg.sender] = 0;                        // Effects: แก้ยอดก่อน
    (bool ok, ) = msg.sender.call{value: amount}(""); // Interactions: ส่งเงินทีหลัง
    require(ok, "send failed");
}

// แนวคิดของ reentrancy guard แบบย่อ
bool private locked;
modifier nonReentrant() {
    require(!locked, "reentrant call");
    locked = true;
    _;
    locked = false;
}
อย่าพึ่ง transfer() หรือรุ่นคอมไพเลอร์แทน CEI transfer และ send ส่ง gas ต่อให้ผู้รับเพียง 2,300 ซึ่งไม่พอให้ผู้รับเรียกฟังก์ชันกลับเข้ามา จึงเคยเป็นวิธีที่แนะนำ แต่ราคา gas ของ opcode เปลี่ยนได้เมื่อมีการอัปเกรด เช่น EIP-1884 ในปี 2019 ขึ้นราคาบาง opcode จน contract บางตัวรับเงินผ่าน transfer ไม่ได้ (บทที่ 7) ปัจจุบันจึงแนะนำให้ใช้ call คู่กับ CEI หรือ nonReentrant อีกเรื่องหนึ่งคือ ถ้าโค้ดที่มีช่องโหว่เขียนว่า balances[msg.sender] -= amount แทนการตั้งเป็นศูนย์ Solidity 0.8 จะ revert เมื่อยอดติดลบตอนชั้นที่ซ้อนกันคืนค่า การโจมตีแบบง่ายจึงล้มเหลว แต่ผู้โจมตีมีวิธีอื่น เช่น เรียกซ้ำผ่านอีกฟังก์ชันหนึ่งที่อ่านยอดเดียวกัน (cross-function reentrancy) จึงไม่ควรพึ่งการตรวจตัวเลขของคอมไพเลอร์แทน CEI

ผลที่ตามมา

  • Ethereum แยกเป็นสองสาย: hard fork คืนเงินให้ผู้ลงทุน แต่ทำให้เกิด ETH กับ ETC ตามบทที่ 9 และในช่วงแรกผู้ใช้หลายคนเสียเงินจาก replay attack ระหว่างสองสาย จนมี EIP-155 นำ chainId ไปรวมไว้ในลายเซ็น (บทที่ 5)
  • คำถามเรื่อง "code is law": ฝ่ายหนึ่งมองว่าผู้โจมตีทำตามที่โค้ดอนุญาต การแก้ประวัติจึงทำลายหลักที่ว่า blockchain แก้ไม่ได้ อีกฝ่ายมองว่าโค้ดไม่ได้ทำตามเจตนาของผู้ลงทุน และความเสียหายใหญ่เกินกว่าจะปล่อยไว้ ข้อถกเถียงนี้ยังไม่มีข้อยุติ
  • วัฒนธรรมด้านความปลอดภัย: หลังเหตุการณ์นี้ การตรวจสอบโค้ด (audit) ก่อน deploy กลายเป็นขั้นตอนปกติ รูปแบบ CEI และ ReentrancyGuard กลายเป็นความรู้พื้นฐานของนักพัฒนา แต่ reentrancy ยังพบในโครงการใหม่จนถึงปัจจุบัน
  • บทเรียนสำหรับการออกแบบ DAO: DAO ที่ถือเงินจำนวนมากต้องถือว่าโค้ดของตัวเองอาจมีบั๊ก จึงมี timelock ช่องทางหยุดฉุกเฉิน และจำกัดจำนวนเงินที่ย้ายได้ต่อครั้ง เพื่อให้มีเวลาตอบสนองก่อนความเสียหายลุกลาม
  • มุมมองทางกฎหมาย: ในปี 2017 ก.ล.ต. สหรัฐฯ (SEC) ออกรายงานว่าเหรียญ DAO เข้าข่ายหลักทรัพย์ เหตุการณ์นี้จึงเป็นจุดเริ่มต้นของการกำกับดูแลการออกเหรียญด้วย
ประเด็นที่มักออกสอบ ให้โค้ดฟังก์ชันถอนเงินมาแล้วถามว่ามีช่องโหว่อะไร คำตอบที่ต้องเขียนให้ครบมีสามส่วน (1) ส่งเงินด้วย call ก่อนแก้ยอด (2) receive ของผู้รับเรียก withdraw ซ้ำได้ขณะยอดยังไม่เป็นศูนย์ (3) แก้โดยสลับให้แก้ยอดก่อนส่งเงิน (CEI) หรือใช้ nonReentrant และถ้าโจทย์ถามถึง The DAO ให้เชื่อมไปถึง hard fork ปี 2016 และการเกิด Ethereum Classic

สรุปท้ายบท

  • โจทย์: แอปทั่วไปให้ผู้ให้บริการถือกติกา ข้อมูล และเงิน ผู้ใช้จึงต้องเชื่อใจ DApp ย้ายส่วนนี้ไปไว้ใน smart contract และ DAO ย้ายอำนาจตัดสินใจไปไว้ในกติกาที่เขียนเป็นโค้ด
  • 11.1: DApp เก็บกติกาและข้อมูลสำคัญไว้บน chain ผู้ใช้ยืนยันตัวด้วยลายเซ็น และตรวจทุกอย่างได้เอง แต่ต้องแลกกับค่า gas ความเร็ว ความเป็นส่วนตัว และการแก้บั๊กที่ยาก DApp หลายตัวยังมีส่วนที่รวมศูนย์
  • 11.2: DApp ประกอบด้วย Frontend, Wallet, RPC node, Smart contract และที่เก็บไฟล์นอก chain อย่าง IPFS ซึ่งเรียกไฟล์ด้วย CID ที่มาจากค่าแฮชของเนื้อหา ไฟล์บน IPFS ต้องมีผู้ pin ไว้จึงจะไม่หาย
  • 11.3: ABI บอก frontend ว่า contract มีฟังก์ชันและ event อะไร เพื่อ encode calldata และ decode ค่าที่คืนมา ABI ไม่ได้อยู่บน chain provider ใช้อ่านโดยไม่ต้องใช้ key ส่วน signer อยู่ใน wallet และลงลายเซ็นธุรกรรมที่แก้ state หลังผู้ใช้ยืนยัน
  • 11.4: DAO มี governance token, proposal ที่ระบุคำสั่งจริง กติกาการโหวต และ timelock วงจรคือ propose, รอ voting delay, โหวต, queue แล้ว execute การนับเสียง ณ snapshot กันการโหวตซ้ำและ flash loan ส่วน timelock เปิดเวลาให้ผู้ไม่เห็นด้วยถอนตัว
  • 11.5: The DAO ระดมได้มากกว่า 11 ล้าน ETH และเสีย ETH ราว 3.6 ล้าน ETH ให้ช่องโหว่ reentrancy เพราะส่งเงินก่อนแก้ยอด ผลคือ hard fork ที่บล็อก 1,920,000 และการแยกเป็น ETH กับ ETC วิธีป้องกันคือ CEI, nonReentrant และ Pull over Push

ดูเฉลย

4. นักพัฒนามี address ของ contract ที่ deploy แล้ว แต่ไม่มี ABI และ contract ไม่ได้ยืนยันซอร์สโค้ดบน Etherscan ทำไมจึงเรียกฟังก์ชันได้ยาก

5. ธุรกรรมเรียก increment() ของ Counter มีฟิลด์ data เป็น 0xd09de08a เพียง 4 ไบต์ ข้อใดอธิบายถูกต้อง

  1. ก. เป็นค่าแฮชเต็มของ bytecode ของ Counter
  2. ข. เป็น function selector และฟังก์ชันนี้ไม่มีพารามิเตอร์ต่อท้าย
  3. ค. เป็นลายเซ็นของผู้ส่งแบบย่อ
  4. ง. เป็น address ของ contract แบบย่อ
ดูเฉลย
ข. 0xd09de08a คือ 4 ไบต์แรกของ Keccak-256 ของ "increment()" ฟังก์ชันนี้ไม่มีพารามิเตอร์ data จึงมีเพียง selector ลายเซ็นและ address ปลายทางอยู่ในฟิลด์อื่นของธุรกรรม

6. ทำไม DAO จำนวนมากจึงให้มติที่ผ่านแล้วรอใน timelock อีกหลายวันก่อนมีผล

ดูเฉลย
timelock เปิดเวลาระหว่างมติผ่านกับวันที่มีผล ผู้ที่ไม่เห็นด้วยจึงขายเหรียญหรือถอนเงินออกได้ก่อนคำสั่งทำงาน และชุมชนมีเวลาตรวจว่าข้อเสนอซ่อนคำสั่งอันตรายไว้หรือไม่ ถ้าไม่มี timelock ผู้ที่รวมเสียงได้มากพอจะผ่านข้อเสนอที่ย้ายเงินกองกลางแล้วให้มีผลทันที

ดูเฉลย
ผู้โจมตีใช้ flash loan กู้เหรียญจำนวนมาก โหวต แล้วคืนเหรียญในธุรกรรมเดียวกัน หรือโหวตแล้วโอนเหรียญไปอีกบัญชีเพื่อโหวตซ้ำ กรณี Beanstalk ในปี 2022 ใช้วิธีแรก ทางแก้คือนับเสียงจากยอดถือ ณ บล็อก snapshot ในอดีต เช่น getPastVotes เหรียญที่กู้มาภายหลังจึงไม่มีเสียง และเพิ่ม timelock ให้มติไม่มีผลทันที

8. ฟังก์ชันด้านล่างมีช่องโหว่อะไร และควรแก้อย่างไร

function withdraw() external {
    uint256 amount = balances[msg.sender];
    require(amount > 0);
    (bool ok, ) = msg.sender.call{value: amount}("");
    require(ok);
    balances[msg.sender] = 0;
}
ดูเฉลย
ช่องโหว่ reentrancy ฟังก์ชันส่งเงินด้วย call ก่อนตั้งยอดเป็นศูนย์ ถ้าผู้เรียกเป็น contract ฟังก์ชัน receive ของผู้เรียกจะทำงานและเรียก withdraw() ซ้ำได้ขณะยอดยังเท่าเดิม จึงถอนซ้ำจนเงินใน contract หมด วิธีแก้คือย้าย balances[msg.sender] = 0; ไปไว้ก่อน call (Checks-Effects-Interactions) และเพิ่ม modifier nonReentrant ได้อีกชั้น
